## 0. 우선 지금 무엇이 잘못됐는지 인정하고 시작하라

이번 지시는 문구 교정 요청이 아니다. **개발자가 내부 상황을 사용자에게 변명하는 화면을 걷어내고, 야구팬이 이해하고 즐길 수 있는 실제 서비스를 완성하라는 요구**다.

현재 코드가 테스트를 통과했다는 사실은 인정한다. 하지만 사용자는 다음과 같은 경험을 하고 있다.

- 첫 화면에 `선수만 고르세요. 기록은 자동으로 준비합니다.`, `지원하는 기록은 자동으로 준비하고 이 컴퓨터에 보관합니다. 과제 원본이 필요한 경우에는 처음 한 번만 연결합니다.` 같은 **구현 사정을 설명하는 무가치한 문장**이 반복된다.
- 결과에 `기타 타석 결과` 같은 **통계 구현상의 묶음 이름**이 그대로 노출된다. 사용자는 그게 안타인지 범타인지, 아웃인지, 왜 중요한지 알 수 없다.
- 실제 가상 대결을 봐도 **누가 어떤 경기력을 보인 것으로 계산됐는지, 무슨 사건들이 있었는지, 계산 결과를 어떻게 읽어야 하는지** 이해하기 어렵다.
- Match 첫 화면이 `연구 범위를 먼저 확인하세요`, `3아웃 전에 한 점... 제한된 실험`, `투구별 판단·9이닝 승리 학습·역사 비교는 다음 단계`라는 **미완성 안내문을 보여주는 데 많은 지면을 사용한다.** 사용자는 개발 로드맵이 아니라 **지금 실행되는 AI 경쟁과 실제 전략 변화**를 보고 싶다.
- `통계 대결은 AI 학습이 아닙니다. 검증 전엔 연결하지 않습니다.` 같은 내용은 내부 설계·연구 타당성 관리에는 중요하지만, 이것을 대문짝만 하게 보여주는 것이 제품을 개발한 것은 아니다.
- 데이터의 확보·형식·원본 연결·갱신·호환 문제를 사용자가 이해해야만 서비스가 돌아가는 구조여서는 안 된다.

**매번 지시서를 받아 문장과 버튼만 살짝 바꾸고 테스트 개수만 늘리는 식의 대응을 중단한다.** 다음 산출물은 `어떤 코드를 바꿨다`가 아니라 `사용자가 실제로 더 잘 쓰게 되었다`는 증거여야 한다.

### 기존 작업 상태를 정확하게 확인할 것

확인된 저장소 근거:

- `src/baseball_lab/matchup/models.py`: 사건 분류는 삼진/볼넷/사구/단타/2루타/3루타/홈런/**other**의 8개 범주이며 `other`를 `기타 타석 결과`로 노출한다.
- `src/baseball_lab/matchup/service.py`: BaseballLab/EraMatch가 확률 모델·반복 타석 서비스 경계를 공유한다. 현재 이 기능은 **독립 타석 반복**이지 9이닝 전체 경기 시뮬레이터는 아니다.
- `docs/incremental-redesign-validation.md`: MLB 2023·2024, KBO 과제, 기존 Match 보존과 **196개 테스트 통과**를 보고한다. 이 숫자는 사용자 이해도나 야구 시뮬레이션의 완성도를 증명하지 않는다.
- `docs/PROJECT_STATUS.md`: Match의 정밀 투구 판단·전체 경기 승리·인간과의 역사적 비교는 아직 구현 완료되지 않았다.

**작업 시작 전 현재 HEAD를 다시 확인하고, 이 문서와 이후 변경을 대조하라. 이미 개선된 내용은 중복 구현하지 말고 실제 브라우저에서 검증할 것.**

## 1. 변하지 않는 프로젝트 정의 — 다시 혼동하지 말 것

| 프로젝트 | 사용자 관점 기능 | 핵심 책임 |
|---|---|---|
| **BaseballLab** | 타자와 투수를 선택해 실제 자료에 근거한 가상 대결을 실행하고 통계 결과를 확인 | 공통 야구 데이터·규칙·Log5·표본/리그 보정·몬테카를로·대결 계산 엔진·실행 결과 해설 |
| **Match** | AI 타자·투수가 서로 경쟁하고 학습하며 선택과 경기력이 어떻게 달라지는지 관찰 | 타격·투구·볼배합·선수 유형·팀 전략 탐구, 학습 회차별 재평가, 인간 야구의 역사/현대와 비교·해석 |
| **EraMatch** | KBO 역대 선수와 시즌을 선택해 가상 맞대결 | 기존 학교 과제 웹화, 시대 보정, Log5, 몬테카를로, 원본/개선 계산 비교 |

BaseballLab 자체는 기능 있는 시뮬레이터다. **EraMatch에 인간 야구 대 AI의 발전사 비교를 떠넘기지 말 것. 그 최종 연구 질문은 Match 소유다.** 세 프로그램은 공통 데이터·계산 모델·UI 컴포넌트를 재사용하되 서로 다른 사용자 목적을 가진다.

기존 학교 과제는 참고 구현이다. 과제 계산을 재현하는 모드와 실제 데이터에 맞게 검증·개선한 모델을 구분한다. 어떤 모델이 현실에서 더 타당한지는 별도 홀드아웃 데이터·성능 비교 없이 단정하지 않는다.

## 2. 최상위 제품 규칙: 사용자는 야구를 보러 왔다

### 2.1 화면에 **두지 말아야 할 것**

일반 화면의 제목·주요 카드·CTA·결과 요약에서 다음을 금지한다.

- 구현 자랑: `자동으로 준비합니다`, `이 컴퓨터에 보관합니다`, `저장소를 재사용합니다`, `과제 원본을 한 번 연결합니다` 같은 내부 처리 설명의 반복.
- 개발 진척 변명: `현재 제한된 실험`, `추후 예정`, `다음 단계`, `지원 범위를 먼저 확인`, `미구현`, `스키마`, `소스 해시`, `모델 버전`, `seed`, `policy`, `donor`, `checkpoint` 등을 사용자 행동보다 앞에 놓는 화면.
- 의미 없는 격려/안내: `선수만 고르세요`, `결과와 이유를 함께 보여드립니다`, `직관적으로 확인하세요`, `연구를 시작하기 전에...` 같은 당연한 문장을 반복하는 패턴.
- 숫자를 정확히 설명하지 못하는 애매한 결론: `수비 AI 우세`, `진짜 실력`, `더 좋은 방식`, `과학적으로 입증` 등 근거 밖의 단언.
- **기능이 없는 자리에 대형 설명문만 넣고 개발 완료라고 주장하는 것.**

중요한 제약은 **숨기지 말되, 화면의 적절한 위치에 결과와 연결해 간결하게** 알려라. 예컨대 25타석 통계 대결을 실제 9이닝 스코어처럼 표현하는 것은 금지다. 다만 그 사실을 설명하는 문단을 홈 전체에 붙이지 말고 결과의 기준·도움말에 한 문장으로 둔다.

### 2.2 화면에 **반드시 있는 것**

- 사용자가 누를 수 있는 명확한 시작점: `선수 대결`, `AI 대결 학습`, `역대 선수 대결`.
- 선수 이름 검색·연도 선택·비교 상대·실행 버튼. 기초값은 합리적인 기본 선택을 제안하고 변경할 수 있어야 한다.
- 결과의 첫 줄에 **실제로 발생한 대결 요약**: 누구 vs 누구, 몇 타석, 안타/삼진/볼넷/장타 등. 가능한 자료에 따라 그럴듯한 경기 스코어를 조작하지 않는다.
- 결과 아래에 **왜 이런 분포가 나왔는지**: 두 선수의 원본 수치 → 보정 → 최종 확률 → 이번 반복 추첨 결과를 연결해 보여 준다.
- 필요할 때 열어 보는 통계 설명: Log5, BABIP, FIP, K/9, BB/9 등의 정의·분모·데이터 출처·**이번 계산에 실제 반영했는지 여부**.
- 실제 반복 결과를 다루는 탐색: 중요한 사건 필터, 타석별 카드, 이전/다음, 타격 결과 분포, 기대값과 이번 실행값 비교.
- 이 앱에서 못 하는 일을 길게 나열하기보다 **지금 할 수 있는 행동을 완성된 흐름으로 제공**한다.

### 2.3 용어 사전과 문장 감수는 독립적으로 실시

개발 코드의 식별자와 화면 텍스트를 분리한다. 실제 데이터 스키마는 안 바꾸더라도 화면에 나오는 용어·툴팁·설명은 야구팬 기준으로 작성한다.

| 현재 또는 금지 표현 | 수정 방향 |
|---|---|
| `기타 타석 결과` | **실제 원천을 분석해 세부 사건을 분리**. 불가능한 범위만 `그 밖의 결과`로 표시하되 정의·포함 범주·건수를 정확히 설명. `아웃`으로 임의 치환하지 말 것. |
| `일반타석 / 정상승부` | 추상 묶음임을 드러내는 정확한 자연어 설명으로 교체하고, 가능하면 실제 관측 행동 단위로 세분화. |
| `고정 기본정책` | `학습하지 않는 비교 상대`처럼 맥락을 설명하는 말로 표현. 기술 용어는 상세 분석에서만. |
| `모델이 생성한 한 점 득점 상황` | `주자·아웃 조건을 정해 반복한 득점 실험`처럼 실제 동작을 명시. |
| `선수만 고르세요` | 불필요하면 삭제. 사용자가 선택해야 할 항목은 실제 필드 레이블로 충분. |
| `AI 학습은 아닙니다` | BaseballLab/EraMatch의 표제 문구로 쓰지 말 것. Match에만 AI 학습 진입 기능을 명확하게 배치. |
| `이번 조건에서는 우세` | 어떤 지표·비교 상대·측정 기간인지 구분한 후에만 결론. 승패의 기준이 정의되지 않으면 숫자 그대로 표현. |
| `독립 타석`, `범주형 모델`, `홀드아웃`, `재표집` | 일반 화면에서는 실제 예시로 설명. 정확한 수학 용어는 `계산 과정` 패널에 유지. |

**기술적으로 틀리지 않은 말이더라도 사용자가 읽고 `그래서 뭐가 나왔다는 거야?`라고 묻게 되면 실패다.**

## 3. 최우선 P0: `기타 타석 결과`라는 블랙박스 해결

### 3.1 단순 레이블 교체로 끝내지 말 것

현재 `EVENTS`의 마지막 `other`는 **삼진·볼넷·사구·1루타·2루타·3루타·홈런 외 모든 것을 한꺼번에 묶은 잔여 범주**다. 이 안에는 타구로 인한 아웃, 희생타 및 기타 사건이 포함될 수 있지만, **현재 분류만으로 그 개별 비중을 알 수 없다.** 따라서 `기타 타석 결과 = 범타`라고 부르는 것은 오정보다.

구현 지시:

1. Retrosheet 원천의 이벤트 코드/플레이별 기록과 현재 정규화 로직을 조사해 **실제로 분류 가능한 사건을 식별**한다. `event_code`의 의미를 공식 정의와 대조한다.
2. 단일타석·플레이·비타석 사건을 구분해 **사건 분류표, 우선순위, 타석 분모, 중복 배타성 규칙**을 문서화한다. 파울, 도루 등 타석 종료가 아닌 사건을 억지로 하나의 타석 결과로 만들지 않는다.
3. 가능한 경우 `삼진`, `볼넷`, `사구`, `안타(단타/2루타/3루타/홈런)`, `기록에서 구분되는 아웃`, `희생타/희생플라이`, `실책 출루`, `그 밖의 세부 확인 불가`처럼 **자료로 확인 가능한 수준만** 결과 화면에 보여준다. 수비 선택/희생타/공식기록 기준이 겹치는 부분은 배타적 분류로 검증한다.
4. `other` 세분화 때문에 기존 학습 모델/저장 JSON이 깨져서는 안 된다. **원본 사건 코드 보존 + 별도 표시용/향후 모델용 분류 어댑터**로 단계적으로 이행한다. 분류 체계를 변경해 실제 새 모델에 쓰는 경우 버전·재학습 필요 여부를 명시한다.
5. KBO 과제처럼 시즌 집계만 있어 원천 세부 사건이 없는 경우 **없는 세부 사건을 생성하지 않는다**. 해당 묶음은 `그 밖의 결과`로 표시하고 정확히 어떤 항목을 제외한 나머지인지 계산 정의를 보여준다. 가능하면 공식 자료 보강으로 해결한다.
6. 결과에 `그 밖의 결과`가 나타나면 **구체적인 포함 항목/확인 불가 사유가 클릭 한 번으로 보이고, 사용자는 아웃인지 안타인지 혼동하지 않아야 한다.**

### 3.2 반드시 만들어 볼 실제 결과 화면의 형태

- **대결 제목:** `백인천(1982) vs 원태인(2024)`.
- **첫 문장:** `25타석 대결에서 안타 ○개, 삼진 ○개, 볼넷 ○개가 나왔습니다.` — 동그라미는 **실제 실행에서 계산한 수치**로 대체할 것. 무작위 예시 수치를 고정해서 표시하면 안 된다.
- **사건 분포:** 결과별 발생 횟수와 모델상 예상 횟수를 같은 그래프에 표시한다. 분모 25타석을 명확히 보여준다.
- **이해에 필요한 해설:** `이번 결과의 삼진이 예상보다 몇 개 많거나 적은지`, `두 선수의 어떤 기록이 계산에 반영됐는지`, `시대 보정이 어느 값을 얼마나 바꿨는지`를 실제 값과 연결해 설명한다.
- **더 알아보기:** 사용된 Log5 수식, 표본 회귀, 시대 보정, 데이터 출처, 원본 과제 재현 방식. 처음부터 긴 논문형 문장을 붙이지 말 것.

같은 선수·시즌·난수/횟수·모델이면 **같은 결과가 재현돼야 한다.** 사용자가 모르는 난수 번호를 조작해야만 재현되는 UX는 피한다.

## 4. P0: 세 프로젝트의 사용자 여정을 진짜로 다시 만들 것

### 4.1 홈: 불필요한 자기소개는 치우고 곧바로 기능으로

추천 구성:

- **선수 대결:** `MLB/KBO의 타자와 투수 맞대결 계산` — 지원 가능한 원천에 맞춰 정확히 표기.
- **AI 전략 연구:** `AI가 반복 대결하며 바꾸는 선택과 성과 관찰`.
- **역대 선수 대결:** `서로 다른 시대의 KBO 선수 맞대결`.

카드에는 실제로 동작하는 핵심 실행 버튼 하나씩. 하단의 `이 컴퓨터에 보관`, `지원하는 기록 자동 준비`, `원본을 처음 한 번 연결` 같은 운영/설정 문단을 제거한다. 공통 데이터 사용법은 **데이터 관리 화면이나 실제 문제가 발생했을 때**만 설명한다.

### 4.2 BaseballLab: 대결 도구로서 완성

**첫 화면:** 리그 → 시즌 → 타자·투수 검색 → 대결 실행. 추가 설정은 필요할 때만 연다.

**결과 화면의 순서:**

1. 선수/연도, 대결 수, 이번 결과를 한눈에.
2. 안타·장타·삼진·볼넷·사구 및 자료에서 확인 가능한 구체적 결과의 구성.
3. 예상 결과와 이번 난수 실행 결과의 차이, 반복 시 얼마나 달라질 수 있는지.
4. 이 결과의 계산 근거: 각 선수 기록 → 리그 기준 → 보정값 → 승부 확률 → 추첨.
5. 타석별 결과 탐색·필터·다시 실행·저장.

중요: 현재 독립 타석 모델이므로 주자·아웃·점수를 거짓으로 그리지 않는다. 대신 **시각적으로 충분히 납득 가능한 타석/선수/결과 중심 화면**을 만든다. 장기적으로 실제 이닝/주루/수비 모델을 도입할 때 9이닝 경기 화면으로 확장한다.

### 4.3 EraMatch: 과제 기반의 재미있는 역사 대결로서 완성

- 1982~2025 KBO 과제 데이터에서 실제 지원되는 선수/시즌을 빠르게 검색·선택.
- 선수 이름이 같거나 이적 기록이 중복돼도 정확히 식별하고 기록을 적절히 집계.
- 선택한 두 시대의 시즌 기록과 시대 보정 전후 변화를 시각화.
- **25타석 가상 대결**을 누르면 결과가 즉시 이해되고, 반복 횟수도 변경 가능.
- 기존 과제 재현/개선 계산을 선택할 수 있으나, `원본 방식이 더 사실적이다` 또는 `개선 방식이 검증됐다`고 말하지 않는다.
- KBO 원본 연결을 반복 요구하지 않는다. 신뢰할 수 있는 합법적인 배포 경로가 있으면 시스템이 자동 준비하도록 우선 개발한다. 허가·권한이 없는 원천을 무단 재배포하지 않는다. 최초 사용자 제공이 유일하게 가능한 경우에만 **필요한 순간 단일 연결 동작**을 제공한다. 연결이 불가능할 때 대체 시즌으로 조용히 바꾸지 않는다.

### 4.4 Match: `현재 미완성` 설명문을 서비스의 중심에서 제거

**지금 사용자에게 가능한 학습을 실제로 실행하고, 그 과정을 보여주는 화면을 만들어야 한다.**

사용자 첫 흐름:

1. `AI 대결 학습 시작` — 실제로 동작하는 선택 항목 제공.
2. 두 AI의 목표·이번 실험에서 실제로 선택할 수 있는 행동을 **짧고 정확히** 제시.
3. 학습 전 → 중간 → 학습 후를 같은 조건으로 평가하고 비교.
4. **AI가 언제 어떤 선택을 늘리거나 줄였는지**, 그 후 동일 상대에게 성과가 어떻게 바뀌었는지.
5. 과거 체크포인트/고정 상대/서로 다른 초기화와 대결해 발전·후퇴·순환을 보여 줌.
6. 실제 인간 데이터와 비교할 수 있는 범위의 비교를 시작하고, 과장된 `미래 야구의 정답` 결론을 내지 않는다.

현재 R1(3아웃 전 1점 득점/차단)은 **유효한 기존 실험으로 보존**하되, 이를 전체 Match 연구 완료처럼 포장하지 않는다. 다음 개발에서는 `연구 범위 설명 페이지`를 더 만드는 대신 **현실 자료가 뒷받침하는 다음 행동/상황 실험을 실제로 하나 이상 작동시키는 것**을 목표로 한다.

- 우선 실제 투구별 데이터의 접근/이용 조건·표본·관측 가능 필드를 조사하고, **타자 선택과 투수 선택이 각각 독립적으로 바뀌는 최소의 투구 단위 학습 실험**을 구현한다. 가능하면 카운트·구종·공의 위치·스윙/기다리기부터 시작한다.
- 실제 자료만으로 선택하지 않은 행동의 인과 결과를 알 수 없는 부분은 별도 모델 검증·민감도 시험을 수행한다. 근거 없는 구속, 제구 능력, 볼배합의 성공률을 만들어서 `AI 자율 진화`로 발표하지 않는다.
- 적법하게 사용할 수 있는 정밀 데이터에 접근할 수 없다면 **구체적인 접근 불가 근거, 실행 가능한 대체 행동·결과 모델, 실제로 돌아가는 최소 연구 범위**를 보고하고, 기존 R1만 고쳐서 차세대 AI가 완성됐다고 주장하지 않는다.
- 후속 기술 학습(컨택/파워, 구종 조합·제구, 선수 유형, 팀 전체 승리)과 인간 현대/역사 비교는 **Match의 연구 소유권 아래 계속 개발**한다. EraMatch에 떠넘기지 않는다.

**개발하지 않은 기능은 거짓 버튼으로 내놓지 말고**, 실제로 구현 가능한 다음 한 단계를 완성한 뒤 테스트 결과로 보여라. 구현 불가능한 이유를 설명하는 문서를 '기능 구현'으로 계산하지 않는다.

## 5. P1: 데이터 문제를 사용자에게 떠넘기지 않도록 설계

- 공통 `DatasetCatalog`를 모든 프로그램의 데이터 단일 진입점으로 삼고, 자료 제공자별 어댑터/정규화/검사/캐시/갱신을 분리한다.
- 등록·허용된 자료는 사용자 선택 시 자동 점검 및 준비한다. 가져온 파일의 **원천, 리그, 시즌, 필드 의미, 단위, 경기를 분리한 검증, 해시, 라이선스**를 기록한다.
- 기존 KBO 1982~2025 과제 자료, Retrosheet 2023·2024, 향후 MLB/KBO 공식 데이터 등 사용 가능한 모든 자산을 **중복 없이 카탈로그에 등록**한다. 더 많은 연도를 검증할 수 있으면 점진적으로 지원을 확장한다.
- `사용할 수 있는 시즌이 없음` 등 실제 입력 부족 상태와 `인터넷 일시 실패`, `원천 라이선스 제한`, `자료 검증 실패`를 구별한다. 실패 시 **사용자가 고른 시즌·선수를 유지**하고 실제 복구/재시도 동작을 제공한다.
- 앱이 스스로 해야 하는 다운로드·검사·재사용을 소개 문장으로 길게 설명하지 말고 **행동으로 구현**하라. 재다운로드·원본 수동 입력을 불필요하게 반복시키지 말라.
- 데이터가 결측이라고 임의로 0 처리해 사실이라고 말하거나, 다른 리그 통계를 가져와 없는 선수 능력을 사실처럼 추정하지 않는다. 추정·관측·테스트 데이터·사실 확인 전 과제 자료를 구분한다.
- 공개 자료의 재사용/자동화가 허용되지 않으면 조건을 지키되, 이 법적 제약 때문에 모든 사용자 경험을 포기하지 말고 **허가된 공급원·기존 로컬 자료·정식 사용자 연결 경로**를 조사해 구현한다.

## 6. P1: 통계 모델은 공통으로, 연구 결과는 정직하게

기존 과제의 평균 회귀·시대 보정·Log5·몬테카를로를 활용하되 다음을 유지한다.

- 선수의 타석 수와 투수가 상대한 타자 수를 혼동하지 않는다.
- 서로 배타적인 사건 확률의 합은 1이어야 한다. 필요하면 다항 사건 모델을 쓰고 사건별 검증을 남긴다.
- 원본 과제 재현 모델은 `원본 재현`, 개선 모델은 `검증된 범위만큼의 예측 모델`로 표시한다.
- 동기간·다기간의 훈련/검증/최종평가 경기 누수를 방지하고 시즌 간 성능을 실제로 측정한다.
- **통계적 투타 대결 확률 예측**과 **AI가 행동을 선택할 때 발생할 반사실 효과**는 다른 문제다. 같은 계산 엔진·공통 인터페이스를 쓰되 전자는 후자의 인과 검증을 자동 보장하지 않는다.
- 모든 모델에서 확률·표본·가정·불확실성을 저장한다. 그러나 사용자 첫 화면에는 해당 학습을 하지 않은 기술 용어를 늘어놓지 말고, **이번 선택의 결과를 읽는 데 실제 필요한 설명만** 보여준다.

## 7. 역할을 나누되, 책임이 분산되는 다중 에이전트 놀이를 금지

기존 `AGENTS.md`와 설치된 스킬·서브에이전트가 있다면 활용한다. 단, **실제 실행 환경에서 지원되는 기능만** 사용하고 지원하지 않는 것을 썼다고 꾸미지 말라.

| 담당 | 반드시 제출할 실물 산출물 |
|---|---|
| 제품 오너/기획 | 야구팬 입장에서 홈→선수선택→실행→결과 이해까지의 화면 구조·단어 감수, 기존 화면 문제 목록 |
| 데이터 담당 | `other` 원천 분류 감사, KBO/MLB 자료 갱신·원천/권한 검토·결측/중복 검사 |
| 야구·통계 담당 | 사건 정의·Log5/표본/시대 보정·확률 합·검증 지표·모형 사용 범위 검토 |
| 프런트엔드/UX 담당 | 실제 동작하는 3개 사용자 화면, 결과 시각화, 모바일/키보드, 불필요한 문구 제거 |
| Match·AI 담당 | 실제 학습 실행, 행동 변화·성능 비교·다음 실험의 코드/테스트, 인간 비교의 첫 단계 |
| QA·보안 담당 | 현행 코드 회귀, 실제 브라우저 E2E, 금지 문구 스캔, 실제 결과 해설 테스트, 보관 자료/권한 검사 |

**메인 에이전트가 최종 소유자다.** 에이전트별로 수정 파일과 인터페이스를 나누고 같은 파일 동시 수정을 최소화한다. 서브에이전트가 `완료`라고 해도 메인에서 실제 동작을 재현하지 못하면 완료가 아니다.

## 8. 절대 양보하지 않는 완료 기준 (Definition of Done)

다음 체크를 통과하지 못하면 **`완료`라고 보고하지 말 것**.

### A. 사용자 언어

- [ ] 홈/선수 대결/EraMatch/Match 주요 화면에서 불필요한 구현 설명·미래 로드맵·`선수만 고르세요`류의 문장을 삭제했다.
- [ ] 일반 화면의 수식·정책·상태 코드가 야구팬 친화적 문장 또는 명확한 사건 이름으로 치환됐다.
- [ ] `기타 타석 결과`를 실제 정의 없이 그대로 내보내지 않는다. 잔여 범주를 표시한다면 포함 범위와 **분류할 수 없는 이유**를 정확히 알 수 있다.
- [ ] 결과 첫 화면만 읽어도 **누구와 누구의 몇 타석 대결에서 무슨 일이 몇 번 있었는지** 알 수 있다.
- [ ] 결과의 숫자, 비율, 비교 결과를 실제 데이터와 일치시키고 값이 바뀌면 설명도 함께 바뀐다.

### B. 실제 기능

- [ ] BaseballLab에서 지원하는 MLB 시즌/선수를 선택하고 대결을 실행·다시 실행·저장 재열기 할 수 있다.
- [ ] EraMatch에서 KBO 서로 다른 시즌 선수 대결을 원본/개선 방식으로 실행하고 결과 차이를 이해할 수 있다.
- [ ] Match에서 기존 학습이 정상 실행되며 **학습 전/중간/후의 행동·동일 상대 성과를 직접 탐색**할 수 있다.
- [ ] Match의 다음 실험에 대해 **문서가 아닌 실제 코드·연구 결과·실행 화면** 중 의미 있는 개발 진전이 있다. 연구 타당성 문제는 통제·검증하고 허위 성과를 내지 않는다.
- [ ] 새 설치/기존 저장 데이터/오프라인/자료 미보유 상황에서 불필요한 반복 입력이나 상태 혼란이 없다.

### C. 검증·보존

- [ ] 실제 Chromium에서 홈→각 프로젝트→실행→결과 해설→근거 확인→저장 결과 재열기를 직접 테스트했다.
- [ ] PC 및 모바일 너비에서 표/그래프 잘림, 가로 넘침, 키보드 포커스, 콘솔 오류를 확인했다.
- [ ] **야구를 아는 비개발자 관점의 질문 5개**에 화면만 보고 답할 수 있다: 누구와 누구인가? 결과는? `그 밖의 결과`는? 왜 이런 확률인가? Match AI가 학습 후 무엇을 바꿨는가?
- [ ] 기존 pytest 회귀 전체를 통과하고, 기존 연구 데이터·체크포인트·사용자 파일을 임의 변경하지 않았다.
- [ ] 새 사건 분류/데이터 처리 변경에 대한 테스트: 합계·중복·결측·원천/추정 구분·분모·시즌·난수 재현성을 확인했다.
- [ ] Git에 비공개 원본·자격정보가 실수로 포함되지 않았고 보안 기본 방어가 후퇴하지 않았다.
- [ ] 화면 캡처를 **변경 전/후**로 나란히 보고하고, 각 수정이 어떤 사용자 불편을 없앴는지 명시했다.

### D. 완료 보고 양식 — 코드와 증거만

최종 답변은 아래 형식으로 간단히 작성하라.

1. **바뀐 사용자 경험**: 화면/메뉴별로 무엇을 눌러 어떤 결과를 볼 수 있는지 (실제 캡처 링크).
2. **바뀐 실제 기능**: 구현된 코드 경로, 데이터/모델/실험의 실제 변화.
3. **`기타 타석 결과` 문제 처리**: 어떤 사건을 실제 원천으로 나눴는지, 분류 못 한 것은 무엇인지.
4. **실제 사용 시연**: MLB 대결 1건, KBO 시대 대결 1건, Match 학습 비교 1건의 실행 과정과 결과.
5. **검증 수치와 실패**: pytest, 브라우저, 사용자 이해도, 해결 못 한 문제, 원본 보존 검사.
6. **커밋/PR**: 변경된 파일·커밋 링크. 기존 저장소 유지 확인.

**장황한 자기평가, 테스트 숫자만 나열하기, 미래에 할 수 있다는 이야기로 개발 완료를 대신하지 말라.**

## 9. 이 지시를 실제로 수행하는 순서

**첫 작업 — 현재 화면을 직접 열어 3개 프로젝트의 사용 흐름을 기록한다.** 기존 결과를 열고 사용자가 이해 못 할 문장을 전수 수집하며, 코드의 해당 위치를 표시한다.

**둘째 — 결과 사건의 의미와 통계 설명을 정비한다.** `other` 사건을 원천에서 분류할 수 있는지 조사하고, 가능한 분류를 반영한다. 사용자가 읽을 수 있는 결과 서술·그림·비교를 구현한다.

**셋째 — 홈/대결/시대대결/Match의 화면 구조와 상호작용을 개선한다.** 설명문과 연구 로드맵으로 빈 공간을 채우지 않는다. 기능을 중심으로 보여주고 세부 근거는 필요한 위치에서 열 수 있게 한다.

**넷째 — Match의 다음 실제 연구 기능을 개발한다.** 확보한 실제 데이터/검증 범위에서 동작 가능한 연구를 선택해 코드·실행·평가를 남긴다. 단순 UX 수정과 미완성 항목 안내를 Match 개발로 포장하지 않는다.

**다섯째 — 데이터 공급/초기 설정/사용자 선택의 실패 흐름을 고친다.** 적법한 자동 제공을 우선하고, 검증되지 않은 자료를 만들어 통과시키지 않는다.

**여섯째 — 전체 회귀, 브라우저 E2E, 사용자 언어 감수, 데이터 원본 보존 테스트 후 커밋한다.** `원래 기능이 되던 것은 계속 되는가`를 먼저 증명한다.

## 마지막 지시

**이 프로젝트를 사용하는 사람은 개발자가 아니다. 사용자는 야구의 대결과 AI의 발전이 궁금해서 들어온다.**

`이 기능은 연구 범위가 제한됩니다`, `기록을 자동 준비합니다`, `이것은 AI 학습이 아닙니다`라는 문장을 더 아름답게 고쳐 쓰는 것은 해결책이 아니다. **작동하는 기능을 제공하고, 사용자가 결과를 해석하고 다음 행동을 할 수 있게 만드는 것이 해결책이다.**

사용자를 위해 설명해야 할 것은 개발 구조가 아니라 **실제 야구 사건, 선택, 결과, 계산 근거, AI의 전략 변화**다.

작업을 끝내기 전 스스로 질문하라.

> **“이 화면을 처음 보는 야구팬이 개발자에게 물어보지 않고 대결을 실행해, 왜 이런 결과가 나왔는지 이해하고, 다음 시뮬레이션을 해보고 싶어질까?”**

그렇지 않다면 테스트가 모두 통과했어도 아직 완료가 아니다.
