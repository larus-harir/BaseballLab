> **문서 성격:** 프로젝트 기획자의 판단 + Codex 실행 지시서

> **중요:** 이 문서는 기존 프로젝트를 처음부터 재작성하라는 요청이 아니다. **현재 구현을 살리면서 원래 연구 목적을 실제로 달성하도록 우선순위를 교정**하는 요청이다.

## 1. 우리가 만들고 싶었던 것 — 이 한 문장이 최우선이다

**“현실적인 야구 규칙과 실제 기록으로 검증된 환경에서 AI 타자와 AI 투수가 오직 경기의 승리를 위해 반복 경쟁한다면, 어떠한 플레이·전술·스타일을 스스로 발전시키는가? 그 변화는 인간 야구의 역사와 현대 전략에 비추어 어떻게 해석되는가?”**

핵심 관심사는 승률 하나가 아니라 **전략이 생기는 과정, 상대에 따른 재적응, 의외의 선택, 수렴·순환·정체, 그리고 인간 야구와의 비교**이다. AI가 인간과 다른 혁신적인 전략을 반드시 찾아야 성공인 것도 아니다. 실제 데이터와 신뢰할 만한 가정의 범위에서 결과를 재현하고 평가할 수 있으면 연구로서 의미가 있다.

- **부모:** Baseball AI Lab — 공통 데이터·규칙·경기 엔진·학습·평가·기록·시각화.
- **첫 자식 E01:** 타자 vs 투수의 경쟁 학습 및 전략 진화 연구.
- **후속 E02:** MLB AI와 KBO AI를 각각 학습시킨 뒤 **동일한 평가 규칙·능력 제약** 아래 대결. 리그 전략 차이와 선수 구성의 차이를 구분해야 함.
- 이후 시대별 야구, 플레이스타일, 규칙 변화, 팀 전술 연구를 같은 플랫폼 위에 추가.

이 프로젝트는 **일반 승패 예측기**, **기존 야구 스타일 모방기**, **임의 난수 야구 게임**, **그래프만 있는 통계 서비스** 중 어느 것도 아니다.

## 2. 현 상황 판정 — 초기 의도에 맞는가?

**결론: 방향·아키텍처는 대체로 맞지만, 핵심 연구는 아직 실행하지 못했다.** 사용자 제공 요약과 저장소 문서에서 확인한 범위는 다음과 같다.

| 항목 | 판정 | 의미 |
|---|---|---|
| 부모/자식 구조 및 향후 확장 | 유지 | E01 외 프로젝트 확장 방향은 맞음 |
| 웹 실행실, 보고서, 리플레이 틀 | 유지·보완 | 관찰 기능의 뼈대는 있음. **실측 기반 실행 기록은 아직 없음** |
| 타자/투수 신경망 가중치 갱신 | 부분 충족 | 테스트용 생성 자료에서 학습 동작 확인. **실제 학습 성과 아님** |
| 실제 야구 자료의 확보 및 학습 | **핵심 미완성** | 실제 투구 CSV/검증된 모델/실험 결과가 없음 |
| 승리 중심 경쟁 | **핵심 불일치** | 현재 연구 경로는 출루/출루저지 대리목표. 점수·주자·이닝·승패 없음 |
| 의미 있는 전술·볼배합·스타일의 발견 | 제한적 | 현재 타자는 스윙/테이크, 투수는 구종 선택, 관측은 카운트뿐 |
| 인간 역사/현대 야구와 비교 | 미완성 | 아직 유의미한 비교 대상의 학습 전략이 없음 |
| 113개 테스트 통과 | 유효하나 범위 제한 | 프로그램 동작 검증이지 야구 현실성/연구 완성의 증거가 아님 |

### 가장 중요한 문제 4가지 (우선순위 순)

**P0 — 실제 데이터가 없어 'AI 학습 시작'이 연구로 이어지지 않는다.** 현재 코드는 데이터를 검증하는 문지기 기능은 좋지만 문을 통과할 현실 데이터 경로가 막혀 있다. 다음 작업의 최우선 목표는 적법하게 활용할 수 있는 **실제 원천 기록을 확보하고, 반복 가능한 학습까지 성공하는 것**이다. 새로운 화면·보안·검사 함수를 쌓는 일로 이를 대체하지 말 것.

**P1 — 현재 보상이 '승리'가 아니라 '타석 출루'이다.** 처음부터 MLB 9이닝 전체를 구현할 필요는 없지만, 출루율만 최적화한 모델을 승리 전략의 발견으로 해석할 수 없다. 단기적으로 기존 출루 실험은 **실데이터를 통한 파이프라인 점검용 P0 실험**으로만 인정하되, 바로 다음 실험에 실제 경기 기록으로 검증 가능한 **아웃·주자·득점 상태와 종료/승리 맥락**을 넣는 로드맵을 구현 수준으로 구체화할 것. 현재 학습 목표를 화면에서 정직하게 표기할 것.

**P2 — 선택지가 너무 좁아 사용자의 핵심 질문에 답할 수 없다.** 카운트만 보고 스윙/테이크와 구종 선택은 기초 실험으로 의미가 있지만, 타구 방향·컨택/장타·코스·볼배합·번트 등은 행동과 결과의 현실적 연결이 확보돼야 열린다. 지원되지 않는 선택지를 가짜 성공률로 채우거나, 선택지가 없는데도 'AI가 그 전략을 발견하지 않았다'고 결론짓지 말 것.

**P3 — 전략 변화의 의미를 아직 검증할 수 없다.** 서로 함께 발전하는 AI의 자체 승률은 50%에 가까울 수 있다. 고정 기준선, 과거 모델, 동일 환경·동일 평가 예산, 여러 시드에서 **행동 변화와 상대 성적 변화가 실제로 나타났는지** 제시해야 한다. 현실 야구와의 차이는 데이터·규칙·상대·선수 능력·시뮬레이터 편향의 영향을 분리해야 한다.

## 3. 개발 방향: 기존 것을 버리지 말고 '작동하는 연구'를 먼저 완성

### 그대로 유지

- 부모/자식 모듈화 및 E01 플러그인 구조.
- 타석 규칙 엔진, 정책/환경 버전·원천 ID·seed 기록, 과거 체크포인트 보존.
- 웹의 기간 선택·학습 시작·중지·리플레이·전략 비교, 실제/추정/가상/테스트의 구분.
- 누락 데이터 거부, 독립 테스트, 투구 전 정보만 입력하는 정책, 검증 오차 기록.
- 사용자에게 쉬운 한국어로 보여 주는 방식.

### 반드시 수정·완성

- **실제 데이터 경로:** 허용된 출처에서 연구용 데이터 파일을 받아, 선택 기간 필터링 → 보정/검증 분리 → 학습 → 실제 실행 기록을 생성하는 전체 경로.
- **첫 연구 실행:** 동일 데이터와 여러 시드로 타자·투수 경쟁 학습을 실제로 실행해 결과를 관찰할 수 있게 만들기.
- **연구 목표 명칭:** 현재 출루 대리목표를 '경기 승리 AI'로 표시하지 않음. 승리/득점 목표의 실험으로 확장 가능한 최소 상태 전이 설계.
- **전략 화면:** 초구 스윙률, 카운트별 기다리기, 구종 선택 비율, 체크포인트 간 정책 변화, 과거·고정 상대별 성능, 각 값의 표본 수/구간과 실제/가상 출처를 실측 결과로 표시.
- **비교:** AI가 특정 전략을 택한 '원인'은 설명문으로 지어내지 말고 상대 교체·정책 동결·조건 변화 등 통제된 비교로 검증.

### 당분간 하지 말 것

- 화려한 3D 애니메이션, 구현 근거 없는 정교한 투구 궤적.
- KBO AI vs MLB AI, 모든 역사·수비·주루·교체·피로·선수 성장 등을 지금 한꺼번에 구현.
- 현재 모델이 지원하지 않는 번트·파워 스윙·제구 목표 코스에 임의 효과 값을 부여.
- 새 데이터 없이 검사기나 문서만 계속 추가하고 '연구 준비 완료'라고 발표.
- 현재 성능을 '현실 야구의 최적 전략'이라고 홍보.

## 4. 실제 자료 사용 계획 — 현실성 및 사용권 확인을 모두 지킬 것

데이터는 직접 수작업으로 새로 수집해 오라는 요구가 아니라, **공개된 자료의 제공 방법과 실제 이용 조건을 확인하고 소프트웨어가 활용할 수 있도록 연결**하라는 요구다. 다만 허가가 확인되지 않은 자동 수집을 강제하지 않는다.

### 실제 확인 가능한 후보

1. **Retrosheet 공식 제공 플레이별 CSV:** https://www.retrosheet.org/downloads/plays.html  
   경기·이닝·주자·아웃·득점 등 **경기 흐름과 승리 맥락**을 설계할 때 우선 검토. 해당 페이지는 다운로드 자료의 이용과 인용/표시 조건을 설명한다. 관련 조건에 따른 저작권 고지를 구현하고, 적용 범위를 확인할 것. 특정 연도·기록의 상세 수준과 데이터 누락은 검증해야 한다.
2. **MLB Baseball Savant 공식 Statcast 검색/CSV:** https://baseballsavant.mlb.com/statcast_search 및 https://baseballsavant.mlb.com/csv-docs  
   구종·구속·투구 위치·스윙 결과·타구 정보의 현실 보정에 사용. 공개 조회·수동 내보내기가 있다는 사실과 자동 수집·재배포 허가를 혼동하지 말 것. MLB 이용약관과 실제 이용 목적을 별도로 확인.
3. **pybaseball:** https://github.com/jldbc/pybaseball  
   기술적 접근 수단의 후보일 뿐, 라이브러리 설치나 오픈소스 라이선스만으로 원본 데이터의 자동 수집 허가가 생기는 것은 아님.
4. **KBO 공식 기록:** 훗날 E02의 입력 후보. 상세 투구/센서 데이터, 라이선스, 동일 스키마 대응 가능성을 별도로 확인. MLB의 자료로 KBO 빈칸을 채워 'KBO 기반'이라고 쓰지 말 것.

### Codex의 데이터 확보 과제

- 위 후보의 **실제 다운로드 가능 파일·항목·표본 단위·이용 조건·자동화 허용 여부**를 직접 검토하고 저장소 문서에 **확인한 사실/추정/미확인**을 나눠 기록.
- Retrosheet가 적합하면 **공식 제공 다운로드 방식**을 이용해 작은 실제 표본을 우선 확보하고, 출처 고지와 함께 해당 자료를 입력으로 쓰는 실험 경로를 구현. 적법성이 불확실한 소스를 자동 수집하지 말 것.
- Statcast가 필요하지만 자동 수집은 미확인이라면 그 제약을 분명히 표시하고, 공식 내보내기 자료를 한 번 연결해 지속 재사용하는 방식을 현실적인 대안으로 제시. 사용자에게 매 실행마다 CSV를 수동으로 올리게 하지 말 것.
- 실험 목적에 필요한 데이터가 끝내 없다면 무엇이 불가능하고 **가장 작은 어떤 실제 데이터 확보가 선행되어야 하는지** 구체적으로 보고할 것. 가짜 경기와 가짜 수치로 조용히 대체하지 말 것.
- 원본 데이터의 provenance(출처, 기록/획득 날짜, 원본 해시, 필터, 중복 제거, 결측, 라이선스 확인, 데이터 버전)를 남기고 공개 저장소로의 원본 재배포 여부는 이용 조건에 따라 결정.

## 5. 첫 번째 실제 연구 결과(E01-R1)의 합격 기준

**목표: 제한적인 범위더라도 진짜 데이터에 근거한 타자/투수의 반복 학습과 관찰을 성공시키는 것.** 이는 최종 '승리 전략의 끝'을 증명하는 결과가 아니며, 다음 단계로 갈 수 있음을 입증하는 연구 시작점이다.

| 항목 | 반드시 가능해야 하는 것 |
|---|---|
| 데이터 | 실제 출처·원본·날짜 범위·독립 검증 구간을 추적할 수 있어야 함 |
| 결과 모델 | 학습 기록과 독립 데이터에서 분포 및 조건별 오차를 비교하고 가정을 표시 |
| 학습 | 타자와 투수 정책 파라미터가 반복 실행으로 실제 갱신됨 |
| 관찰 | 초구/카운트별 행동 비율, 구종 선택 변화와 체크포인트별 그래프가 실제 실행 로그에서 계산됨 |
| 평가 | 초기/과거/고정/제3의 상대와 **학습에 쓰지 않은 평가 환경**에서 대결, 표본 수·구간·여러 시드 보고 |
| 시각화 | 한 투구씩 넘기는 리플레이 + 상태/선택/결과 + 진화 그래프 + 현실 데이터 검증 화면 |
| 진실성 | 실제 관측·데이터 기반 추정·AI 가상 행동·미검증 가정·테스트용 입력을 명시적으로 구분 |
| 재현성 | 동일 데이터/모델/코드/seed로 재실행 가능, 실패를 성공으로 표시하지 않음 |
| UX | 기간·학습량 등 최소 설정 → 가능한 상태면 **학습 시작** → 결과까지 사용자가 이해할 수 있음 |

### 무엇을 첫 결과로 인정할지

- **E01-R0 (기술 검증, 기존 경로):** 타석 출루 보상 + 스윙/테이크/구종 선택. 실제 자료로 학습·검증하면 **'제한된 타석 전략 실험'**으로 인정. **경기 승리 전략 연구의 완성으로 인정하지 않음.**
- **E01-R1 (사용자 의도에 가까운 첫 본 연구):** 실제 경기 로그를 근거로 한 최소한의 이닝·주자·아웃·득점·경기 승패(또는 명확한 득점 목표) 맥락을 갖춰 경쟁 학습. 9이닝 전체 구현이 필수는 아니지만 **'출루 자체가 목표'에서 벗어나 실제로 점수를 만들거나 상대 득점을 억제하는 선택**을 학습해야 함. 이때 실제 관측으로 검증되지 않은 인과 전이나 행동은 지원하지 않거나 가정으로 분리.
- **E01-R2 이후:** 코스·타격 의도·번트·수비·주루·선수 능력 배분을 **각 기능의 실증 가능성 검토 후** 확장하고, 인간 야구와의 역사 비교를 본격화.

E01-R1이 데이터 제약 때문에 불가능하면 R0의 실제 데이터 학습 성공과 R1의 구체적 장애물/해결 계획을 남길 것. 단, 이를 E01 완료로 선언하지 말 것.

## 6. 학습 모델에서 중요한 현실성 조건

1. **정답 전략을 코드에 주입하지 않는다.** 실제 야구 전략은 기준선/사후 비교용이지 학습 AI가 그대로 따라야 할 답이 아니다.
2. 에이전트 입력에는 투구 결정 **이전 시점에 알 수 있는 정보만** 제공한다. 타자가 투구 전에 실제 도착 좌표나 최종 구종을 아는 식의 미래 정보 누수 금지. 투수가 인간 기록의 사후 결과를 미리 아는 것도 금지.
3. 관측 데이터는 인간이 행동을 선택해 만들어진 기록이다. 예를 들어 원래 잘 치는 공만 스윙한 결과를 가지고 '모든 공에서 스윙하면 그 비율로 안타'라고 계산하면 **선택 편향과 가짜 승리 전략**을 학습할 수 있다. 비교 가능한 조건·표본 수·민감도·반사실 불확실성을 보여 줄 것.
4. 현재 결과 모델의 위치/구속 재추출과 상태 조건부 결과가 인과적으로 충분한지 점검. **모델이 손쉽게 이용할 허점**을 찾는 별도의 대조 실험을 설계.
5. 학습 AI는 자기 대결 50% 승률만으로 발전을 판단할 수 없다. 고정 상대·이전 버전·공통 평가 조건·시드 비교를 포함.
6. 능력치·파워·컨택·제구·피로 등의 변수를 만들 때 실제 측정 근거와 제약을 확보하기 전에는 임의 숫자로 경기 결과를 바꾸지 않는다.
7. 통계 지표(BABIP, wOBA, K/9, BB/9 등)는 **평가/해석/현실 보정**에 사용. 이를 학습의 숨겨진 선호 보상으로 넣어 '스타일 발견'을 연출하지 않는다.

## 7. 화면 설계: AI를 사람이 '보면서 이해'하게 할 것

### A. 실행 화면

- 데이터 출처와 이용 가능 상태, 기간·학습량·실험 번호, `AI 학습 시작` 단일 주 동작.
- 데이터 없음/허용 조건 미확인/불충분 표본 시 실패 원인과 **다음 실제 행동**을 쉬운 한국어로 보여 주되 가짜 진행률/성공 표시 금지.

### B. 한 투구 리플레이

- 스트라이크존 2D, 지원되는 실제 기록의 도착 좌표/구종/구속, 카운트·주자·아웃·점수(미구현이면 미지원).
- 투구 이전 각 AI가 볼 수 있었던 정보, 선택 가능한 행동의 정책 확률, 선택한 행동, 이후의 결과를 시간 순서로 표시.
- 실측 투구와 시뮬레이션 생성 투구의 레이어를 명확하게 구분. 실측하지 않은 궤적/의도는 애니메이션으로 단정하지 않음.

### C. 전략 진화 실험실

- 가로축: 에피소드/학습 회차. 타자 초구 스윙률·카운트별 테이크·투수 구종 선택·성과를 같은 시점 체크포인트로 추적.
- 고정/과거 상대 성적을 매트릭스나 그래프로 비교. 단일 seed나 자기 대결 승률만 표시하지 않음.
- 그래프 점 선택 → 해당 정책 버전과 대표 타석·실패 예시 리플레이로 이동.
- 전략이 변한 것과 **왜 변했는지**는 구별. 인과 해석을 하려면 상대를 고정하거나 바꾼 재실험 등 별도 검증 필요.

### D. 인간 야구와의 비교 (후속, 가능한 범위부터)

- 인간 기록의 카운트별 스윙·구종 비중 등 **동일하게 관측 가능한 지표**를 먼저 비교.
- 서로 다른 데이터 시기·규칙·선수 구성·상대 난이도 차이를 통제하지 못하면 단순 유사/차이만 표시.
- AI 행동의 인간과의 차이를 실력 우열로 곧바로 해석하지 않음.

## 8. 다음 3회 개발 작업 — 이 순서대로

### 작업 1 — 데이터 확보 + 현재 구현의 사실 검증 (**최우선**)

- 지금 `main` 코드에서 자료 부재로 막히는 실제 원인을 확인하고, 실제 허용 데이터 획득 방법을 **작동하는 최소 경로**로 구현.
- Retrosheet·Statcast 중 어떤 데이터를 당장 실제로 이용 가능한지 검토. 특히 Retrosheet 공식 다운로드/고지 조건은 우선 검사.
- 소규모 실제 표본을 한 번 확보했다면 업로드/연결 → 정규화 → 기간 분리 → 결과 모델 적합/검증까지 **증거와 실행 로그**를 제출.
- 성공하지 못하면 '확인한 경로 / 막힌 이유 / 다음 가능한 조치'를 분리해서 쓰고, 실제 학습 완료 주장 금지.

**완료 기준:** 적어도 한 실제 출처에 대해 출처/권리 검토 기록 + 검증된 입력 처리 실험을 보여 주거나, 무엇이 권리/데이터 수준에서 막혔는지 명확한 보고.

### 작업 2 — E01-R0 실제 학습 성공 + 눈으로 확인되는 전략 기록

- 실제 기록 기반 결과 모델의 검증을 통과한 제한 범위에 대해 타자·투수 **정책 갱신을 실제 실행**.
- 여러 학습 체크포인트를 보존하고, 기준선/과거 상대/시드 재평가 수행.
- 웹에서 첫 실행의 실제 자료 출처, 학습 진척, 대표 장면, 정책 변화 그래프, 검증 한계를 쉽게 확인하도록 연결.

**완료 기준:** 실제 데이터 출처와 run ID를 가진 보고서 + 실제 학습 로그 + 최소 2개 체크포인트의 행동 변화/성과 평가 + 재실행 안내. 성능 향상을 강제로 요구하지 않음.

### 작업 3 — 승리 맥락으로 넘어가는 최소 E01-R1

- Retrosheet 등의 실제 경기 기록을 활용해 이닝/주자/아웃/득점 전이의 신뢰성부터 확인.
- 보상은 '출루하기'가 아니라 **득점/실점 또는 종료 시 경기 승패**와 일치하도록 설계. 어떤 수준에서 승리로 간주할 수 있는지 명칭을 정확하게 붙일 것.
- 현재 정책 인터페이스를 유지하면서 상태 확장 및 필요한 행동 확장, 홀드아웃 경기 검증, 평가와 화면을 연결.

**완료 기준:** 가정·데이터·지표·누수 검사·승리 관련 보상을 공개하고, 실제 자료로 검증 가능한 최소 상황 게임에서 학습이 재현됨. 전체 9이닝 구현을 이 단계의 필수 조건으로 삼지 않음.

## 9. Codex에게 필요한 작업 방식과 최종 보고 형식

- **사용자에게 이해하기 쉬운 한국어**로 먼저 5줄 요약: `지금 되는 것 / 안 되는 것 / 이번에 한 것 / 근거 / 다음 일`.
- 코드 작성 전에 **프로젝트 원래 목표와 현재 구현의 3가지 괴리**를 인정하고 짧게 계획 제시.
- 기존 코드/테스트가 유효하면 최대한 재사용. '전부 다시 만들기' 금지.
- 불필요한 추가 기획 질문/끝없는 문서화 대신 우선순위 높은 **실제 코드·실행·검증**을 진행. 단 접근 허가나 제3자 사용권은 임의로 가정하지 말 것.
- 변경마다 실제 명령, 테스트 결과, 데이터/모델/run ID, 어떤 기간·표본으로 평가했는지 표시.
- `테스트 통과`, `실제 데이터 적합`, `현실성/인과 검증`, `승리 목적 달성`을 **별도의 상태**로 보고.
- 시뮬레이터가 없는 결과를 만든 것처럼 꾸미지 않고, 실패·불확실성도 그대로 보고.
- 변경을 Git에 커밋하고 사용자의 기존 GitHub 흐름에 맞춰 반영하되, 사용권 불분명한 원본 데이터를 퍼블릭 저장소에 올리지 말 것.
