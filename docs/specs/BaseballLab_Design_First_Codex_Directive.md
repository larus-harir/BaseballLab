## 0. 이번 지시가 나온 이유 — 변명 말고 제품을 고쳐라

최근 여러 차례 '사용자 친화적으로 바꿔라'고 지시했는데, 결과는 쓸데없는 안내 문장을 긴 한국어로 바꾸거나, 개발자용 설명을 접었다 펴는 형태로 남기는 수준이었다. **문장만 짧아지는 것은 UX 개선이 아니다.**

최신 코드 기준으로 명확히 확인한 문제:

- `web/portal.html`: **BaseballLab / Match / EraMatch 세 카드**가 여전히 병렬 진입점이다. 이제 선수 대결은 하나로 합쳐라.
- `web/matchup.html`: 왼쪽에는 선수 선택·결과·여러 펼침 목록, 오른쪽에는 '실제로 관측된 것은?', '두 기록을 어떻게 결합하나요?', '숫자를 어떻게 읽나요?' 같은 긴 텍스트가 반복된다. **정보 밀도는 높은데 핵심을 읽기 어렵다.**
- `web/match.html`: `세 아웃까지 득점 쌓기`, `한 점 먼저 내기` 등 내부 실험 구조를 그대로 사용자 메뉴로 내보낸다. **연구 방법을 사용자에게 설명하라고 맡긴 것이 아니다.**
- `web/matchup.html`: 확률과 추첨 결과, 출처와 모델 한계, 재현 번호 등 서로 다른 독자를 위한 정보가 한 흐름에 섞여 있다.
- 같은 화면 곳곳에서 '이건 9이닝이 아닙니다', '미검증입니다', '기록을 준비합니다' 같은 문장을 반복한다. **정확한 고지는 유지하되, 화면 전체를 변명문처럼 만들지 마라.**

**완료 기준은 '테스트 N개 통과'가 아니다.** 처음 온 야구팬이 몇 초 안에 버튼을 찾고, 대결을 실행하고, 주요 결과를 이해하며, 궁금하면 별도 탭에서 계산법을 확인할 수 있어야 한다.

## 1. 제품 구조 확정 — 사용자 화면에는 두 가지 경험만

### A. **선수 가상 대결 (EraMatch) — MLB와 KBO 통합**

- 홈의 메인 카드는 **선수 가상 대결** 하나만. 별도의 `BaseballLab 선수 대결` 카드는 없앤다.
- 화면에서 **리그 MLB / KBO를 선택**하고, 해당 리그의 시즌·타자·투수를 고른다.
- 같은 시즌 / 다른 시대 대결 모두 **실제 해당 데이터와 검증 가능한 계산 방식이 허용하는 범위**에서 제공한다.
- MLB의 현재 확보 범위(예: 2023·2024), KBO의 현재 확보 범위(1982~2025)를 무작정 동일하다고 표시하지 않는다. 확보한 자료에 따라 옵션을 채운다.
- 다른 시대 대결을 일반 대결과 별도 프로그램으로 갈라놓지 않는다. 시즌 선택만 다르게 한다.
- 공통 `matchup` 데이터·확률·몬테카를로 엔진을 그대로 사용한다. MLB/KBO를 화면에서 합친다고 미검증 모델을 동일한 정확도로 보증하지 않는다.
- 기존 `/baseball` 북마크·저장 결과·딥링크는 **새 `/eramatch`로 호환 이동**하거나 해당 결과를 정상 표시한다. 기존 저장 데이터의 `project=baseball` 식별자는 임의 변경 금지.
- 프로젝트명 `BaseballLab`은 서비스 브랜드·내부 엔진·저장소 이름으로 유지한다. **숨기라는 건 사용자 메뉴의 중복 카드이지 핵심 코드를 삭제하라는 것이 아니다.**

### B. **AI 전략 연구 (Match)**

- 실제 AI 경쟁 학습, 학습 시점별 선택 변화, 성과 비교, 현대/역사적 인간 야구 비교 연구는 **Match가 전담**한다.
- Match를 선수 가상 대결과 **서로 다른 목적의 메뉴**로 보여준다.
- `세 아웃까지 득점 쌓기`, `한 점 먼저 내기`처럼 실험 원문을 메인 CTA로 쓰지 않는다. 사용자에게는 `AI 득점 전략`, `AI가 선택을 바꾼 과정`처럼 **무엇을 해보고 무엇을 볼 수 있는지**가 먼저 보이도록 한다.
- 기술적으로 실제 구현된 연구 목표·보상·경기 단위가 달라질 수 있으므로, 짧은 세부 안내와 연구 상세에서 구분한다. 이름만 바꿔 9이닝 전체 경기 학습처럼 속이지 않는다.
- 현재의 한 점 연구/반이닝 득점 연구, 연구 결과·체크포인트·상대 평가·리플레이를 보존한다.

### C. **정보 탭: 계산 원리**

- `/eramatch` 내부 **독립된 `계산 원리` 탭** 또는 명확한 상단 내비게이션으로 제공. 기존 오른쪽에 길게 쌓인 문장 대신 이곳이 **공식적인 학습·검증·비교 공간**이다.
- **별도의 `개발자 정보` 화면** 또는 고급 영역에 경로·해시·원본 코드·버전·seed·데이터 상태·검증 로그를 집중시킨다. 일반 사용자 화면에 노출하지 않는다.
- 홈에 공통으로 `선수 가상 대결`, `AI 전략 연구`를 중심으로 배치하고, `계산 원리`는 가상 대결의 상단 탭으로 접근한다. `자료 관리`는 설정·개발자 쪽으로 이동.

## 2. 화면을 실제 제품처럼 다시 설계 — 가장 중요한 구간

### 2.1 홈

**보여줄 것:** 심플한 브랜드 헤더, `선수 가상 대결`, `AI 전략 연구` 두 진입점. 이름과 누를 버튼만으로 목적이 구분되게.

**없앨 것:** 빈약한 가이드 문장, 내부 상태 요약, 기술적 한계의 단락, 중복 CTA, 화면의 3분의 1을 차지하는 설명 텍스트.

예시 (문장 그대로 강요 아님):
- 카드 1: `선수 가상 대결` / `MLB · KBO` / 버튼 `대결하기`
- 카드 2: `AI 전략 연구` / `학습과 전략 변화` / 버튼 `연구 보기`

### 2.2 선수 대결 — 입력

**첫 화면에 남길 것:** 리그(MBL 오타 금지, MLB), 시즌, 타자, 투수, 대결 횟수, `대결 시작` 버튼. 타자/투수는 검색 즉시 선택할 수 있는 목록.

- MLB/KBO 변경 시 **리그·선수·시즌 옵션이 자연스럽게 연동**되어야 한다. 지원 조건을 설명문으로 늘어놓는 대신 선택 가능 상태에 반영.
- 이미 있는 기본 데이터/자동 준비는 별도 강조 문구 없이 동작. 실패했을 때만 원인과 `다시 시도`가 보이게.
- 확률 모델·표본 보정 상수·seed·재현 옵션·원본 해시·반복 범위는 `고급 설정/개발자 정보`로 이동.
- 사용자가 횟수를 바꾸면 **화면 전체의 모든 횟수·타석·분모가 실제 선택값을 반영**. 예시의 `25타석` 하드코딩을 템플릿·설명·도움말·보고서까지 전수 검색.
- `대결 시작`과 `다시 대결`은 **새 난수**. `같은 결과 재현`은 과거 결과를 재현할 때만. 최신 커밋의 이 수정은 유지하고 양 리그에서 검사.

### 2.3 선수 대결 — 결과

**화면을 '결론 → 핵심 수치 → 분포 → 한 타석씩 보기 → 자세한 근거' 순서로 재배치.**

1. 헤더: `김도영(2024) vs 안우진(2022)` 및 실제 선택한 대결 횟수.
2. 한 문장 요약: `100타석 결과 · 안타 17 · 삼진 26 · 볼넷 6`처럼 **결과를 직접 말하기**. '모델의 예상 안타 수 23.5개'는 **예측과 실제 추첨의 차이**가 드러나는 시각 요소에서 설명.
3. 3~4개 핵심 카드: 안타/삼진/볼넷(·사구)/홈런 또는 목적에 더 적합한 실제 성과. `23.5%`의 의미를 `안타 예상 확률`로 명확히; 이번 안타 17/100과 구별.
4. 결과 분포: 안타 종류, 삼진, 볼넷, 아웃 등 **야구의 사건명**을 우선. `그 밖의 결과`는 정말 구분 불가능한 경우에만 근거 있는 표시. 각 막대의 단위와 분모 명확히.
5. 타석별 타임라인: 1회, 2회...가 아니라 `1번째 타석`, `2번째 타석` 등. 저장된 실제 추첨을 이동·재생하고 사건 이름이 분명해야 한다.
6. 추가 관심 있을 때만 `자세한 기록`, `계산 원리`, `개발자 정보`로 접근.

**절대 금지:** 그래프 아래마다 똑같은 주의 문구/연구 한계 서술 반복. 100타석과 9이닝의 차이는 결과 근처 **'타석별 가상 대결' 한 줄** 또는 설명 아이콘 한 번으로 충분. 실제 9이닝 결과로 오해하게 만드는 제목도 금지.

### 2.4 MLB/KBO 차이의 처리

- MLB는 공식 Retrosheet 타석 사건에서 확인 가능한 수준으로 세부 사건을 구분하고, 원천 관측과 모델 내 추정 분할을 다르게 표시.
- KBO 시즌 총합 자료는 타구별 상세를 임의로 만들어 `뜬공 아웃 18`처럼 표시하지 않는다. 확정 가능한 범주만 분리하고 나머지 묶음은 `기타 결과 (세부 기록 없음)`처럼 간결하게 **한 곳에서만** 고지.
- 서로 다른 데이터 공급원이 가진 `타석`, `타수`, `상대한 타자`, `안타`, `볼넷` 분모/통계를 섞지 않는다. 상세 수치가 결측이면 '미집계'로 표시하며 0으로 위조하지 않는다.
- 개선 가능하다면 실제 8개 기본 범주 확률 모델도 사건 분류부터 검토해 모델 자체를 개선한다. 다만 화면만 개선하는 과정에서 관측되지 않은 KBO 세부 결과를 꾸며내지는 않는다.

### 2.5 Match — 연구 화면

- `세 아웃까지 득점 쌓기` 같은 제목을 메인 메뉴에서 퇴출. 초보자에게 실제 무엇을 시험하는지 **시각적인 경기 상황과 그래프**로 보여줘라.
- `실험 설정하기`보다 **학습 시작/결과 비교/성장 과정 보기** 등 결과 중심 행동을 전면 배치.
- 학습 단계별 선택 변화, 같은 상대 대비 성과, 과거 AI와 비교를 시각화. **실제로 없는 구종·스윙·9이닝 전략은 보이는 것처럼 꾸미지 않는다.**
- 한 점 득점 연구와 반이닝 득점 연구를 구분하는 내부 정확성은 `연구 상세`에 유지.
- 일반 사용자가 무슨 연구인지 이해하지 못하는 상황에서는 '기술적 설명을 추가'하지 말고 **설명 없이도 의미가 보이게 디자인부터 바꿔라.**

## 3. 별도 `계산 원리` 탭 — 사용자의 기존 보고서를 토대로 구축

**단순한 문서 링크나 FAQ, Log5 설명 두 문단으로 끝내지 마라.** 실제 입력한 선수와 결과를 바꾸면 예시 숫자도 바뀌는 **인터랙티브한 계산 해설/교육 페이지**로 구현.

### 3.1 과제 원본의 계산 파이프라인 재현

사용자 제공 `컴퓨터공학기초 기말과제보고서`, 원본 `code.zip`, 저장소의 `matchup.models.legacy`를 참고하고 실제 계산식 및 용어를 교차 검증.

1. **시즌 선수 기록 조회**: 타자/투수의 실제 PA, AB, H, K, BB, HR, 2B, 3B 등. 결측·출처를 분모와 함께 명시.
2. **리그/시대 보정**: 타고투저·투고타저 환경 차이를 왜 보정하는지, 원본 비율식의 입력과 한계.
3. **표본 안정화(평균 회귀)**: 짧게 활약한 선수가 왜 과대평가될 수 있는지, 원본 고정 상수와 새로운 보정 강도의 차이.
4. **BABIP/DIPS**: 홈런 외 인플레이 타구의 안타 확률과 수비·환경 영향을 분리해서 설명. 원본의 '투수 BABIP는 리그 평균으로 고정'은 **가정**이지 확정된 자연법칙이 아님을 구별.
5. **Log5**: 타자·투수·리그 기록을 어떻게 조합하는지. 적용 대상 사건·이항식/다항 확장 차이.
6. **몬테카를로**: 계산된 확률에서 개별 타석을 추첨하고 여러 번 반복했을 때 왜 결과가 달라지는지.
7. **결과 해석**: 예상 확률, 이번 추첨 수, 반복 시 변동 범위, 무엇을 말할 수 있고 없는지.

### 3.2 원본 과제 vs 개선 모델 — 별도 핵심 콘텐츠

필수 비교 표/카드: `항목 / 과제 원본 / 현재 방식 / 왜 바꿨나 / 실제 검증 결과 또는 미검증`.

꼭 포함할 실제 논점:

- 과제의 **이항 Log5 사건별 독립 결합·순서 분기**와 현재 **전체 사건 확률을 100%로 정규화한 다항 Log5**의 차이.
- **사구(HBP) 분리**와 삼진·안타·볼넷 등 겹치지 않는 사건 정의.
- 과제 **첫 팀 행 선택** vs 선수-시즌 이적 팀 기록의 합계 처리; 합계와 팀 행 중복 방지.
- **시즌별 기준 기록·시대 보정**의 차이와 교차 시대 공정성의 미검증 영역.
- **BABIP 강제 리그 평균 가정** vs 실제 허용 안타 사건 반영 및 한계.
- **고정 회귀 상수** vs MLB 기간 분리 평가를 통해 선택한 보정 강도. KBO에서 별도 검증 안 됐다면 단정 금지.
- **모델 예측력 검사**: MLB 2024/2023 등 실제 실행·저장 근거에 있는 로그손실·Brier·교정 지표. 모델 개선이 어떤 데이터에서 어느 정도 관측됐는지를 숫자로 표시. KBO나 과거 시대까지 검증됐다고 뻥치지 마라.

각 변경점은 `이전 → 현재`의 **작동 방식, 왜 변경했는지, 실제 대결에서 수치가 어떻게 달라지는지**까지 연결해야 한다. 말로만 '과학적으로 개선'이라고 쓰는 것 금지.

### 3.3 화면 설계의 기준

- 상단: `계산 흐름` 한 장짜리 시각 다이어그램.
- 중간: 단계별 카드 + 선택한 선수의 실제 숫자 예시(동적) + 간결한 그래프.
- 우측 또는 하단: `과제 원본 ↔ 현재 방식` 비교. 핵심 차이 하이라이트, 단위/분모 표시.
- 하단: `데이터 출처 · 검증 결과 · 상세 수식`은 관심 있는 사용자만 볼 수 있는 탭/접힘 영역.
- 원본 과제의 내용과 후속 연구/추가 검증 결과를 **명확히 구별**한다.
- 설명 문장은 야구팬 눈높이, 기술 명칭(예: Log5, BABIP)은 정확히 유지하되 **한 줄 정의 + 그림/수치 예시**가 우선.

## 4. 개발자 정보와 사용자 정보 완전 분리

**일반 화면에 두지 말 것:** 개발 내부 명칭(`R1`, `seed`, `policy`, `donor`, `transition`, `baseline`), 데이터 해시/절대 경로/코드 버전/보정 강도 상세, 로컬 저장 경고, 연구 범위 변명 단락, 자동 준비 설명, 운영 로그.

**개발자 정보에는 유지:** 실행 ID, 재현 번호, 엔진/모델 버전, 자료 출처·라이선스·해시, 실제 수집·검증 범위, 검증하지 않은 부분, 로깅/보안, 상세 수식, 실험 규격, 기존 연구의 한계 및 입력/행동/보상 정의. 정보 제거가 아니라 **독자에 따른 위치 이동**이다.

단, **사용자의 핵심 판단을 바꾸는 한계**를 속여 숨기지 않는다. 예컨대 '실제 9이닝 경기 결과가 아닌 타석별 대결'이라는 정보는 짧고 명료한 안내로 정확한 위치에 한 번은 제공.

## 5. 문구 작성 규칙 — 길게 풀어쓰지 마라

- 기본 화면 설명은 **필요한 곳에만 한 줄**. 라벨과 그래프가 전달할 수 있는 내용을 문장으로 중복하지 않는다.
- `선수만 고르세요. 기록은 자동으로 준비합니다.` → **삭제**(작동하면 설명할 이유 없음).
- `지원하는 기록은 자동으로 준비하고 이 컴퓨터에 보관합니다...` → **삭제**(실패/개인정보 알림이 필요한 시점만).
- `이것은 전체 9이닝이 아니며...`가 화면 여러 군데 반복 → **핵심 맥락 한 번만**.
- `세 아웃까지 득점 쌓기` → 사용자 화면에서는 **`이닝 득점 전략`** 등으로 변경, 실제 정의는 상세에서 표현.
- `기타 타석`, `그 밖의 결과` → **가능한 사건 종류를 먼저 보여주고**, 분리가 불가능할 때만 `기타 결과 (세부 기록 없음)`으로 처리.
- `100번의 가상 대결에서 ... 모델의 예상 안타 수 ...` → 요약은 짧게, **예상 vs 실제 추첨**은 카드나 그래프에서 비교.
- `과제 재현·개선 후보` → 사용자에게는 **`기존 계산 / 개선된 계산`**, 과학적 검증 상태는 계산 원리·개발자 상세에 분리.
- `계산식·중간값`은 일반 대결 화면에 항상 펼치지 않는다. `계산 원리`에서 자세히 볼 수 있다.
- 사용자 문장은 딱딱한 개발 보고서체·기계적 존댓말 반복 금지. 장황한 '안내드립니다/확인해주세요/참고 바랍니다'와 과도한 `~입니다`를 걷어내라.
- `KBO 데이터 1984~2025`로 오기하지 말고 **실제 소스가 지원하는 시즌을 데이터로 표시**. 기존 과제 집계는 1982~2025로 검토되어 있다.

## 6. 협업 구조는 정확히 두 역할 — 토큰 경량화

### 역할 1: 메인 **Codex = 총괄 + 개발 + QA + 최종 통합**

- 요구 해석, 기존 코드 파악, API/라우팅, MLB/KBO 선택 통합, 기존 결과 호환, 계산 원리의 실제 모델/근거 확인, 보안·테스트·커밋.
- 다수 하위 에이전트 생성 금지. 단순 조사/코드 수정도 메인이 직접.
- 디자이너가 제안한 디자인을 코드 구조·실제 데이터에 연결하고 최종 수락 테스트 실행.

### 역할 2: **Designer Agent = UI/UX 전문 하위 에이전트 1명**

- 현재 홈/가상 대결/Match/계산 원리 화면의 **스크린샷·사용자 여정·텍스트 밀도·계층 구조**를 검토.
- **시각적 화면 설계 및 실제 디자인 구현**에 집중: 레이아웃, 정보 우선순위, 타이포그래피, 여백, 색상 대비, 반응형, 그래프, 명료한 문구, 접근성.
- 코드 파일 수정이 필요하면 메인과 **작업 파일 소유권을 먼저 분리**해 충돌 방지.
- **보고서는 짧게**: 바뀐 화면 3~4장, 주요 차이 5개 이내, 남은 위험. 전체 저장소를 다시 학습하거나 100페이지 기획서를 만들지 말 것.

**두 역할 외 별도 QA·통계·데이터 하위 에이전트 호출 금지.** 필요한 통계·데이터·보안 검토는 메인이 수행. designer 1명도 필요한 작업 구간에만 실행하고, 여러 번 '디자인 검토'를 중복 요청하지 않는다. `AGENTS.md`를 이 규칙으로 고쳐 향후 유지.

## 7. 실제 구현 순서 — '기획서만 작성' 금지

1. 현재 HEAD·작업트리·기존 데이터/결과 상태를 점검하고 **기존 파일 해시/기능 기준선** 저장. 과거 계획서 전체 반복 독해 금지.
2. 디자이너가 **사용자 흐름 + 홈/선수 대결/계산 원리/Match**의 디자인을 구체화. 막연한 감상문 불가.
3. 메인 Codex가 `/baseball`과 `/eramatch`의 진입점·리그 선택·상태 전환을 통합. **기존 서비스 API/저장 결과/모델 재사용**, 삭제 대신 호환 경로.
4. 디자이너 중심으로 HTML/CSS/JS 구조 개편. 안내문을 줄이고 시각적 결과가 전면에 나오게 수정.
5. `계산 원리` 페이지 구축: 원본 보고서 7단계+원본/개선 비교+실제 입력 연동. 상세 근거는 한 곳에.
6. Match 홈/실행/결과의 핵심 용어·카드·차트 재배치. 기존 연구 작동과 저장 기록 보존.
7. 자동화 브라우저에서 기본 흐름을 완료. **실제 화면 이미지 비교**로 디자이너와 메인이 최종 점검.
8. 작동 결과가 실제로 더 이해되는지 정성적 사용성 체크를 마친 후, 정해진 회귀·무결성·보안 테스트 실행하고 커밋.

## 8. 완료 판정: 반드시 통과해야 하는 사용자 시나리오

### 선수 가상 대결

- [ ] 첫 방문 홈에서 **선수 가상 대결 / AI 전략 연구**만 주 메뉴로 보임. 불필요한 별도 BaseballLab 선수 대결 카드 없음.
- [ ] 한 화면에서 MLB → KBO를 전환하며 실제 선수·시즌 목록이 올바르게 바뀜. 타자/투수 선택이 잘못 섞이지 않음.
- [ ] MLB 2023·2024 및 KBO 1982·2024 등 실제 자료 기반 조합을 실행. 동일 리그 내 시대 교차 선택도 지원 가능한 범위를 정확히 안내.
- [ ] 25·100·250타석으로 바꿀 때 제목, 차트, 결과, 해설, 이동·재생, 저장 보고서까지 전부 해당 수치로 일치.
- [ ] `대결 시작/다시 대결`은 새 난수, `같은 결과 재현`은 저장 난수. 중복 실행·빠른 시즌 변경·이전 결과 재열기도 검사.
- [ ] 5초 정도 화면을 훑어보면 **누가 누구와 대결했고, 몇 타석이며, 안타/삼진 등 결과가 몇 번인지** 드러남.
- [ ] 일반 사용자에게 seed, SHA, 연구 ID, 미검증 경고 단락 등이 난립하지 않음. 필요한 정확성 고지는 한 번 짧게.
- [ ] '기타 결과'의 뜻/분류 기준이 데이터와 일치하고, 없는 KBO 세부 타구를 지어내지 않음.

### 계산 원리

- [ ] 사용자가 직접 누를 수 있는 **독립 탭**이 있다. FAQ 한 페이지가 아니라 도식·수치·비교를 제공.
- [ ] 원본 보고서의 시대 보정·표본 회귀·BABIP/DIPS·Log5·몬테카를로를 설명하고 실제 구현과 연결.
- [ ] **'기존 계산 vs 개선된 계산'**에 무엇이 왜 바뀌었는지, 실제 계산 차이와 검증 근거를 보여줌.
- [ ] MLB와 KBO의 검증 수준 차이를 정확히 보여주고 거짓 정확도/가상 선수 기록을 만들지 않음.

### Match

- [ ] 내부 연구 코드명/`세 아웃` 같은 표현을 주 화면 핵심 제목에서 제거. **실제 경기를 나타내는 시각 언어**로 설명.
- [ ] 첫 화면에서 `학습 시작`, `전략 변화`, `결과 비교` 중 실제 가능한 행동을 선택할 수 있음.
- [ ] 기존 한 점 연구·이닝 득점 연구와 저장 결과·리플레이가 손상되지 않음.

### 디자인/기술 검증

- [ ] PC 1366px 및 모바일 390px에서 **가로 넘침, 잘림, 불필요한 여백, 글자 과밀, 지나친 긴 설명** 없음. 실제 캡처로 확인.
- [ ] 제목·단위·축·색상·버튼 계층이 분명하고 키보드/스크린리더 레이블·명도 대비를 점검.
- [ ] 실제 레코드와 기존 가중치/원본/연구 결과 무변조. 과제 원본 재현 210조건·MLB 기존 검증 수치 회귀.
- [ ] 필수 자동 테스트 및 실제 웹 브라우저 동선 통과. 실패 시 재수정 후 재검증.
- [ ] Git 기록·원본 보존, 변경 SHA 및 되돌리기 방법 기록. **새 저장소·V2 복제품·새 확률 엔진 무단 생성 금지.**

## 10. Codex에 마지막으로 강조한다

**이 작업은 개발자가 보고서를 읽는 화면을 만드는 일이 아니다. 야구를 좋아하는 사람이 결과를 보고 싶어서 누르는 서비스 화면을 만드는 일이다.**

문구를 줄여 달라고 했으면 문장을 세 줄에서 한 줄로 고치는 수준에서 멈추지 말고 **없애야 할 문구를 삭제하고, 의미는 시각적 구성으로 전달**하라. 계산 원리를 보여 달라고 했으면 기존 보고서를 링크하는 대신 **실제 모델과 연결된 별도 탭**을 만들어라. 세 프로젝트가 겹친다면 **기능을 없애는 것이 아니라 사용자 입구를 통합**하라.

**메인 Codex(개발·총괄) + 디자이너 에이전트 한 명. 나머지 에이전트는 쓰지 않는다.** 구현과 실제 브라우저 확인까지 수행하고 완료를 선언하라.
