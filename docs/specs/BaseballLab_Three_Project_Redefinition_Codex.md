## 0. 제일 먼저 이해할 것 — 이제 3개는 이렇게 정의한다

| 이름 | 사용자가 보는 프로젝트의 정체성 | 핵심 질문 / 주요 기능 |
|---|---|---|
| **BaseballLab** | **야구 통계·세이버메트릭스 기반 타자-투수 대결 시뮬레이터** | 실제 야구 기록으로 투타 대결 결과의 확률을 계산하고 몬테카를로로 여러 번 가상 대결하며, 그 계산에 쓴 Log5·BABIP·시대/표본 보정 등 이론과 근거를 이해한다. 이것이 사용자 관점의 **기본 프로젝트**다. |
| **Match** | **AI의 자율 경쟁학습 및 전략 진화 연구** | AI 타자/투수가 야구 규칙·현실적 제약 아래 승리를 위해 경쟁하면 무엇을 스스로 배우고, 어떻게 적응하며, 어떤 전술·플레이스타일에 도달하는가? 학습 구간별 우열·전략 변화를 기록하고, **인간 야구의 현대 수준 및 역사적 발전과 비교하여 그 의미와 한계를 탐색**한다. |
| **EraMatch** | **역대 KBO 선수 가상 맞대결** | 서로 다른 시즌의 KBO 타자·투수를 선택하여 당시의 실제 기록을 조회하고, 시대 차이를 보정한 확률로 가상 대결한다. **사용자의 기존 학교 과제의 웹 제품화가 1차 목표**다. 새로운 AI 진화 연구는 이 프로젝트의 책임이 아니다. |

**핵심 정정:** 부모 BaseballLab을 ‘공통 UI/데이터 허브만 있는 빈 플랫폼’으로 만들어서는 안 된다. **BaseballLab 자체가 사용자가 실행할 수 있는 타자 대 투수 통계 시뮬레이션 프로그램**이어야 한다. 그 아래의 공통 데이터·계산 엔진·규칙·UI를 Match와 EraMatch가 재사용한다.

**또 다른 핵심 정정:** 인간 야구의 발전 및 AI의 결과와 현대 야구를 비교하는 주제는 **Match의 연구 목표**다. **EraMatch의 목표로 넘기지 마라.** EraMatch가 우연히 시대별 성적을 참고하는 것과, AI 전략의 인간 비교 연구를 소유하는 것은 다르다.

이름은 메뉴에서도 `BaseballLab` / `Match` / `EraMatch`로 통일한다. 레거시 `E01`, `R0`, `R1`, `Match-A/B`는 내부 실험 식별자이자 하위 연구로 유지할 수 있지만 홈페이지의 대표 프로젝트 이름으로 쓰지 않는다.

## 1. 사용자가 실제로 만들고 싶은 제품 경험

첫 화면은 다음 세 프로젝트를 **명확하게 클릭·선택**할 수 있어야 한다.

```text
BASEBALLLAB  ·  야구 시뮬레이션 연구실

[ BaseballLab ]      [ Match ]         [ EraMatch ]
[투타 대결 시뮬]      [AI 전략 연구]     [역대 선수 대결]

선택한 프로젝트 화면
┌────────────────────────────────┬───────────────────────┐
│  주요 작업 영역                 │  지금 사용하는 계산/이론 │
│  선수 선택 / 조건 / 시뮬레이션   │  · Log5란 무엇인가?       │
│  또는 AI 학습 / 결과 / 비교      │  · 왜 이 수치가 나왔나?    │
│  실제 야구장 · 표 · 차트 · 리플레이│  · 출처·표본·가정·한계     │
└────────────────────────────────┴───────────────────────┘
```

- 프로젝트 사이를 상단 메뉴·홈 카드로 이동한다. 프로젝트마다 진입점, 목표, 현재 지원 범위를 명확히 구분한다.
- 기본 레이아웃은 **왼쪽 시뮬레이션/실험 + 오른쪽 '이 결과를 어떻게 계산했나요?' 설명 패널**. 모바일에서는 패널을 아래로 배치하거나 탭·접이식 설명으로 제공한다.
- 오른쪽 설명은 정적인 ‘용어집’ 링크가 아니라 **현재 선택한 선수, 시즌, 모델, 계산 단계에 따라 바뀌는 맥락형 패널**이다. 초보자 설명과 ‘공식·세부 근거 보기’ 두 단계로 나눈다.
- 실제 기록, 계산된 기대값, 무작위로 생성한 가상 결과를 **눈에 띄게 구별**한다. 근거 없는 투구 궤적·구속·수비 플레이 애니메이션을 만들지 않는다.
- UI의 첫 화면에서 `seed`, `policy`, `donor`, `checkpoint`, `transition`, `R1`, `Monte Carlo` 같은 내부 용어를 남발하지 않는다. 다만 '몬테카를로'와 'Log5'는 이해할 수 있도록 설명하는 **사용자 선택 가능한 전문 항목**으로 둔다.
- 기존 홈페이지·2D 야구장·연구 리포트·저장자료 화면은 최대한 재사용한다. 더 많이 구현한 척하지 말고 실제 지원 범위를 보여준다.

## 2. BaseballLab — 통계 기반 투타 대결 시뮬레이터 자체

### 2.1 목표와 기능

일반 사용자 흐름:

1. **타자·투수 또는 두 프로필 선택**: 리그/시즌/선수 또는 조건에 맞는 검증된 통계 프로필. 실제 데이터가 없거나 다른 정밀도로만 있으면 지원 범위를 표시.
2. **분석 조건 선택**: 데이터 기간, 적용할 추정 모델, 대결 횟수(예: 25타석/100타석/1,000타석)와 시뮬레이션 시드(고급 설정), 같은 시즌/중립 리그 등 지원되는 조건만 제공.
3. **예상 대결 결과 확인**: 삼진·볼넷·안타·장타 등 사건의 **확률과 분모**, 여러 가상 대결의 결과 분포, 불확실성, 선수·시즌 원천 데이터.
4. **경기처럼 보기**: 각 가상 타석의 결과·누적 기록·간단한 사건 타임라인/2D 야구장. 타석 반복을 실제 9이닝 경기처럼 속여 보여주지 않는다.
5. **옆 설명 보기**: 원본 성적 → 시즌/리그 보정 → 표본 안정화 → 투타 확률 결합 → 무작위 추출 → 결과 집계의 과정을 클릭하여 이해한다.

**원본 과제의 핵심 흐름**은 `CSV 읽기 → 선수 검색 → 시대 보정 → 표본 회귀 → Log5 → 몬테카를로 25타석`이다. 보고서 PDF와 `code.zip`의 `code/KBOsimulator.py`를 출발점으로 삼되, 기존 구현이 과학적으로 검증되었다고 간주해서는 안 된다. 아래의 두 모델을 분리하라.

### 2.2 계산 모드: '과제 재현'과 '검증된 개선'의 분리

**A. 원본 과제 재현 모드**
- 기존의 시대 보정, 표본 안정화, Log5, 몬테카를로 결과를 **기존 의도를 최대한 보존해 재현**. 기존 코드가 가진 가정·제한·결함을 명확히 표시한다.
- 사용자에게 이 모드를 **'과제 방식 재현(연구 검증 전)'**으로 표시하고 기본 분석의 진리로 내세우지 않는다.
- 계산 결과가 원본과 일치하지 않으면 이유를 문서화한다. 무작위 시드가 없는 기존 결과는 완전한 수치 재현이 불가능할 수 있다.

**B. 검증·개선 모델(목표 기본 모드)**
- 실제 자료의 필드 정의·분모·결측·표본 수·리그/시즌 기준을 검증한 모델을 설계하고, 보류 경기/선수/시즌에 대한 예측 오차 검증 뒤 기본값으로 채택한다. **검증 전에는 기본 모델이 검증되었다고 표시하지 않는다.**
- 후보: 다항 결과 사건을 보존하는 **정규화된 일반화 Log5**, 계층적/베이지안 부분 풀링, 다항/조건부 확률 모형, 경험적 확률을 포함한 비교 기준선. 특정 기법을 이름만으로 우수하다고 결정하지 말고 동일 데이터·분리 조건에서 성능과 보정(calibration)을 비교하라.
- 각 사건의 확률은 서로 배타적이며 총합 1이 되도록 정의한다. 누락 사건을 무조건 0으로 보정하거나 확률 합 초과분을 몰래 버리지 않는다.
- 모델 정밀도가 허용하는 것만 구현한다. 단순 시즌 합계 기록을 투구별 공 궤적/3D 경기로 포장하지 않는다.

### 2.3 과제 코드에서 반드시 검토할 것

- **Log5**: 원래 이항 사건용으로 정식화된 모델을 K/BB/HR/인플레이 히트 등에 개별 적용한다고 자동으로 일관된 다항 분포가 되지는 않는다. 사건 분할, 중복·조건부 구조, 전체 확률 합을 검증한다. SABR의 다중 결과 확장 연구와 Log5의 편향 연구를 비교한다.
- **DIPS/FIP**: 타구의 결과를 FIP에서 빼는 *지표 설계*가 투수의 인플레이 타구 영향이 언제나 정확히 0임을 증명하지 않는다. 기존 코드의 **투수 BABIP 무조건 리그 평균 고정**은 선택 가능한 가정/대조 실험으로 격하하고 검증한다.
- **BABIP**: 기본 사건 공식과 분모를 원천 스키마에 맞춰 계산한다. `SF` 결측을 모두 0으로 취급하지 않는다. `HP`/`HBP`가 실제 있다면 누락했다고 단정하지 않는다.
- **PA/AB/TBF**: `AB = PA - BB`로 일반화하지 않는다. 희생타, 사구, 타격방해, 일부 예외를 고려해 원천 분모를 구분한다. 투수 이닝은 소수 계산이 아닌 **아웃 카운트** 기준으로 처리한다.
- **표본 부족과 회귀**: 특정 안정화 상수(150, 200, 400 등)는 보편적 정답이 아니다. 출처·추정법·실제 표본 검증을 남기고, 추정 불확실성을 표시한다. '운을 완전히 제거하여 순수 실력 확정' 금지.
- **시대·리그 보정**: 시즌 평균 대비 상대 비교는 방법론이지만 시대별 규칙·선수 구성·측정 단위·파크팩터 차이 전체를 없애지 않는다. 같은 시즌 시뮬레이션과 다른 시즌의 가상 대결을 구분한다.
- **동명이인·이적 기록**: 선수 ID·팀별 기록/시즌 합산 중복을 검증한다. 시즌별로 여러 팀을 거친 선수의 합산을 2중 집계하지 않는다.
- **시뮬레이션 명칭**: 25타석은 **가상 25타석 대결**이지 ‘실제 경기를 25타석 동안 재현한 최종 스코어’가 아니다. 9이닝 경기/주자 진루/점수는 별도 규칙·검증 모델이 필요하다.

이 문제를 해결한다는 이유로 사용자 과제의 원본을 덮어쓰지 마라. 오히려 **원본 방식 대비 개선 방식의 비교 화면**을 만들면 학습·검증 과정 자체가 유용하다.

## 3. Match — AI가 야구 전략의 한계를 탐색하는 별도 연구

**Match는 단순히 BaseballLab의 시뮬레이션 횟수를 늘린 메뉴가 아니다.** 야구의 실제 규칙·가능한 선택·검증된 결과 분포를 학습 환경으로 사용하면서 **타자/투수의 정책이 경쟁에 따라 바뀌는 독립 연구 프로젝트**다.

### 3.1 변하지 않는 궁극 질문

> AI 타자와 AI 투수가 야구의 규칙·현실적인 선수 능력·기술·플레이스타일과 충분한 통계적 정보를 반영한 환경에서, **오직 승리하기 위해 스스로 경쟁 학습**한다면 어디까지 발전하는가?
>
> 학습 초반/중간/후반 각 AI는 어떤 선택으로 달라졌고 어떤 상대·상황에서 유리해졌는가? 그 결과는 현대 인간 야구와 역사상 인간 전략 변화에 대입하면 어떤 의미가 있는가? AI가 특정 조건에서 더 효율적이라면 인간은 그 전략을 참고해야 할 근거가 있는가? 반대 결과라면 왜 그런가?

**이 질문과 인간 야구 비교는 전부 Match의 소관이다. EraMatch로 이전하지 않는다.** AI가 인간보다 강하다는 결론을 미리 정해 놓지 않는다. 성능 정체·사이클·인간과의 유사성도 중요한 결과다.

### 3.2 연구 구현의 단계 구분

- **기존 R1의 위치:** 실제 Retrosheet 2024 플레이 자료로 **3아웃 전 1점 득점/차단**, 공격의 일반타석/번트 관측과 수비의 정상승부/고의볼넷 선택을 사용한 제한적 학습. 2023년 외부 시즌 평가는 기존 근거로 보존. 이걸 ‘모든 야구 기술 학습’으로 부르지 않는다.
- **Match 단계 1: 한 타석·투구 전략**: 자료 확보·합법적 사용·피처/행동/결과 검증이 되면 카운트, 스윙/테이크, 구종, 코스, 구속(실제 제공 범위), 선구안/컨택/장타 등을 점진적으로 학습. 실제 인간 기록에 선택되지 않은 행동의 인과 효과는 추가 가정·실험·검증 없이 사실로 확정하지 않는다.
- **Match 단계 2: 득점·경기 승리**: 주자·아웃·점수차·이닝·타순 등 실제 경기 맥락을 포함하여 이닝/9이닝 게임으로 확장. '출루 보상', '1점 득점 보상', '경기 승리 보상'을 구분한다.
- **Match 단계 3: 선수 유형/능력 조합**: 교타/장타, 제구/구위, 구종 다양성과 숙련도의 트레이드오프 등을 실제 자료가 뒷받침하는 제약 하에 별도 진화 축으로 연구. 플레이 중 전술의 학습과 선수 능력 자체의 변화 가정을 혼동하지 않는다.
- **Match 단계 4: 인간 야구와 비교**: 현대 완료 3시즌 정도를 우선 비교 기준선으로 검토하고, 별도 역사적 장기 기록과 시대별 규칙 차이를 고려해 AI의 학습 궤적과 인간 전략의 장기 변화를 비교. **AI가 가상 환경에서 이긴 것 = 현실 선수가 따라야 할 정답**이라는 결론 금지.

### 3.3 Match 결과 화면의 핵심

- 동일한 조건에서 **AI 타자와 AI 투수가 학습 단계별로 어떤 행동 확률을 바꾸었는지** 보여준다.
- 학습 전/중간/후의 타자 vs 투수, 고정 상대, 과거 버전 및 다른 시작점(seed) 재대결을 비교해 누가 **그 조건에서** 유리한지 검증한다. 현재 1점 득점 게임처럼 역할이 비대칭이면 50%를 동등 실력 기준으로 삼지 않는다.
- 서로의 전략에 대한 **적응 → 재적응**을 그래프와 실제 지원되는 장면 리플레이로 보여준다.
- 사용자에게 ‘이렇게 변했다 / 그래서 성과가 달라졌다 / 인간과 비교할 때 무엇을 말할 수 없다’를 분리해 설명한다.
- 현대·역사적 인간 야구와의 비교는 **Match의 연구 탭**이다. 현대 3년과 역사 전체는 서로 다른 비교 목적이므로 데이터를 무조건 섞지 않는다.

**중요:** BaseballLab의 통계 기반 승부 예측 모형을 **Match의 정답 전략으로 직접 주입하지 않는다.** 공통 환경/결과 모델의 검증 근거는 재사용하지만, Match의 전략 선택은 AI가 경기 피드백으로 학습해야 한다. 통계 지표가 많다고 AI가 그 기술을 행동할 수 있는 것은 아니다. 사용할 수 있는 행동·관측·현실적인 결과가 구현돼야 한다.

## 4. EraMatch — KBO 역대 선수 가상 맞대결 웹 제품

**1차 범위는 기존 학교 과제의 사용자 친화적 웹 버전이다.** AI 학습, AI의 현대 야구 비교, MLB-KBO 정책 대결 같은 연구를 여기에 추가하지 않는다.

### 4.1 사용자 경험

- KBO 선수 **이름 + 시즌** 검색. 타자와 투수를 선택하고 각각의 원본 시즌 스탯과 출처/표본 수 표시.
- 서로 다른 두 시즌(예: 1980년대 타자 vs 2020년대 투수)의 시대 차이를 어떤 방식으로 보정했는지 설명.
- 기본 **25타석 가상 대결** 버튼. 반복 수를 바꾸면 평균·분포·시드·불확실성 확인.
- 결과: 삼진/볼넷/홈런/인플레이 안타/아웃 등 실제 모델이 지원하는 범위의 확률, 가상 횟수, 기대값. 9이닝 경기 점수처럼 꾸미지 않는다.
- 오른쪽 패널에 **시대 보정 · 표본 회귀 · Log5 · 몬테카를로**를 차례대로 설명하고, 원본 재현 모드 vs 개선 모델의 차이가 무엇인지 보여준다.
- 데이터가 없는 선수·연도, 중복/동명이인, 결측 분모, 근거 없는 시즌은 이유와 함께 선택 제한.

### 4.2 과제의 정확한 활용 방법

사용자가 제공한 자료:
- `컴퓨터공학기초_기말과제보고서_12263188_김찬웅(2).pdf` (2026-06-16, 10페이지)
- `code.zip` 내부 `code/KBOsimulator.py`, `code/kbo_batting_stats_by_season_1982-2025.csv`, `code/kbo_pitching_stats_by_season_1982-2025.csv`.

**원본을 보존하고** 현재 저장소에 있는 파일이 맞는지 확인. 파일이 없다면 **사용자가 제공한 첨부를 명확하게 연결**하도록 안내하고 없는 자료를 임의 생성하지 않는다. 과제의 의도와 각 함수의 설명을 참고하되, 공식 원천·이용 조건·수식 정의가 검증되지 않은 부분은 `LEGACY_UNVERIFIED`로 분리한다. Kaggle이라고만 적혀 있어 실제 URL/버전/라이선스를 독립적으로 확인하지 못했다면 연구 검증 완료로 표시하지 마라.

EraMatch는 BaseballLab의 공통 **타자-투수 확률 엔진/데이터 카탈로그/UI 컴포넌트**를 재사용하되, '다른 시즌끼리의 비교 조건·시대 보정·선수 탐색'이 EraMatch 고유의 차별점이다. 같은 Log5 코드를 두 군데 중복 구현하지 않는다.

## 5. 공통 실제 데이터 + 검증된 야구 지식 저장소

BaseballLab은 **이 세 프로젝트의 공통 데이터와 계산 근거를 소유/관리**한다. Match와 EraMatch가 임의의 CSV를 각각 가져가 따로 관리하지 않도록 한다. 그렇다고 모든 데이터를 하나의 거대 CSV로 합치는 것도 아니다.

| 자료 레벨 | 역할 | 현재/예시 |
|---|---|---|
| 실제 원본 | 변경 불가능한 출처 데이터 | 보유 KBO 1982~2025 선수 시즌 CSV(초기 출처 검증 필요), Retrosheet 2023/2024 MLB 플레이 기록 |
| 정규화 데이터 | 선수/팀/시즌/경기 ID, 단위, 분모, 결측, 중복, 스키마 정리 | `player_season`, `game`, `play`, 향후 `pitch` |
| 검증된 이론·공식 | 야구 규칙, Log5, BABIP, DIPS/FIP, K/9·BB/9, OPS·wOBA 등 | **각 지표의 분자·분모·단위·적용 범위·출처·논쟁점** 기록 |
| 모델과 가정 | 시대 보정, 표본 회귀, 다항 결합, 시뮬레이션 이벤트 모형 | 모델별 버전·보정·검증 성능·금지 해석 |
| 실험 결과 | 시뮬레이션/학습 결과·체크포인트·인간 비교 | 데이터/코드/시드/모델 버전으로 재현 가능 |

**원본 경로와 메타데이터는 구분:** 원본 CSV/ZIP/개인 실행 가중치·로그는 로컬 비공개 보관. Git에는 출처 목록·스키마·검증 코드·허가된 집계 결과만. 원본 파일 접근은 데이터 카탈로그를 통해 하고 각 실행이 정확한 데이터셋 버전을 기록한다.

데이터 범위는 프로젝트별로 다르게 쓰는 것이 맞다.
- **BaseballLab:** 실제 지원되는 시즌·리그/선수 프로필에 따라 투타 확률 계산.
- **EraMatch:** 가능하면 **1982~2025 KBO 장기 선수 기록**을 정제·검증하고 시대별 비교. 선수 기록만으로 세부 투구 궤적을 만들어내지 않는다.
- **Match:** 첫 실험은 실제 데이터가 검증된 특정 시즌에서 수행하되, **현대 야구의 최근 완료 3시즌 평가**와 **장기간 역사 변화 비교**를 차후 분리. 더 많은 연도 데이터를 무조건 섞는다고 편향이 사라지는 건 아니다.

정규화와 자료 등록은 단계적으로 구현한다. 기존 `data/local/retrosheet`, `data/local/statcast` 및 저장 결과를 큰 이사 작업으로 깨뜨리지 마라. Windows ACL/동기화/암호화는 현재 검증된 범위를 넘어서 지원했다고 표시하지 않는다.

## 6. 오른쪽 '이 시뮬레이션을 이해하기' 설명 패널 요구사항

각 프로젝트 화면에 고정 또는 선택적으로 펼치는 **설명 패널**을 둔다. 설명은 실제 모델 메타데이터와 연결해야 한다.

**BaseballLab 예시**
- *이번 결과는 무엇인가?* “선택한 실제 기록에서 타자/투수의 사건 확률을 추정한 뒤, 같은 조건의 가상 타석을 반복해 나온 결과입니다.”
- *Log5란?* “리그 평균을 기준으로 타자와 투수의 상대적인 기록을 결합하는 방법입니다.” / 상세: 사건 수식·입력율·계산 결과·일반화 가정.
- *표본 보정이란?* “기록이 적은 선수의 극단적인 수치를 완화하기 위한 추정입니다.” / 상세: 사전 분포, 상수/학습 방식, 불확실성.
- *몬테카를로란?* “계산한 사건 확률을 바탕으로 같은 대결을 무작위로 여러 번 진행해 결과의 분포를 보는 방법입니다.” / 상세: 난수번호, 횟수, 오차 추정.
- *주의할 점*: “이는 실제 경기 결과의 기록이 아니라 모델이 예측해 생성한 결과이며, 투구별 위치나 9이닝 점수를 재현하는 기능은 아닙니다.”

**Match 예시**
- “AI는 지금 어떤 야구 상황을 관찰할 수 있나요?”
- “현재 AI가 선택할 수 있는 행동과 최종 보상은 무엇인가요?”
- “이 실험에서 1,000번째 학습 이후 무엇이 바뀌었나요?”
- “실제 인간 야구와 비교할 때 어떤 자료/가정이 다른가요?”
- **AI의 선택 변화 ≠ 성과 개선 ≠ 현실 최적 전략**을 명확히 구분.

**EraMatch 예시**
- “두 선수의 시즌·리그 평균 차이를 왜 보정하나요?”
- “이 시대 보정이 제거하지 못하는 차이는 무엇인가요?”
- “원본 과제 방식과 검증·개선 모델이 다른 이유는 무엇인가요?”
- “25타석은 실제 9이닝 경기가 아니라 무엇을 의미하나요?”

**사용자 표현 금지 사례**: `모델이 생성한 한 점 득점 상황`, `고정 기본정책 일반타석 / 정상 승부`, `seed 41의 학습 정책 1,000 episodes 대결 후 success`. 사람에게는 ‘무사 1루에서 득점을 노리는 가상 장면’, ‘공격은 번트 없이 진행, 수비는 고의볼넷 없이 승부’, ‘1,000번의 연습 뒤 같은 상황에서 어떤 선택을 더 자주 했는지’ 등으로 말하라. 단, 위 표현도 **실제로 지원된 행동과 사건일 때만** 사용한다.

## 7. 연구·제품의 신뢰를 위해 요구하는 검증

- **BaseballLab:** 비율 계산·분모·확률합·영역[0,1]·재현성·같은 선수 동일 시즌·극소표본·결측·이적 기록·연도 보정 경계 검증. 기준선(Log5 단일/다항, 경험 빈도 등)과 보류 표본의 예측 성능·교정 곡선·로그손실 등 가능한 지표를 비교하고 실험 범위를 공개.
- **Match:** 학습 전후 가중치 변경만으로 성공 처리 금지. 같은 상대/과거 상대/여러 seed/독립 기간 평가에서 실제 성과·정책 변화·과적합 및 행동 선택 편향 검증. 현실 비교는 관측·인과·가능성의 단계가 다름을 명시.
- **EraMatch:** PDF/ZIP 원본을 기준으로 검색·시대 보정·확률 계산·25타석 시뮬레이션 경로 재현. 선수별 중복/팀 분할·외부 시즌·검증되지 않은 KBO 원본 라이선스 표기. legacy 모드와 개선 모드 출력 차이를 설명.
- **웹:** 모든 진입점의 클릭/선택/입력/도움말/계산과 결과 로딩/오류/모바일 대응을 실제 브라우저에서 검증. 스크린샷 3 프로젝트 + 설명 패널 저장.
- **보안:** 기존 로컬 바인딩·CSRF 성격의 토큰·경로/업로드/다운로드 제한·Git 사적 데이터 제외·검증된 삭제 절차 보존. 데이터/시드/모델/실행 버전의 출처 추적. 로컬 PC 보안 확인과 공개 서비스 보안 인증을 혼동하지 않음.

## 8. Codex 개발 우선순위 — 계획서만 쓰고 멈추지 말 것

### P0 — 정의 바로잡기·코드 현황 감사

- 먼저 현재 main을 가져오고 실제 코드와 경로/이름/의존성을 감사해 `docs/PROJECT_STATUS.md`의 3프로젝트 표를 갱신한다.
- `README.md`, `PROJECT_VISION.md`, `docs/PROJECT_COMPASS.md`에서 기존의 **부모=기반만**, **Era=AI-인간 역사 비교** 표현을 새 정의로 바로잡는다. 기획 변경 이력은 남긴다.
- 현재의 Match R1 학습·원본·체크포인트·2023 외부 평가와 보안 기능은 건드리지 않고 회귀 검증한다.

### P1 — **BaseballLab 시뮬레이터를 사용자 관점에서 실제 실행 가능하게**

- 이미 있는 시뮬레이션 UI를 살리고 **타자/투수 선택 → 통계/모델 선택 → 확률 계산 → 몬테카를로 타석 반복 → 결과 + 근거 패널**이라는 경로를 구현한다.
- 과제의 계산 코드를 읽고 원본 재현 vs 검증·개선 모델 경계를 만든다. 과제 자체에만 한정된 시대 보정은 EraMatch에 따로 노출하되 확률 계산 코드는 중복하지 않는다.
- 사용하는 자료에 따라 **현재 실제 가능한 데이터**만 선택 가능하게 한다. 데이터가 비어 있으면 허구 선수/확률/실행 성공을 만들지 않는다.

### P2 — EraMatch를 과제 웹 버전으로 구현

- 연도·선수 검색 → 원본 스탯 → 시대 보정 → 타자·투수 Log5 결합 → 25타석 몬테카를로 → 결과·설명 패널을 작동하게 한다.
- 과제 재현/개선 모델의 결과 차이를 비교한다. KBO CSV 검증 전에는 '과제 자료 기반' 상태를 표시하고 공인 정확도나 공식 검증을 가장하지 않는다.
- 현재 있는 KBO/MLB 데이터 인프라를 공유하고 과제용 별도 무단 다운로드/복제 경로를 만들지 않는다.

### P3 — Match 기존 연구를 새 UX/엔진 정의와 연결 및 후속 데이터 개발 준비

- Match를 `AI 전략의 자율 경쟁학습 + 인간과의 역사/현대 비교`의 전체 연구 기능으로 재정렬한다. **현재 R1은 제한된 연구로 보존**하고 이미 구현된 학습 상태를 제대로 보여준다.
- BaseballLab의 통계 시뮬레이션 모델을 Match에서 사용할 때, 행동에 따른 **반사실 결과의 현실성 검증이 없으면** 학습 근거로 바로 채택하지 않는다.
- 실제 투구 단위 Match 단계와 현대/역사 비교는 별도 미완성 단계로 명확하게 남기고, 추가 자료가 확보된 범위부터 개발한다. 무리하게 모든 시대/기술/9이닝을 당장 완성했다고 주장하지 않는다.

### P4 — 실제 데이터·세이버메트릭스 지식 허브 확장(후속·독립 마일스톤)

- MLB/KBO 시즌별 기록, 경기별 플레이, 투구 단위 자료를 **허용된 경로로** 축적. 자료 출처·버전·수집 일시·이용 조건·필드/분모·결측·표본 편중을 남긴다.
- Log5, 다항 Log5, BABIP, DIPS/FIP, K/9, BB/9, OBP, SLG, OPS, wOBA, 파크팩터, 평균 회귀, 시대 보정 등 지표 정의와 논문·설명서를 데이터 카탈로그로 관리한다.
- 데이터 정밀도와 결측에 따라 각 프로젝트가 이용 가능한 기능을 자동 표시한다. 기존 실제 2023/2024 Retrosheet와 KBO 1982~2025 과제 데이터의 검증 상태는 분리.

**작업 권고:** 우선 P0~P2를 실제 코드와 웹 동작까지 끝내고, P3~P4는 이번 작업의 진행 가능 범위와 필요한 데이터/이용조건을 구체화하라. 기능이 작동하지 않는데 계획서만 늘리지 말 것.

## 9. 완료 보고서 양식 — 사용자에게 알아듣게 설명

완료 후 Codex는 반드시 다음 순서로 보고한다.

1. **BaseballLab / Match / EraMatch 각각 지금 무엇을 클릭해서 할 수 있나** (URL·버튼·실제 지원 범위)
2. **이번에 실제 구현한 것과 아직 하지 않은 것** (화면과 코드 경로, 변경 파일)
3. **원본 과제 방식과 개선 모델의 차이** (근거·확률 합·검증 성능, 검증이 안 됐으면 이유)
4. **실제 데이터의 출처/보관/권한과 구체적 한계** (사용자 파일 없으면 어떻게 표시되는지)
5. **테스트 결과**: pytest 결과, 실제 브라우저를 사용한 시나리오, 주요 스크린샷, 기존 연구 결과 보존 여부
6. **다음 한 번의 개발에서 실현할 수 있는 작업 2~3개** (우선순위와 완료 조건)

**정직한 결론이면 충분하다.** 테스트 통과는 논문의 인과 검증이 아니며, Log5를 썼다는 사실만으로 현실과 같은 야구를 재현했다고 주장하지 마라.

## Codex에 이 파일과 함께 보낼 첫 지시

> 이 MD는 이전 기획의 프로젝트 역할 정의를 수정한 최신 요구사항이다. 기존 문서와 충돌하면 본 MD를 우선으로 적용하라. 현재 저장소의 구현을 감사한 뒤 **BaseballLab = 통계·세이버메트릭스 기반 타자-투수 시뮬레이터, Match = AI 경쟁 학습과 인간 야구 비교 연구, EraMatch = 기존 KBO 역대 선수 가상 대결 과제의 웹화**로 바로잡아라. 실제 웹에서 각 프로젝트를 선택하고 실행하는 UX와 맥락형 계산 설명 패널을 구현하라. KBO 과제의 원본 코드/데이터가 있으면 보존한 채 재현하고, 모델 가정을 검증한 개선 방식과 비교하라. 우선 P0~P2를 실제 구현·테스트·스크린샷까지 완료하고 Match 기존 연구 데이터와 보안 기능을 손상하지 마라. 검증되지 않은 데이터를 실데이터 검증 완료로 포장하거나 없는 기능을 구현했다고 보고하지 마라.
