## 0. 사용자 의도 — 가장 먼저 이해할 것

이 프로젝트는 야구를 좋아하는 사용자가 **리그·시즌·선수·대결 목적을 선택하고, 실제 야구 기록을 근거로 시뮬레이션을 실행하며, 그 결과가 왜 나왔는지 이해하는 웹 연구실**이다. 그 기반 위에서 AI가 인간이 정한 최적 전술을 모방하는 것이 아니라 **서로 경쟁하면서 타격·투구·전략을 변화시키는 과정**을 연구하고 싶다.

사용자가 지쳐 있는 이유는 다음과 같다.

1. 기존 코드에 매번 기능을 끼워 넣으면서 제품 목적보다 내부 구조·호환성이 앞섰다.
2. 모델·데이터·검사·파일 연결 상태를 사용자가 알아야 실행할 수 있어 UX가 번거롭다.
3. '고정 기본정책', '모델이 생성한 한 점 득점 상황' 등 개발자 문구가 화면에 나온다.
4. 자료 출처와 무결성은 중요하지만, 시스템이 해결할 일을 사용자에게 떠넘기고 있다.
5. Log5·몬테카를로·기존 세이버메트릭스 과제의 계산이 각 화면/프로젝트에서 어떻게 동일하게 쓰이는지 명확하지 않다.
6. 다수의 개발 지시 문서가 쌓이며 BaseballLab·Match·EraMatch의 역할이 반복해서 바뀌었다.

**이번 작업은 새 기술 데모를 만드는 것이 아니라, 이미 만들어진 제품을 제대로 정리하는 작업이다.** 구현 전에 기존 기능을 확인하되, 기존 설계의 불필요한 제약에 끌려가지 말라.

### 절대 금지 사항

- 새 GitHub 저장소, 새 루트 프로젝트, `v2/`에 별도 사본을 만들고 기존 앱을 방치하는 방식 금지.
- 기존 연구 결과(JSON·가중치·원본 CSV·ZIP·로그), 기존 사용자 과제, Git 이력을 임의로 삭제·덮어쓰기·재생성 금지.
- 기능을 없애고 '재설계'라 부르기 금지. 이전 실행 경로·결과를 최소한의 호환 경로로 유지하라.
- 근거 없는 임의 성공률, 가짜 선수·시즌, 검증되지 않은 능력치를 실제 데이터처럼 제시하지 말라.
- 단순 테스트 통과를 과학적 모델 타당성·개인정보 보호·사용성 인증으로 발표하지 말라.
- '더 많은 연구가 필요하다'는 보고서만 작성하고 실제 사용자 동선을 개선하지 않은 채 종료하지 말라.

- 모든 프로젝트는 **동일한 부모의 데이터 규격, 규칙 표현, 확률 계산 서비스와 시뮬레이션 인터페이스**를 재사용한다.
- '같은 엔진'은 **모든 시대·자료에 없는 세부 변수를 억지로 생성**하라는 뜻이 아니다. 자료의 해상도에 따라 동작 가능한 모델을 버전으로 구분하되 동일한 계약·검증·표시 방식을 사용한다.
- Match가 선택할 수 있는 행동·보상·학습기는 별도 실험 책임이다. 기존 통계 모델의 결과 빈도가 곧바로 **새 전략의 인과적 효과**가 되는 것은 아니다.
- EraMatch 원본 재현 모드와 개선 모델은 둘 다 공통 시뮬레이션 서비스로 연결하되, **검증 상태와 모델 버전이 다른 것**을 명시한다.

## 3. 한 가지 공통 계산 기준 — 시뮬레이션의 신뢰성

### 3.1 공통 엔진의 계층

```text
실제 원본 데이터 / 출처·이용조건
         ↓
정제·검증된 선수/리그/시즌 기록  ←  공식 규칙 및 세이버메트릭스 지표 정의
         ↓
표본 처리·리그 및 시대 보정 (적용된 가정/버전 공개)
         ↓
타자 × 투수 대결 확률 모델 (Log5 등 검증 가능한 대안)
         ↓
결과 사건의 완전한 분포(합=1, 배타성, 단위/분모 검증)
         ↓
몬테카를로 반복 추첨 + 규칙/상황 전이
         ↓
표본 수·신뢰구간·경기 장면·설명·실행 ID
```

- Log5는 상대적 확률 결합 방법이고 몬테카를로는 추정 분포에 따른 반복 추첨 방법이다. 둘 다 그 자체로 9이닝·주루·구종·볼배합의 전체 물리/인과 엔진은 아니다.
- 단타/2루타/3루타/홈런/볼넷/사구/삼진/기타처럼 서로 배타적인 사건 결과가 **음수가 아니고 합이 정확히 1**이 되도록 검증하라. `1-나머지`를 0으로 잘라 모순을 감추지 말라.
- 이항 Log5, 다항/일반화 Log5 또는 더 나은 경험/계층 모델은 **같은 보류 데이터를 통한 로그손실·Brier·교정도·조건별 오차·소표본 평가**로 비교하라. '세이버메트릭스라서 정확하다'는 주장은 금지.
- 과제의 표본 안정화 상수, DIPS/BABIP 강제 평균 고정, PA−BB로 타수 계산, SF 결측 0 처리, 시대 보정 비율은 각각 원문 재현용과 개선 모델을 구분하라.
- 개선 모델의 근거는 논문/공식 지표 정의·실제 데이터 성능으로 기록하고, 모델 선택에 쓴 validation과 최종 test를 분리하라.
- 기존 2024 MLB에서 보고된 다항 Log5 로그손실 개선은 해당 데이터/기간에서의 예측 결과이지 모든 리그·역대 선수·실제 전술의 우수성 입증이 아니다.
- 결과는 `engine_version`, `model_version`, `dataset_ids`, `assumptions`, `prediction_scope`, `random_seed`, `simulation_count`, `coverage`, `uncertainty`, `model_limitations` 등을 기록해 재현 가능하게 하라.

### 3.2 실행 가능 범위의 자동 결정

- **시즌 집계만 있는 경우:** 시즌 성적 기반 독립 타석/타자·투수 결과 시뮬레이션.
- **플레이별 기록이 있는 경우:** 아웃·주자·득점 등 추가 상태가 검증된 범위에서 상황형 시뮬레이션.
- **투구별 고해상도 자료가 있는 경우:** 근거가 확인된 구종·구속·투구 위치·타격 행동 등 더 정교한 모델 후보.

모든 경로는 공통 엔진 인터페이스를 쓰되, **해상도가 낮은 자료를 이용해 구종/스윙 궤적을 꾸며서는 안 된다.** 실행 가능한 가장 구체적인 검증 모델로 자동 선택하고, 화면에서는 '시즌 기록 기반' 등 짧은 문장으로만 알린다. 자료가 너무 부족해 합당한 계산이 불가능하면 버튼을 작동하는 척하지 말고 이유와 대안을 표시한다.

### 3.3 Match를 위한 경계

공통 결과 모델을 재사용할 수는 있지만, Match가 선택하는 구종·코스·스윙·기술·스타일에 따라 결과가 현실적으로 달라지는 **행동 조건부 모델의 타당성**을 따로 입증해야 한다. 현실에서 관측되지 않은 행동의 결과는 자료만으로 자동 확인되지 않는다. AI에게 인간의 좋은 전술을 정답으로 주입하지 말고, 가능 행동·규칙·제약·행동 관측 정보·보상을 명시하라. 향후 팀 승리는 타석 출루나 '3아웃 전 1점'과 별개 보상/경기 상태가 필요하다.

## 4. 데이터 플랫폼 — 사용자가 CSV 관리자처럼 일하지 않게 하라

### 4.1 공통 소유권

- **BaseballLab이 데이터/지표 지식의 단일 관리자**다. Match와 EraMatch는 경로를 제각각 하드코딩하지 않고 공통 `DatasetCatalog`/서비스 API로 데이터를 요청한다.
- 기존 `data/local/catalog/`, `data/local/retrosheet/`, `data/local/statcast/`, `outputs/`는 **이관 없이 우선 유지**하고 새 메타데이터 인덱스를 위에 얹는다. 물리 저장소 이동은 이점과 마이그레이션/롤백 테스트가 명확할 때만 한다.
- 각 데이터는 `provider / league / seasons / granularity(season,game,PA,pitch) / schema / units / license / acquisition_method / timestamp / version / sha256 / row count / missingness / entity IDs / known biases / allowed uses`를 가진다.
- 선수 고유 ID·동명이인·이적·복수 팀 시즌 기록·리그 평균 분모를 철저히 구분한다. 'KBO CSV가 있다'는 사실만으로 모든 연도가 정확하다고 취급하지 말라.
- 세이버메트릭스 지식 사전: AVG/OBP/SLG/OPS, BABIP, K%, BB%, K/9, BB/9, FIP, wOBA, wRC+, WAR, DIPS, Log5 등은 **정의·수식·분자/분모·단위·시대별 가용성·원천·주의사항·모델에서 실제로 사용되는지 여부**를 분리 기록한다. 근거 없는 지표를 단순 나열해 'AI가 모든 야구 정보를 배웠다'고 하지 말라.

### 4.2 데이터 자동 연결 UX — 사용자는 선수만 고른다

사용자가 `KBO / 1990 / 타자 A / 투수 B / 25타석`을 고르면:

1. 검증된 로컬 캐시와 기존 카탈로그 확인.
2. 없으면 **허용된 공식 배포 / 조건이 명확한 API**에서 자동 확보 가능한지 확인.
3. 획득 시 버전·체크섬·필드·기간·출처·이용 조건을 자동 검사 및 캐싱.
4. 지원 가능한 적절한 모델 선택. 실패하면 다른 공식적이고 적합한 소스로 제한적 전환할 수 있는지 평가하되, **조용한 시즌 교체/리그 대체/합성 자료 대체는 금지**.
5. 해당 데이터로 지원되는 분석은 곧바로 실행. 정말 접근권한·공식 파일이 필요한 경우에만 **최초 한 번의 간단한 연결** 절차를 보여주고 이후 재사용.

일반 사용자가 `dataset_id`, `source-url`, `sha256`, `validation_from`, `seed`를 입력하게 하지 말라. 이런 설정은 *고급/연구자용*으로 숨겨라. 데이터가 준비되는 동안 진행 상태를 '선수 기록 확인 → 계산 → 결과'로 설명하라.

### 4.3 제공 경로 조사와 안전성

- Retrosheet 공식 플레이별 자료는 이미 일부 확보한 실제 자료를 보존하며 연도 확장 가능성과 공식 고지를 확인한다.
- MLB StatsAPI/공식 통계 제공·공식 시즌 기록 및 Statcast 계열은 **기능, 이용 약관, 자동 요청 허용 여부, 갱신 주기, 식별자/필드, 한도**를 각각 조사하고 실제 연결 성공을 검증하기 전 '자동 지원'으로 표시하지 않는다.
- KBO 기존 과제 CSV는 `LEGACY_UNVERIFIED`로 관리하며 출처·Kaggle 원본 버전·재배포 권한·공식 통계 대조가 확인되기 전 공개 배포하지 않는다. 사용자가 이전에 제공한 자료를 기존 설치에서 재사용할 수 있으면 재업로드를 강요하지 않는다.
- 최신 정보는 제공 API의 허용 범위에서 갱신하고, 오프라인 시 **최종 검증된 시점**을 표시한다. 자동 접근이 불허된 사이트를 무단 스크래핑해서 UX를 맞추지 말라.
- 자료 부족을 사용자 책임으로 떠넘기지 않고, 자료와 기능의 매핑·준비 상태·실패 원인을 시스템이 설명하라.

### 4.4 데이터 신뢰성/보안

원본 불변, 해시/버전, schema validation, 중복·결측·분모 오류·범위·연도/팀 편향 검사, 훈련/평가 누수 방지, 다운로드 경로/리다이렉트/ZIP 압축 검사, 로그·화면의 토큰/로컬 경로 노출 방지, Git 비공개 자료 제외, 삭제 전 영향 확인과 재현성 안내를 유지한다. **Windows ACL·OneDrive 동기화·백업·디스크 암호화는 실제 테스트하지 않았다면 미확인으로 표기**한다. 코드가 암호화하지 않으면서 '안전하게 암호화 보관'이라고 주장하지 말라.

## 5. UX/UI — 야구팬의 언어로 실행하고 이해한다

### 5.1 제품 첫 화면

세 진입점이 각각 무엇을 할 수 있는지 즉시 알 수 있어야 한다.

- **선수 대결** — '실제 기록으로 타자와 투수가 붙으면?' (`/baseball`)
- **AI 전략 연구** — 'AI가 야구를 스스로 배우면 어떤 선택이 바뀔까?' (`/match`)
- **역대 선수 대결** — '다른 시대 선수가 맞붙으면?' (`/eramatch`)

일반 사용자에게 `E01`, `R0`, `R1`, `baseline`, `checkpoint`, `transition`, `donor`, `policy`, `seed`, `model-generated` 등의 내부어를 첫 화면에서 강요하지 않는다. 내부 용어를 삭제하는 것이 아니라 **한국어 UI 표현과 연구자 상세 로그를 분리**한다.

### 5.2 공통 대결 화면

- 좌측/중앙: 선수/연도 검색(자동완성), 시뮬레이션 횟수(기본값), 대결 시작, 결과 카드, 스코어보드/타석·주자 상태(데이터가 뒷받침하는 경우만), 이전/다음/재생.
- 우측/하단: **'이 결과는 어떻게 계산했나요?'** 설명 패널 — 사용 원본, 보정 전후 값, Log5 등 적용 공식의 이유, Monte Carlo 반복의 의미, 신뢰 범위, 비교 모델, 데이터 한계.
- 결과는 단일 25타석 난수 실현과 다회 시행의 기대/변동성을 구분한다. 25타석 결과를 실제 경기 점수나 검증된 타자 능력처럼 표시하지 말라.
- 다른 시즌·선수 선택 시 자료 준비/실패 처리 때문에 화면 전체가 막히지 않도록 하고, 잘못된 선택은 안내와 즉시 수정 가능한 입력으로 처리한다.
- 초기 사용자 흐름 목표: **홈 → 프로젝트 클릭 → 선수/시즌 선택 → 실행 → 설명 확인**. 정보 입력, 수동 URL 붙여넣기, 여러 검사 버튼은 고급 옵션으로 이동.

### 5.3 Match 전용 관찰 화면

- AI 학습 전/중간/후의 **같은 상황·같은 상대** 선택 비교를 기본으로.
- 행동 빈도와 정책 확률을 구분하고, 수치·그래프·리플레이를 연결한다.
- 왜 선택했는지 확인 불가능한 내적 동기를 만들어 설명하지 않는다. '이 상황에서 번트 선택 확률이 X→Y로 바뀜'처럼 관찰 사실을 먼저 제시.
- 승률·득점률·우세를 혼동하지 말고, 비대칭 역할의 성공률 50%를 '누가 더 강하다'의 기준으로 사용하지 말라.
- 인간 전략과 비교하는 화면·보고서는 **Match의 장기 산출물**이다. EraMatch에 잘못 배정하지 말 것.

### 5.4 접근성·제품 완성도

데스크톱 1366px, 모바일 390px, 키보드 탭/포커스, 대비, 데이터 로딩/오류/빈 상태, 한글 문장, 그래프 대체 텍스트를 실제 브라우저에서 검증. 스크린샷뿐 아니라 **최초 설치 환경에서 클릭해 끝까지 실행하는 동선**을 테스트한다.

## 6. Codex 개발 방식 — 역할 분담은 수단, 검증은 필수

단일 AI에게 기획/자료/통계/보안/UI를 무검증으로 한 번에 맡기지 않는다. **Codex가 지원하는 도구가 실제로 있는지 확인한 뒤** `AGENTS.md` 및 필요한 Skills/Subagents를 활용하라. 존재하지 않는 멀티 에이전트 기능을 작동한다고 보고하지 말라.

권장 역할:

| 역할 | 독립 산출물 / 리뷰 포인트 |
|---|---|
| 메인 오케스트레이터·아키텍트 | 목적 충돌 해결, 단계 분할, 공유 계약, 최종 통합 |
| 세이버메트릭스 검토 | 원 과제와 개선 모델의 수식/확률/성능 및 근거 검증 |
| 데이터 엔지니어 | 카탈로그, 합법적 수집 경로, 스키마·시즌·식별자 검증 |
| 시뮬레이션/ML | 공통 계산 엔진·전이·Match 호환·재현 테스트 |
| UI/UX | 실제 사용자 동선, 쉬운 한국어, 반응형, 설명 패널 |
| QA/보안 | 입력·압축·출처·원본 보호·회귀·브라우저/Windows 검사 |

- 서로 같은 파일을 동시에 수정해 충돌을 만드는 병렬 작업보다, **리서치/독립 코드 영역/리뷰**를 병렬화하라.
- `AGENTS.md`에는 불변 목적, 세 프로젝트 책임, 데이터 보호, 테스트/커밋 게이트, 임의 데이터 금지를 기록한다.
- 각 작업은 `증상 → 원인 → 수정 코드 → 테스트 → 실제 UI 확인 → 남은 한계`를 남긴다.
- **기존 기능의 테스트와 원본 해시는 변경 전후 비교**. 통과되지 않으면 새 기능 완료로 표시하지 않는다.

## 7. 단계별 **기존 코드 개선** 계획 — 이번 Codex가 실행할 순서

### 0단계 — 현 상태 스냅샷 / 위험 없는 시작

**반드시 수행:** 최신 `origin/main` 확인, 작업 트리 상태 확인, 별도 **작업 브랜치** 생성(새 저장소 아님), 현재 `pytest`, 기존 스크립트·브라우저 경로·보관 파일 해시·기존 실행 결과 백업/기록. 사용자 변경이 있으면 무단 초기화하지 말 것. 변경된 부분을 읽고 기존 보존 조건을 선언.

**산출물:** 변경 대상 경계, 보존 파일, 당장 손댈 곳, 실제 테스트 결과, 불확실한 데이터 공급 경로의 목록.

### 1단계 — 공통 계산 계약 및 중복 제거 (우선 구현)

- 현재 `matchup` 서비스와 EraMatch의 원본/개선 계산, 기존 `simulation`을 감사한다.
- 공유할 **선수 시즌 표준 스키마·확률 분포·시뮬레이션 실행 계약·모델 메타데이터**를 구현/정리한다.
- 기존 `src/baseball_lab/matchup/` 등 검증된 코드부터 재사용하고, 책임이 뒤섞인 부분만 점진적으로 리팩터링한다.
- EraMatch 원본 재현 결과와 MLB 2024 기존 연구 수치를 회귀 테스트로 유지한다.
- 추가 모델의 학문적 타당성을 자동 주장하지 말고 기존 모델 대비 성능과 오류를 보여준다.

**완료 기준:** `BaseballLab`과 `EraMatch`가 동일한 계산 API 계약·출처 계보를 사용하며 기존 재현 테스트가 깨지지 않는다.

### 2단계 — 데이터 자동 준비와 선택 UX (이번 작업에서 실제로 진행)

- 검증된 로컬 자료 자동 발견 → 공식/허용된 제공원 연결 → 정규화 → 캐시 → 상태 표시 흐름 구현.
- 최소한 **현재 이미 사용 가능한 KBO 과제 자료와 MLB 2024 자료**에 대해 사용자가 불필요하게 업로드·검사 설정을 반복하지 않고 실행하도록 개선.
- 2023 MLB는 이미 확보된 플레이 자료를 재사용할 수 있는지 확인하고, 선수 대결 카탈로그로 확장 가능하면 실제 구현·검증.
- 더 많은 연도·API는 출처·약관·스키마·이용료가 확인된 순서로 추가. 미검증 연도는 '지원'으로 표시하지 않는다.
- 자료 부족 시 *가능한 분석은 실행, 불가능한 분석은 왜 불가능한지 쉽게 설명*하는 기능별 대체 동선을 구현.

**완료 기준:** 기본 사용자가 리그/시즌/선수를 고른 뒤 원본 URL·해시·데이터 분리 날짜를 입력하지 않아도 2024 MLB 선수 대결과 이미 연결된 KBO EraMatch가 작동. 없는 데이터는 가짜로 생성하지 않는다.

### 3단계 — 공통 웹 UI/UX 개선 (이번 작업에서 실제로 진행)

- 홈의 3개 진입점, BaseballLab/ EraMatch 대결 화면, 오른쪽 계산 근거 패널, 결과 재생·저장/재열기를 한 사용자 언어 시스템으로 정리.
- 각 화면의 실제 동작·데이터 준비 안내·에러 메시지를 재작성; 개발자 용어는 접힌 상세 정보로 이동.
- 동일 카드/선수 검색/상태 표시/설명 컴포넌트 공유. Match 화면의 연구 기능은 보존.

**완료 기준:** 첫 사용자 시나리오 3개(BaseballLab 선수 대결, EraMatch 다른 시대 선수, Match 기존 학습 결과 보기)를 실제 브라우저에서 완료하고 화면·스크린샷·오류 없음 기록.

### 4단계 — 학술 검증과 Match 확장 준비 (설계 + 검증 가능한 작은 구현)

- 실제 데이터와 모델 근거를 바탕으로 **독립적인 다른 시즌**에서 확률 모델의 예측력/편중/결측 처리·불확실성을 검증.
- Match의 구종·제구·볼배합·선구안·교타/장타 선택을 지원하려면 필요한 입력/행동/결과 데이터 목록과 인과적 제약을 구체화하고, 자료가 있는 가장 작은 하나의 전술 실험을 선정.
- 기존 '3아웃 전 한 점' 학습 경로와 저장 결과는 유지하되 이를 곧장 야구 전략의 극한 연구 완료로 부르지 않는다.
- 인간 야구의 **현대 3개 시즌 비교와 장기간 역사 변화 비교는 Match의 연구 축**으로 개발 로드맵에 연결. EraMatch는 역대 선수 가상 대결의 웹 기능을 우선 유지.

**완료 기준:** 과장 없는 실제 검증표, 다음 Match 실험의 관측/행동/보상/환경/자료/평가 계약, UX에서 그 한계 설명.

> 4단계의 전 기능을 한 번에 완성하겠다고 약속하지 말 것. 다만 이번 개발이 '모델을 나중에 검토'만 하다가 끝나지 않도록 1~3단계의 실제 사용자 개선을 완료하고 검증까지 수행할 것.

## 9. 결과 보고 형식 — Codex 최종 답변에 반드시 포함

1. **이번 작업에서 실제로 바뀐 사용자 경험**: 이전 → 이후, 어떤 버튼과 화면에서 어떻게 달라졌는지.
2. **코드 구조**: 새로 만든 프로젝트가 아니라 기존 어느 모듈을 재사용/정리했는지.
3. **데이터**: 실제 지원 리그·연도·출처·사용 조건·자동 수집 성공과 한계.
4. **시뮬레이션**: 기존 Log5/몬테카를로 재현, 개선 모델의 근거, 검증 숫자와 남은 가정.
5. **Match와 EraMatch**: 기존 기능 보존 여부, 이번에 새로 개발한 것과 아직 없는 것.
6. **테스트/실행**: 명령·실제 테스트 수·브라우저 동선·스크린샷·실패/미실행 사유.
7. **보안**: 수행한 점검/개선과 미확인 범위.
8. **커밋**: 커밋 SHA, 변경 파일, 롤백 방법. 권한이 있다면 작은 검증 단위로 커밋하고 허용된 기존 저장소 브랜치로 반영하라.

**완료됐다는 문구는 실제 동작·테스트로 확인한 범위에만 사용한다.**
