## 0. 제일 먼저 이해할 것

사용자는 프로그래밍 로그를 읽고 싶은 것이 아니다. 야구에 관심 있는 일반 사용자·연구 기획자의 눈으로 **경기를 관찰하고, AI가 무엇을 선택했는지 보고, 이전보다 어떻게 변했는지 알아보고, 그 결과를 얼마나 믿을 수 있는지 이해하고** 싶다. 현재는 `모델이 생성한 한 점 득점 상황`, `고정 기본정책 일반타석 / 정상 승부`, `지원 상황`, `seed`, `전이`, `정책` 같은 개발 용어가 화면을 차지한다. 이 상태에서 수치를 더 늘리는 것은 개선이 아니다.

**요청의 우선순위:** ① 개념·화면 용어 교정 ② 화면 자체를 야구 중심으로 재설계 ③ 실제 데이터·학습 결과·보안의 신뢰성 ④ 반복 학습 과정의 시각화 ⑤ 이후 Match-A 및 전체 경기 확장. 사용자가 이해하지 못하는 차트를 그럴듯하게 미화하지 말라.

### 화면이 반드시 답할 네 질문
1. **지금 어떤 야구를 보고 있나?** 실제 경기 기록인가, 실제 기록으로 보정한 가상 상황인가? 어떤 범위의 규칙/선택이 지원되는가?
2. **AI가 실제로 무슨 결정을 내렸나?** 사람이 읽는 행동 이름과 선택 당시의 아웃·주자·이닝/점수 등 *실제로 엔진이 가진 정보*를 보여줄 것.
3. **반복 대결 후 무엇이 달라졌나?** 학습 전, 중간, 이후의 동일한 상황에서의 선택과 고정된 상대를 상대로 한 성과를 같이 보여줄 것.
4. **왜 믿거나 조심해야 하나?** 자료의 출처·범위·누락·검증·현실과 다른 점이 보일 것. 한계는 숨기지 않되 기술적 원문은 접힌 상세 정보로 분리.

### 잘한 것은 유지
- 부모 `/simulation`과 자식 `/match`의 화면·코드 경계가 생겼다.
- Retrosheet 2023/2024 공식 배포 자료, 출처/해시, 원본·가상 플레이 구별, 실제 학습 정책/재평가·체크포인트.
- 한 번 실행·중지·과거 실행·리플레이·비교, 테스트 입력과 연구 결과의 구분.
- 로컬 전용 서버, POST 실행 토큰, Origin/Host 제한, 경로 검증, 무제한 파일 업로드 방지 등 일부 방어 장치.

### 지금 화면의 핵심 결함
1. **개발자용 개념이 사용자용 메인 문구에 그대로 노출된다.** `/simulation`의 대표 제목이 `모델이 생성한 한 점 득점 상황`, 정책이 `양쪽 모두 고정 기본 정책`으로 표시됨. 일반 사용자는 장면의 내용·목적을 해석할 수 없다.
2. **야구 장면보다 글자가 중심**이다. 스크린샷의 관찰 화면은 작은 주자 다이아몬드, 줄글, 이전/다음 버튼 위주로 구성되어 경기의 흐름이 직관적이지 않다.
3. **결과 첫 화면이 질문에 비해 단순하다.** 맞대결 46.9%/53.1%, 고의볼넷 확률 변화 등은 있지만 *어떤 상황에서 어떤 선택을 했는지, 대응의 변화가 어떻게 얽혔는지*를 곧바로 탐색하기 어렵다.
4. **‘우세’ 표현 자체를 재검토해야 한다.** 현재 게임은 24개 아웃·주자 상태를 균등하게 시작해 `3아웃 전 1점 득점`을 평가한다. 이 구조에서 성공률 50%는 양측 실력의 자연스럽고 공정한 대칭점이라고 볼 근거가 없다. `46.9% 득점 / 53.1% 차단 → 수비 우세` 문구는 **실제 기록된 결과 빈도와 역할별 능력 우위를 혼동**시킬 수 있다. `verdict()`의 0.5 기준 통계 검정은 재검토하고, 근거 있는 대칭 기준이 없으면 **'이번 설정에서는 1,500번 중 704번 득점'**만 표시하라. 공격/수비의 개선은 *각자가 동일한 고정 상대를 상대했을 때* 따로 판단한다.
5. **다른 가상 장면에서 실제 플레이를 가져와 만든다는 설명이 부족**하다. `ordinary_turn`은 '타자의 스윙 버튼'이 아니라 과거 실제 플레이 묶음의 분류다. 사용자에게 `일반 타석`만 던지면 정밀한 스윙·타구 시뮬레이션으로 오해할 수 있다.
6. Match-A는 실제 투구 기반 학습 미완성, Match-B는 1점 득점 실험에 한정. 화면이 과도한 'AI 야구 학습' 완성감을 주면 안 된다.
7. 자료 보호·무결성·공개 범위·보관 정책을 사용자가 확인할 수 있는 **자료 관리 화면 및 문서**가 부족하다. 로컬 저장과 해시가 있다고 포괄적 '보안 완비'로 표현하면 안 된다.

## 2. 첫 화면부터 정보 설계 수정

### 부모/자식은 같은 사이트 내에서 명확히 탐색
- `/` BaseballLab **야구 연구실**: 오늘 할 수 있는 두 활동을 간결히 설명. **① 야구 장면 살펴보기 ② AI 전략 변화 실험하기**. `AI 학습 시작` 링크를 눌렀는데 실제로는 설정 페이지로 이동한다면 링크명은 `실험 설정하기` 또는 `연구 시작하기`로 수정. 누를 때 실제 시작되는 액션과 표현을 일치.
- `/simulation` **야구 시뮬레이션**: 실제 기록의 재생 vs 기록을 바탕으로 만든 가상 상황 관찰을 명확히 선택. 여기서는 새 AI 학습 없음.
- `/match` **AI 전략 연구**: Match-A **한 타석 승부**(현재 준비 중), Match-B **득점 전략 연구**(현재 제한된 범위 실행 가능) 구분. 사용자에게 E01/R0/R1/스키마 버전 강요하지 않음.
- `/match/team` **득점 전략 연구 시작**: 기간, 학습 반복 횟수는 쉬운 설명과 기본값; 버튼 클릭 전 '이번 실험이 할 수 있는 것/없는 것' 한 문단. 실행 중에는 그래프와 경기 장면을 이어서 볼 수 있게.
- `/lab/data` **데이터 관리·신뢰성**: 현재 저장 자료, 데이터 제공 기관, 용도, 시즌, 표본, 품질, 저장 위치, 라이선스·이용 범위·삭제/정리 방법 등.
- 향후 Match-A/전체 경기: **지원되지 않은 기능은 비활성/로드맵**으로 표시. 이행되지 않은 동작 버튼을 제공하지 말 것.

## 3. 야구 시뮬레이션은 '정보 페이지'가 아니라 '관람 화면'이어야 한다

현재 엔진이 지원하는 범위에서 우선 **2D 야구 필드/주루 다이아몬드 + 스코어/아웃/진행 타임라인**으로 만든다. 3D 경기·애니메이션이 조건이 아니다. 실제 기록 없는 선수 외형, 공의 비행 궤도, 구종·위치·속도는 **절대 그럴듯하게 생성하지 말 것**.

**핵심 레이아웃(데스크톱)**

```text
[실제 경기 기록 재생 ▾ / 기록 기반 가상 시뮬레이션 ▾]  [자료: 2024 MLB]
┌──────────────────────────────────┬──────────────────────────┐
│  경기 상황(실제 엔진 지원값만)    │  이번 장면              │
│  아웃 ●●○ / 주자 ●○○            │  '1루에 주자, 무사'     │
│          ◇2루                    │  공격 선택: 번트 시도   │
│      ◇3루  ◇1루                 │  수비 선택: 승부       │
│          홈                      │  결과: 1아웃 2루       │
│  [이전] [재생/멈춤] [다음]         │  이번 선택의 의미 [ⓘ]  │
├──────────────────────────────────┴──────────────────────────┤
│  장면 목록: ① 시작 → ② 타석 종료 → ③ ...                 │
│  [실제 기록] 또는 [기록 바탕 가상 장면]                     │
│  출처·실행번호·원본 ID는 [자료 상세 보기]                   │
└──────────────────────────────────────────────────────────────┘
```

- **경기 시작/끝/다음 장면**을 표시하고 진행 단계마다 바뀐 주자와 아웃을 강조. 특정 턴에 실제 득점이 있으면 원인이 관측된 범위에서만 표시.
- 실측 장면은 `실제 경기에서 일어났던 기록`, 가상 장면은 `실제 경기 기록에서 비슷한 상황을 골라 계산한 가상 장면`으로 **항상 고정 표기**. 한 번의 가상 실행을 원래 MLB 경기처럼 보이지 않게 할 것.
- 2024 Retrosheet에 없는 **투수 손에서 포수 미트까지의 공 궤적, 스트라이크존, 구속, 선수별 능력치**는 현재 재생 불가. 향후 해당 데이터 확보 이후에만 추가.
- 실제 기록 원문/모델 상태는 1차 화면이 아니라 펼치기 패널. 사용자가 야구 규칙을 잘 모르더라도 `무사 1루 → 1사 2루` 같은 변화는 자연어+그림으로 이해하도록.
- 모바일은 주자 그림 → 사건 카드 → 이동 컨트롤 → 타임라인 순서. 키보드/화면읽기/명암·상태를 색 외 텍스트로 제공.
- `자동 재생`은 명확한 일시정지·속도 조절·마지막 장면 동작이 있어야 하며 스크린 리더에도 현재 턴 변경을 알릴 것.

## 4. AI 전략 연구 화면: 핵심은 '학습 전후의 경기와 의사결정' 비교

### 기본 결과 페이지 3단 구성

**상단 — '이번에 알아낸 것' (연구 질문 단위):**
- `3아웃 전에 1점을 낼 수 있었던 비율` 등 모델의 정확한 목적 표현. 절대로 `MLB 수비가 더 강하다` 같은 일반화 금지.
- 같은 고정 상대와의 비교: 예) `득점 저지 성과는 이전보다 좋아졌고, 공격 성과 개선은 확인되지 않았습니다.` **확률 개선/검정의 조건**은 간결하게 아래 작은 글에서 연결.
- 현재 실행의 범위: 실제 2024년 기록 기반 / 지원 행동: 번트 여부(관측 분류)·고의볼넷 여부 / 전체 경기 승부 아님.

**중단 — '어떻게 달라졌나':**
- 학습 `처음 → 1,000회 → 2,000회 → 3,000회` 구간(실제 저장된 체크포인트만) 슬라이더.
- 왼쪽은 상황 선택(예: 무사 1루), 가운데는 그 상황의 **공격/수비 선택 비율 시각화**, 오른쪽은 **기준 상대를 상대한 성공률 변화**. 다른 상대 대결을 합쳐 만든 변화처럼 설명하지 말 것.
- 변화는 선택 확률(모델 정책 출력), 실행 빈도(실제로 선택된 횟수), 결과 빈도를 따로 표시. 각 지표의 분모와 데이터 출처를 클릭하면 확인.
- 두 AI의 선택이 교대로 바뀌는 타임라인, 초기/과거 체크포인트 상호 대결. **인과 검증 없이 '상대의 대응 때문에'라고 단정하지 않음**.

**하단 — '경기처럼 보기'**:
- 해당 시점의 저장 리플레이 불러오기 → 위 2D 필드에 표시.
- 같은 출발 상황/같은 평가 조건 아래 초기 vs 최신 AI를 나란히 비교할 수 있게. 단 확률적 환경에서 한 장면 차이가 곧 실력 차이는 아님.
- `사람은 보통 어떻게 선택했나?` 비교를 할 때 **실제 인간 관측 비율**과 AI 선택 비율을 비교하되 선수 구성/상황 차이·표본을 함께 표시. 실제 사람 개개인의 의도는 추정하지 않는다.

### 사용자가 편하게 이용하도록
- `어떤 실험인가` 설명은 첫 실행 2~3문장. 나머지 기준·한계·출처는 자세히 보기.
- 그래프별 제목은 `그래프가 보여주는 질문`으로 작성. 단순 `Timeline`, `Overview`, `Cross-play` 탭 금지.
- 실험 끝나면 **한눈에 본 결론 3개**: 바뀐 선택 / 바뀐 성과 / 아직 말할 수 없는 것.
- 결과가 없으면 실제로 왜 없는지 표시. 임의로 예쁜 성공 그래프 만들지 말 것.
- 의미 없는 카드·숫자·상태 배지는 줄이고, 전체 페이지를 나열식 리포트 대신 좌우 비교와 경기 화면 위주로.

## 5. 학습자료와 연구 결과의 보안·신뢰성: '보안'과 '데이터 근거' 둘 다 필요

### 현재 확인된 최소 보호 조치(유지)
- `127.0.0.1`에만 HTTP 서버 바인딩, POST 요청 토큰, Origin/Host 체크.
- 사용자 파일명으로 서버 경로를 직접 만들지 않음. 결과 파일 경로를 출력 폴더로 제한.
- 공식 원천 URL·라이선스/이용고지·SHA256, 사용자 업로드 최대 크기 제한, 원본/생성/가정 분리.
- 원본 ZIP·CSV 및 가중치는 로컬에 보관하고 Git 저장소에 원본 데이터 파일을 업로드하지 않는 정책.

이는 **정적 코드·문서에서 확인한 일부 장치**다. 전체 보안 테스트, 비밀 유출 점검, 파일 권한, 암호화 저장 여부까지 검증한 것은 아니다.

### 추가로 요구하는 보안·관리 기능 (P0/P1)
1. **자료 분류**: 공식 공개 자료 / 사용자 제공 비공개 자료 / 정제 중간산출물 / 학습 모델·체크포인트 / 리포트·로그 / 테스트용 가짜 자료로 나눠 보관. 서로 목적이 다르므로 동일 취급 금지.
2. **안전한 기본 저장**: 데이터·로그·체크포인트의 위치와 크기, 접근 범위, 보관 기간을 화면에서 확인; 디폴트 로컬 전용, 파일·디렉터리 권한을 OS 기준으로 강화. Windows 환경에서 다른 사용자 접근/백업/클라우드 동기화 경로(OneDrive 등) 노출 점검. 암호화 저장을 했다고 주장하지 않음; 필요 시 OS BitLocker 등 *선택적 보호 방법* 안내.
3. **Git 유출 방지**: `.gitignore` 점검, 큰 원본 CSV·ZIP·결과·임시 파일·키·환경 변수 파일의 Git 추적 차단, `git status`/history/secrets 스캔. 기존 추적 파일은 성격에 따라 제거 여부 판단, 이전 커밋에 남은 비밀은 별도 대응. 공개 가능한 익명 집계만 명시적으로 Git 배포.
4. **네트워크·공급망**: 자동 다운로드는 사전 확인한 **고정 HTTPS 공급원/릴리스/해시** 및 사용 조건에 한해 동작. 사용자가 임의 URL을 입력했을 때 서버가 접근하는 기능을 무분별하게 만들지 않음(SSRF 위험). ZIP 압축 폭탄·경로 이탈·잘못된 CSV·거대 텍스트/행 수·인코딩 처리 검증.
5. **권한·세션**: 현재 단일 사용자 로컬 앱 전제 유지. 공개 웹 배포 또는 LAN 열기는 완전히 다른 보안 모델(인증·사용자별 자료 격리·HTTPS·속도 제한·권한)이 필요하므로 기본 기능으로 열지 말 것. 토큰 노출·로그·Origin/Host 우회·DNS rebinding·XSS와 HTML/CSV 출력 이스케이프 점검.
6. **삭제·보존 UX**: 자료 소스별 용량·마지막 사용 시점·의존 학습 결과를 표시. 캐시 삭제/연구 결과 삭제는 *사전 확인 후*, 원본 연구의 재현성이 없어질 수 있음을 알림. 자동 무단 삭제 금지. 보관 정책을 문서화.
7. **개인정보/라이선스**: 공개 MLB 선수명도 출처와 사용 조건을 준수; 향후 비공개 로스터/사용자 파일에는 별도 접근·보존 정책 필요. 사용 조건이 허락하지 않는 재배포 금지. Retrosheet 저작권 고지 보존.
8. **무결성과 재현**: 다운로드 파일 해시, 원본 버전, 정제·모델 버전, 학습 설정, 코드 커밋과 dirty 여부, 난수 설정을 보존. 데이터·모델 버전이 달라지면 무음 재사용 금지. 실험이 다른 데이터로 돌아가면 이를 화면에 표시.
9. **연구 안전장치**: 원본 관측/통계적 추정/가상 플레이/검증되지 않은 가정/테스트 입력은 화면·저장 파일 모두 명확히 분리. 가짜 데이터가 실제 학습 결과로 섞이는 것을 테스트로 차단.
10. **보안 점검표**: 외부 연결 실패, 데이터 변조, ZIP 경로 이탈, malformed CSV, 로그에 절대 경로·토큰·사용자 파일명 출력, HTML 삽입, 잘못된 report path, 멀티 탭 작업 중복, 실수로 개발 모드 공개 등이 어떤 테스트로 방어되는지 체크리스트를 제출.

### 사용자에게 보여 줄 데이터 관리 화면
`자료명 / 출처 / 시즌 / 실제 사용 범위 / 원본·정제 상태 / 검증 상태 / 저장 공간 / 외부 전송 여부 / 삭제·보관 정책 / 이용 허용 범위`를 쉬운 문장으로. 민감 정보가 없으면 '기본 로컬 보관'이라고 안내; **암호화 또는 절대 안전**을 확인 없이 주장하지 말 것.

## 6. 데이터 다양화와 연구의 사실성 (기존 목표 유지)

- 현재 확보됐다고 보고된 Retrosheet 2023/2024의 플레이별 데이터로 가능한 건 주자/아웃/득점 전이 관찰이다. **이것만으로 타자 개인의 타격·투수의 구종·코스·구속을 재현하지 말 것**.
- 현재 Match-A의 본격적인 연구를 열려면 정당하게 이용할 수 있는 투구 단위 데이터, 구종/위치/카운트/결과 정규화, 사전 의사결정 신호와 사후 기록 구분, 행동별 반사실 추정 타당성이 필요하다.
- 여러 시즌을 개별 평가하고 다년간 실험을 준비하되 연도별 데이터 정의·규칙·선수/구장 편중을 확인할 것. 2023/24 검증만으로 모든 연대/리그에 통한다고 하지 말 것.
- **AI는 인간의 선택을 정답으로 암기하지 않는다.** 실제 자료는 현실적인 확률/제약/평가에 쓰고, 상대를 이길 전략은 경쟁 학습으로 찾는다.
- 사람이 하지 않은 행동의 결과는 기록만으로 확정되지 않는다. 선택 편향, 미관측 변수, 실험 조건 변경의 한계를 유지한다.

## 7. 개발 순서 — UI부터 손대되 연구 엔진은 보존

### 단계 1: 말과 화면을 먼저 고친다 (이번 작업에서 반드시 종료)
- 기존 screenshot을 기준으로 사용자 작업 흐름을 검토: 홈 → 시뮬레이션 → Match-B 학습 → 결과·리플레이 → 자료 확인.
- 용어 사전·화면별 제목·설명 교체, 50% 우세 판정 및 그 관련 단위테스트 재검토.
- `/simulation`에 2D 야구장·상황/턴/플레이 변화 중심 화면 구현. 데이터에 없는 가짜 애니메이션 금지.
- Match 결과에 상황별 선택 변화와 학습 단계 비교(시각화) 전면 배치. 기존 JSON/체크포인트 그대로 읽도록.
- 사용자가 첫 화면만 보고 **뭐가 가능한지 / 현재 어떤 목표로 학습하는지 / 실제 자료인지** 설명할 수 있어야 한다.

### 단계 2: 보안·자료관리·데이터 다양화의 기본 도구
- 현재 코드·로컬 데이터 보관·Git/서버/입력 경로를 실제로 감사해서 `docs/security-audit.md`에 **확인/미확인/조치** 목록 작성. 위 10개 항목의 P0 보호 조치부터 구현하고 회귀 테스트.
- `/lab/data`를 정적인 설명이 아니라 실제 저장 자료/사용 상태 대시보드로 확장. 원본 복원/보관/삭제 UX와 저작권·사용 조건 명시.
- 2023/24 다년 연구 확장 가능성은 데이터 정의·지원 행동·관측 공간과 독립 평가를 우선 점검. 데이터가 없거나 재사용이 금지되면 사용자에게 이유 표시.

### 단계 3: 실제 연구 가치 높이기
- Match-B는 R1의 한계(현재 아웃·주자와 번트/고의볼넷만)가 결과의 대부분을 좌우하지 않는지 통제 실험.
- Match-A는 자료·합리적인 결과 모델의 검증이 가능해질 때 실제 투구 단위 연구로 진행.
- 팀 승리 실험으로 확장할 때 점수 차·이닝·상대 팀·주루/수비 등을 실제 근거와 함께 단계적으로 추가.
- 다양한 시즌/상대/체크포인트 교차 대결과 실제 인간 전략 비교를 **같은 조건**에서 수행.

**단계 1을 완료하기 전에는 포장용 추가 차트, AI 이름 붙이기, 근거 없는 전략 발견 스토리 생성, 구종/물리효과 가짜 구현으로 흐르지 말 것.**

- [ ] 모바일/데스크톱 실제 브라우저 화면, 이전/다음/자동 재생/학습 시작/중지/결과 열기/자료 관리 링크를 클릭 검증. 콘솔 오류·반응형 줄바꿈·키보드 조작·화면 읽기 기본 체크.
- [ ] 보고서에 최소 3장의 새 캡처 저장: 첫 화면 / 경기 관람 / AI 전략 진화. **숫자 화면만 세 장 저장하지 말 것**.

## 9. Codex에 이 문서와 함께 넣는 시작 프롬프트

> `BaseballLab_Project_Compass.md`를 프로젝트의 방향 문서로, 이 `BaseballLab_Codex_UX_Security_Execution_Plan.md`를 이번 작업의 실행 명세로 적용해 줘. `4cb9895` 이후 변경된 커밋이 있다면 먼저 main을 최신화하고 diff를 읽어라. 기존 실제 2024 연구와 2023 외부 검증, 체크포인트·문서·테스트를 보존하라. 이번에는 **보고서의 내부 용어만 교체하고 종료하지 말고**, 홈/경기 관람/AI 학습 변화의 실제 화면을 일반 사용자가 이해할 수 있도록 고쳐라. `수비 우세 53.1%` 판정의 50% 기준이 비대칭 1점 성공 게임에서 정말 타당한지 검토하고, 타당성 없으면 '우열' 대신 측정된 결과로 교체하라. 자료는 원본·가상 장면·정책을 명확히 구분한다. 로컬 데이터 저장·웹 엔드포인트·배포/저작권·Git 추적/보안 위협도 실제 코드 기준으로 감사하고 필요한 테스트를 추가하라. 실제 브라우저/전체 테스트를 직접 실행해 결과와 캡처를 남겨라. 기능을 모조리 한꺼번에 개발하기보다 우선 **단계 1과 필수 보안 P0**을 확실히 완료하고 단계 2/3의 남은 일을 분명히 정리해 줘.
