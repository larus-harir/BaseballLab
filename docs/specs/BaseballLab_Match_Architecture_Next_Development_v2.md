## 1. 사용자 의도: 다시 정확히 이해하기

사용자는 그저 야구 AI와 사람이 하는 야구를 흉내 내거나 통계를 보여 주는 서비스를 원하는 것이 아니다. 야구라는 게임에 대해 **규칙·허용된 행동·실제 경기·선수/환경 능력 및 제약을 가능한 한 폭넓게 반영한 연구 환경**을 주고, 타격 측과 투구/수비 측의 AI가 **사람이 미리 지정한 좋은 전략 없이**, 상대를 이길 방법을 자율적으로 배우며 서로 적응하는 전 과정을 관찰하고 싶어 한다. 그 후 AI의 전략이 실제 MLB/KBO와 시대별 인간 야구의 전략에 얼마나 가깝거나 다른지, 차이가 왜 발생했는지 신중하게 비교하고 싶다.

'모든 정보를 AI에게 알려준다'는 뜻은 모든 미래 사건이나 상대의 비공개 행동을 순간마다 보여 주는 전지적 AI가 아니다. 다음 세 층을 **반드시 구분**한다.

1. **환경이 사용하는 지식:** 야구 규칙, 실측 데이터, 물리·능력 제약, 결과 추정 모델, 불확실성. AI가 학습할 *세계의 구성*에 해당한다.
2. **의사결정 시 AI가 실제로 관측하는 정보:** 현 상황에서 해당 역할의 선수/코치가 알 수 있는 공개·허용 정보. 투구 전의 실제 결과, 숨겨진 현재 구종/코스, 테스트 데이터의 정답은 누설하지 않는다.
3. **연구자가 사후에 보는 기록:** 실제 출처, AI 선택 확률, 상대 적응, 경기 결과, 모델 오차, 미검증 가정과 실험의 한계.

'수단을 가리지 않고 승리한다'는 표현은 **야구 규칙과 현실적 능력 안의 지원되는 모든 합법적 선택을 자유롭게 탐색**한다는 의미다. 규칙 위반, 정보 누수, 무제한 능력, 시뮬레이터 버그 악용까지 성과로 인정하라는 뜻이 아니다.

3. 타격 측·투구 측 신경망이 가중치를 갱신하고, 3개 seed, 체크포인트, 고정/과거 상대 평가, 교차대결, 웹 리플레이가 추가되었다.
4. 처음의 출루 대리보상에서 발전해 **주자/아웃 상황별 3아웃 전 1점 이상 득점 성공 vs 이를 막기** 실험(R1)이 생겼다.
5. 저장소 보고서상 투구/수비 측은 고의볼넷을 줄여 성능을 개선했으나 **타격 측 개선은 입증되지 않았다**. 이 역시 연구 결과로 정직하게 보존한다.
6. R1은 투구 결과나 컨택/파워·구속·선수 능력치를 임의로 만든다고 주장하지 않는다. 관측 이벤트 재추출·한계 표시를 유지한다.

## 3. 부모 프로젝트: BaseballLab

### 목적

앞으로 MLB/KBO, 시대별, 규칙 변화, 선수 능력, Match 실험을 **동일한 실험 기반 위에서 비교**할 수 있도록 공통의 데이터·규칙·엔진·학습·시각화 서비스를 제공한다. 부모 프로젝트 그 자체에서도 **사람이 웹에서 실제 자료 기반 야구 시뮬레이션을 실행하고 확인하는 경험**이 필요하다.

### 책임

- 실제 자료 제공자 연결 / 라이선스·출처·버전 / 정규화·결측·표본 편향·품질 검사
- 야구 상태, 규칙, 이벤트 전이, 점수·아웃·주자·승패의 공통 정의와 불변조건
- 실측에 기반한 전이·확률·물리 및 규칙 모델과 그 불확실성 관리
- 역할별 에이전트 관측/행동/정보 접근 계약, 학습기 및 체크포인트 인터페이스
- 시뮬레이션 세션·실험·평가·재생·데이터 계보 공통 기록
- 웹의 공통 탐색/시뮬레이션/자료 설명/시각화 모듈
- 리그·시대·규칙·데이터셋·모델의 **교체 가능한 버전 계약**

### 부모 웹의 사용 경험 — 구현 기준

- **야구 시뮬레이션:** 지원되는 경기 단위/역할/규칙을 선택하고 실행·일시정지·한 장면씩 진행. 누가 AI인지, 고정 정책인지 표시.
- **시각적 관찰:** 스코어보드, 이닝·아웃·주자 다이아몬드, 상태 변화, 플레이 로그, 실행 seed/모델 출처를 보여 준다. 투구 좌표가 있는 실제 자료 모델에서만 스트라이크존/투구 분포를 표시한다.
- **데이터 연구실:** 출처, 시즌, MLB/KBO 지원 범위, 관측값·모델 추정·가상 사건·미검증 가정의 구분.
- **실험 허브:** Match 등 자식 연구를 열고 실행할 수 있다.

부모가 9이닝의 모든 야구 행동을 실제 근거로 구현했다고 주장할 수 없으면, **현재 지원되는 경기 범위**를 분명히 보여 준다. R1 한 점 득점 게임을 '완전한 야구'로 이름 붙이지 않는다.

## 4. 자식 프로젝트: BaseballLab-Match

### 정체성

**승리를 향한 자율 전략 진화 실험실.** 부모 엔진을 이용하지만 연구 목표·행동 공간·보상·상대 정책 풀·전략 변화 대시보드·평가를 Match가 소유한다. 앞으로 별도 자식 실험이 늘어도 Match만의 임시 규칙을 부모에 섞지 않는다.

### Match-A — 타자 vs 투수 단위 학습

질문: 실제 타자와 투수가 상대를 이기려고 반복 학습하면, 카운트·구종·코스·타격 판단 등의 **상황별 정책이 어떻게 발전하는가?**

- 관측: 사전 카운트, 선수의 알려진 상대 정보와 이전 투구 이력 등 **실제 사전 접근 가능한** 정보 중 검증된 범위.
- 행동: 구종·목표 코스 / 스윙·기다리기에서 시작. 이후 자료와 결과 모델이 허용하면 컨택·파워 의도·번트 등 확장.
- 결과: 실제 투구 단위 자료와 검증된 규칙·추정 모델. 관측 위치를 의도한 코스로 착각하지 않고, 명령한 코스의 반사실 효과를 알고 있다고 단정하지 않는다.
- 보상: 초반 타석 승부의 성과를 **명확한 대리목표**로 정의할 수 있다. 단, 이를 팀 승리와 동일시하지 않으며 장타/득점 맥락이 없으면 승리 전략이라는 표현을 제한한다.
- 필수 관찰: 행동 분포·상대 대응·시점별 정책·구버전 교차대결·원천/모델 검증.
- 현재 R0은 **재검토·재사용 후보**다. 데이터 연결이나 반사실 타당성이 확인되지 않으면 완성으로 처리하지 않는다.

### Match-B — 팀의 경기 승리 단위 학습

질문: 타자·투수·주루·수비·타순·교체 등 팀 차원의 선택이 경기 승패에 어떤 영향을 주고 AI가 어떤 전술을 찾는가?

- 상태: 경기 점수/이닝/아웃/주자, 선수 라인업/교체, 상황별 제한 등 실제로 필요한 맥락.
- 행동: 먼저 **실제 근거가 있는 팀 측 전술**부터 지원. 이후 주루·번트·수비 위치·투수 교체 등 검증 근거와 함께 확장.
- 보상: 최종적으로 경기 승/패. 득점률이나 한 점 획득은 연구 단계의 명시된 중간 목표일 뿐.
- 현재 `E01-R1`은 **Match-B의 제한된 전구 실험(3아웃 전 1득점)**으로 보존한다. 완전한 팀 승리 게임이 아니다.
- 전제: 야구는 매 턴 무작위로 리셋되는 경기만이 아니다. 상태·능력·선수·라인업과 전이 간 의존성을 현실적으로 모델링해야 한다.

### E02 등의 후속 확장

MLB 학습 AI와 KBO 학습 AI의 대결은 부모의 공통 규칙·데이터/선수능력 어댑터·정책 호환성 기능을 사용해 **정책 차이, 선수 수준 차이, 리그 규칙과 환경 차이**를 따로 비교한다. 리그에 없는 자료를 다른 리그의 데이터로 채워 동급으로 표시하지 않는다. 역사 대결·규칙 변화 실험도 같은 원칙이다.

```text
│   └── match/                 # BaseballLab-Match의 연구 질문·한계
└── tests/
```

위 경로는 **권장 목적 구조**, 현재 실제 디렉터리가 아니다. 기존 `src/baseball_lab/r1/`, R0, 웹 진입점 및 저장 결과를 확인한 뒤 안전하게 점진 이관하라. 임의 대규모 일괄 리네이밍은 금지. 기존 CLI/웹 경로와 checkpoint/결과의 버전 호환을 유지하거나 명시적 이전 도구·경고를 제공한다.

권장 웹 구성:
- `/` 또는 `/lab`: BaseballLab — 실제 자료/엔진/시뮬레이터/자식 실험 목록
- `/match`: BaseballLab-Match — 연구 목적과 진행 상태
- `/match/at-bat`: Match-A — 투구·타석 승부 진화
- `/match/team`: Match-B — 득점 상황 R1 및 팀 승리 진화

라우팅 방식은 현재 로컬 웹 서버와 맞추되 URL 자체보다 **사용자가 두 프로젝트와 각 실험을 구분할 수 있는 것**이 우선이다. 서버를 하나 더 만들 필요는 없다.

## 6. 실제 자료 다양화 — 반드시 설계하되 무책임하게 확대하지 말 것

야구 전체에 관한 정보를 다룰수록 단일 2024 MLB 정규시즌은 충분한 일반화 근거가 되지 않는다. **하지만 방금 완성된 2024 R1을 폐기하지는 않는다.**

- 공급자별로 원본·수집 방식·사용 조건·시즌·리그·선수·팀·측정 정의·결측·품질·버전을 식별한다.
- Retrosheet의 **여러 시즌**을 활용할 수 있도록 2024 하드코딩과 ZIP 해시 상수를 공급자별·연도별 검증 메타데이터로 일반화한다. 해시 검증을 끄거나 임의 값을 통과시키지 않는다.
- 시즌별 독립 실험, 다년간 학습, 시기/팀/선수 분리 평가를 지원한다. 동일 게임·동일 원본 이벤트가 학습/최종 평가에 누수되지 않아야 한다.
- 규칙과 공·경기 환경 변화, 구종 추적 데이터 정의 변화, 선수 구성과 구장 차이를 기록하고 비교 조건을 맞춘다.
- **투구 단위** 연구에는 Retrosheet 플레이별 요약만으로 확인할 수 없는 구종·구속·실제 코스 등 정보를 요구하며 Statcast 등 합법적으로 이용 가능한 제공원을 별도 조사한다. 부족한 데이터는 '모름/미지원'으로 두고 꾸며 넣지 않는다.
- KBO 데이터 제공 수준·이용 조건·구종/투구 추적 가용성은 별도 검증할 것. 아직 확보하지 못한 수준을 확보했다고 표시하지 않는다.
- 관측된 인간 전략과 AI가 다른 행동을 선택했을 때의 결과는 동일하지 않을 수 있다. **선택 편향·반사실 식별의 한계**를 결과 화면과 연구 문서에 보존한다.

**데이터 다양화의 목표는 인간이 한 행동을 AI에 정답으로 복사하는 게 아니라, AI가 현실적인 야구의 폭넓은 선택을 시도할 수 있는 검증된 환경의 범위를 넓히는 것**이다.

## 7. 개발 우선순위 — 다음 세 작업만 먼저 완성

### 1차 — 두 프로젝트의 경계 + 현재 R1 사용 경험 고정

1. 현재 부모의 공유 부분과 Match 전용 부분을 코드 경로/책임 표로 감사한다. 실제 구현 / 부분 구현 / 미지원 / 테스트 전용을 구분한다.
2. 부모와 Match의 독립적인 메인 화면·메뉴·문서를 만든다. R1을 **Match-B의 '한 점 득점 실험'**으로 명확히 표기한다.
3. 기존 2024 공식 데이터 자동 준비 → R1 AI 학습 → 두 정책 변화 → 리플레이 → 고정/구버전 성적 비교가 **리팩터링 후에도** 유지되도록 검증한다.
4. 부모에는 실제로 지원되는 한도에서 **독립적으로 실행 가능한 시뮬레이션 관찰** 화면을 만든다. 최소한 R1의 공통 이벤트·이닝/아웃·주자 변화를 AI 학습 코드와 분리된 시뮬레이션 실행으로 관찰할 수 있어야 한다. 원천 이벤트 재생과 모델 생성 장면은 구분한다.
5. 기존 결과 리포트, 테스트, CLI, 데이터 출처 표기, 2024 R1 연구 보고서와 seed를 보존한다.

**1차 완료 기준:** 사용자가 웹에서 '야구 시뮬레이션'과 'AI 전략 진화 실험'의 목적이 다름을 확인하고 각각 열어볼 수 있으며, Match-B R1이 실제 자료로 다시 성공적으로 동작한다. 부모가 지원하지 않는 9이닝·투구 추적 기능은 없는 그대로 명확히 표시된다.

### 2차 — 데이터 다양화와 정확성 검증

1. 실제 이용 조건을 확인한 여러 Retrosheet 시즌을 등록하는 공급자 구조를 구현한다. 우선 2024+서로 다른 한 시즌으로 전기간 외부 평가를 수행한다. 이용 가능성과 자료 정확성 확인이 우선이며 특정 연도를 임의로 약속하지 않는다.
2. 연도별 독립 학습/교차 평가를 수행하고, 선수·팀/카운트·주자상황·행동 표본 편중을 차트로 보여 준다. R1에는 **카운트 정보가 정책 관측으로 포함돼 있지 않음**을 정직하게 표시한다.
3. 경험적 결과 분포 검사는 물론, 능력·선수·구장·상황이 생략될 때 생기는 효과와 번트 관측 선택 편향의 민감도 검사를 수행한다.
4. Match-A에 필요한 투구 단위 실제 자료의 확보/이용 범위와 행동-결과 모델 가정을 검토한다. 합법적 획득 경로가 없으면 지원 불가 근거와 대체 가능한 검증된 범위를 보고한다.

**2차 완료 기준:** 데이터 적용 가능한 시즌이 2개 이상이며 그 범위가 원본/스키마/출처로 검증된다. 독립 시즌 평가 결과와 한계를 UI·리포트에서 관찰할 수 있다. 단순 수집에 그치지 말 것.

### 3차 — Match-A 독립 연구 흐름과 팀 승리 확장 설계

1. 기존 R0 스윙/기다리기·구종 코드를 연구 질문에 맞게 감사하고, 가능한 실제 데이터로 **개별 투구/타석 승부에 대해 어떤 선택이 학습되는지** 최소 반복 실험을 구축한다. 데이터가 지원하지 않는 타격 의도·코스 선택을 가짜 확률로 열지 말 것.
2. R1과 Match-A의 상태·행동·목적·평가/시각화/데이터를 구별하고 공통 신경망·기록기는 재사용한다.
3. Match-B의 '실제 경기 승리'로 가기 위한 필요한 최소 게임 상태(점수 차·이닝/주루/교체/연장 등), 규칙/실측 전이, 보상, 실패 가능성을 설계하고 **근거가 있는 첫 세로 단면**만 추가한다. 9이닝 완성이나 투구 물리 엔진을 한 번에 만들지 말 것.
4. 학습 과정, 체크포인트 비교, 고정/과거 정책 상대, 인간 경기와의 비교 가능한 측정치를 Match-A/B 각각 지원한다.

**3차 완료 기준:** Match-A가 실제 자료·검증된 지원 범위에서 최소 1회 반복 학습 실행·정량 평가·시각적 변화 추적을 제공하거나, 미확보 데이터 때문에 막히는 정확한 지점과 합법적 대안을 제시한다. Match-B는 R1에서 전체 승리로 향하는 실제 구현 가능한 첫 확장 단계를 입증한다.

## 8. 평가 원칙과 '진화했다'의 조건

- 정책 파라미터가 바뀌었다는 사실만으로 강해졌다고 하지 않는다. 고정·과거·여러 상대에 대한 비교와 독립 기간 평가를 한다.
- 각 단계마다 실제 정책 행동확률·발생 횟수·상대 전략·성과·분산/구간·원본과 모델 버전을 기록한다.
- 동등 수준의 두 AI가 함께 진화하면 서로의 승률은 약 50%일 수 있다. 체크포인트별 교차 대결과 외부 기준선을 사용한다.
- 개선이 없거나 변동 방향이 seed마다 다르면 그대로 실패/불확실성으로 기록한다. 'AI 전략 발명'으로 서사화하지 않는다.
- 목표함수는 분리한다: **Match-A 타석 대리목표 ≠ Match-B 한 점 득점 ≠ Match-B 전체 경기 승률**.
- 인간 기록은 *환경 보정/검증과 사후 비교*에 쓰되 '인간이 택한 행동이 정답'이라는 행동 모방을 기본으로 하지 않는다.
- 데이터로 없는 반사실 결과를 실제 관찰 결과로 표시하지 않는다.
- 미래의 모든 전략/능력 분배/팀 운영을 지금부터 완성할 필요는 없다. 하지만 연구 축·인터페이스는 초기부터 구분한다.

## 9. Codex 작업 방식 지시 — 실행을 포함할 것

1. 이 문서를 읽고 `PROJECT_VISION.md` 및 최신 `docs/r1-research.md`를 우선시한다. 이전 보고서의 **'실제 학습 아직 없음'** 진단을 새 R1에 반복 적용하지 않는다.
2. 먼저 실제 경로에 근거해 부모/Match/Match-A/Match-B의 완료·부분·미완료 현황을 간단히 보고한다.
3. **1차 작업을 실제로 구현**하고 테스트·로컬 웹 확인·기존 R1 회귀 실행을 수행한다. 문서만 쓰고 끝내지 않는다. 테스트 자료와 실제 자료를 구별한다.
4. 그 다음 2차 작업을 가능한 범위에서 진행한다. 라이선스/자료 장애가 있으면 무단 스크래핑이나 임의 데이터로 우회하지 않는다.
5. 변경 파일·실행 방법·샘플을 포함한 실행 증거·남은 한계를 쉬운 한국어로 정리한다. 기존 데이터를 잃거나 결과 스키마가 깨질 위험이 있으면 마이그레이션/회귀 검증을 우선한다.
6. 저장소에 커밋·푸시할 수 있다면 프로젝트의 기존 워크플로대로 처리하되 성공 여부와 커밋 SHA를 확인한다. 사용자에게 완료되지 않은 기능을 완료라고 하지 않는다.
