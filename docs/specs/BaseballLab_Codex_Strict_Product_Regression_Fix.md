## 0. 먼저 읽어라: 현재 결과물에 대한 평가

지금까지 '사용자 친화적인 UI', '실행 결과를 이해할 수 있는 설명', '실제 대결 시뮬레이션'을 반복해서 요청했다. 그런데 최신 화면에도 여전히 다음 문제가 남아 있다.

1. **일반 대결 버튼을 다시 눌러도 난수 번호 41을 재사용하므로 똑같은 가상 대결이 생성된다.** 기본 경험으로는 부적절하다.
2. 사용자가 **100타석**을 실행해도 안내 패널은 **`25타석은 같은 조건의 독립 반복 25번입니다`**라고 말한다. 실제 상태와 맞지 않는 하드코딩 버그다.
3. **`100번의 가상 대결`**이라는 표현은 100타석의 독립 추첨인지 100경기인지 모호하다. 사용자가 잘못 이해하도록 만드는 표현이다.
4. **`기타 타석` / `그 밖의 결과`**처럼 사건의 의미를 숨기는 범주가 핵심 화면에 등장한다. 세부 분류 코드를 추가해 놓고도 사용자는 무엇이 일어났는지 즉시 알기 어렵다.
5. **`선수만 고르세요`, `기록은 자동으로 준비합니다`, `연구 범위를 먼저 확인하세요`, `지원하지 않습니다`** 류의 문구가 실제 기능보다 더 눈에 띈다. 개발 과정의 해명은 제품 카피가 아니다.
6. 결과 설명이 길고 반복적이다. `단정하지 않습니다`, `검증 전`, `한계`를 여러 군데 붙여 놓는다고 이해하기 쉬운 설명이 되는 것은 아니다.
7. 경기 결과와 통계 결과를 구분해야 하는 것은 맞지만, **구분을 구현하지 않은 채 제한 사항을 장문으로 보여주는 건 개발 완료가 아니다.**
8. 새로운 기능을 추가할 때 이전 요구사항을 놓치고 지나간다. 따라서 **회귀 확인과 제품 수용 기준을 통과하지 않으면 완료 선언을 금지한다.**

### 가장 중요한 메시지

**개발자에게 친절한 설명이 아니라, 일반 야구팬에게 친절한 경험을 만들어라.**

문장만 순화하지 마라. 비슷한 안내를 줄줄이 덧붙이지 마라. 화면에서 필요 없는 내용은 없애고, 결과의 해석에 꼭 필요한 내용만 적재적소에 보여라. 실제 기능·숫자·버튼 동작을 바로잡아야 한다.

## 2. 확인된 구현 문제 — 코드를 근거로 시정할 것

### A. 대결을 반복해도 같게 나오는 문제: P0 / 즉시 수정

**확인된 위치**

- `src/baseball_lab/web/matchup.html`
  - 기본 입력: `<input id="seed" ... value="41">`.
  - `calculate` 이벤트에서 `seed:Number($('seed').value)`를 매번 전송한다.
- `src/baseball_lab/matchup/models.py`
  - `simulate(model,n=25,seed=41,repetitions=200)`.
  - `rng=Random(seed)`로 개별 타석의 난수 시퀀스를 만든다.
  - 반복 실험에도 `Random(seed+100000+repeat)`을 사용한다.
- `src/baseball_lab/matchup/service.py`
  - 입력을 그대로 `simulate()`에 넘긴다.
  - 재현성 식별자는 선수·모델·실험 횟수·난수 번호에 의존한다.

따라서 **같은 선수/확률 모델/타석 수/seed를 반복 실행하면 같은 사건 시퀀스가 나오는 것이 코드의 현재 동작**이다. 이는 수학적으로 오류가 아니라 **일반 실행 UX의 설계 오류**다.

#### 반드시 이렇게 고쳐라

- 일반 사용자 기본 동작은 `새 대결`이다. 버튼을 누를 때마다 **새 난수 번호**를 생성해 실행한다.
- 이전 결과를 저장해서 다시 열거나 `같은 대결 재현`을 선택한 경우에만 기존 seed를 재사용한다.
- 재현 번호는 고급/실험용 정보에 두고 초기값 41을 사용자 기본값으로 사용하지 않는다.
- **확률 분포**는 같은 선수·동일 모델·동일 데이터라면 그대로여야 한다. **실제로 추첨된 사건**은 매 실행마다 별도 표본이다.
- 새로운 seed를 사용해도 우연히 동일한 합계가 나올 수 있으므로 `실행할 때마다 안타 수가 반드시 달라야 한다`는 식으로 조작하지 마라. 핵심은 **매번 독립된 난수 흐름을 사용**하는 것이다.
- 저장 실행의 식별자와 연구의 **재현성 지문**을 구분하라. 동일 설정을 명시적으로 재현한 경우 계산 결과는 같아도 실행 이력은 구분해 저장할 수 있어야 한다.
- 난수는 서버에서 안전하게 생성하거나, 프런트와 서버가 일관되게 생성·전달하도록 설계하라. 중복 클릭·새로고침·동시 요청·저장된 보고서 재열기도 검증한다.

#### 최소 자동 테스트

1. 같은 설정으로 기본 `대결 시작`을 3회 클릭 → 저장된 seed가 서로 다름.
2. 세 실행의 모델 확률은 완전히 같음(같은 데이터/모델 기준).
3. 같은 seed로 `재현`을 2회 수행 → **타석별 사건 배열까지 정확히 일치**.
4. 고정 시험 분포로 서로 다른 seed를 대조 → 사건 배열이 정상적으로 달라질 수 있음을 확인.
5. 이전 실행을 열어도 당시 결과가 바뀌지 않음.
6. 우연히 합계가 같아도 테스트가 이를 실패로 간주하지 않음.

**검증 실험 참고:** GitHub 코드의 추첨 로직을 별도 재현하여 예시 확률·100타석에서 seed 41 재실행은 사건 시퀀스와 합계가 완전히 일치, 42/43에서는 달라짐을 확인했다. **해당 실험은 실제 김도영/안우진 전체 앱 실행이 아니므로, 실제 데이터로 E2E를 별도 실행하라.**

### B. 25타석 하드코딩: P0 / 즉시 수정

**확인된 위치:** `src/baseball_lab/web/matchup.html`의 `aside#explanation > details`에 `25타석은 같은 조건의 독립 반복 25번입니다`라는 고정 문구가 있다. 반면 입력 `id="n"`은 1~10,000을 지원한다.

- **25, 100, 250타석으로 각각 실행**한 뒤 결과 제목·통계·표·리플레이·설명·저장 기록에 과거 숫자가 남지 않는지 확인하라.
- 설명에서 굳이 매번 `25타석이 9이닝은 아닙니다`라는 식의 장황한 안내를 반복하지 마라.
- 기본 결과 영역은 선택한 타석 수를 바인딩하고, 해당 시뮬레이션이 `개별 타석 반복`이라는 사실은 **표현 방식과 모드명으로 자연스럽게 이해**되게 하라.
- 값의 출처가 여러 파일에 흩어져 있지 않도록 단일 UI 상태/결과 모델에서 표시한다.
- `25타석`, `100타석`, `200회` 같은 숫자가 설명이나 컴포넌트에 고정되어 있는지 **전체 웹 파일·보고서·결과 템플릿을 검색해 전수 조사**하라. 단, 예시 문서·과거 연구 결과의 역사적 숫자는 임의 변경하지 말 것.

### C. `기타 타석` / `그 밖의 결과`: P0 / 의미가 보이도록 수정

**확인된 코드:**

- `simulation/contracts.py`는 8개 사건 `strikeout/walk/hbp/single/double/triple/home_run/other`를 사용한다.
- `matchup/models.py`의 확률 모델은 아직 이 8개 사건 기준이다.
- 신규 `matchup/outcome_details.py`는 MLB 실제 플레이 기록에서 아웃 종류·희생타·실책·야수선택 등으로 `other`를 **표시용 추가 분류**한다.
- `matchup/reading.py`는 세부 분포가 있을 때 상세 항목을 표로 만들어 표시한다.
- KBO 과제 기록에는 같은 수준의 타석별 결과가 없어 상세 분류를 동일하게 재현할 수 없다.

#### 반드시 할 일

1. `other`의 **수학적 정의**, 표본 수, 구체적인 포함 사건을 데이터 공급원별로 직접 감사하라.
2. MLB에서 세부 결과를 확실히 알 수 있는 경우에는 그래프와 리플레이의 **주요 항목에 땅볼 아웃, 뜬공 아웃, 병살, 희생타, 실책 출루, 야수선택 등을 실질적으로 보여라.** 단, 서로 겹치는 사건의 중복 집계를 막아라.
3. 현재 관측 비율을 이용한 2차 추첨은 **정밀한 독립 예측 모델이 아니라는 점**을 내부 데이터 계약과 결과 근거에 남겨라. 표현만 '확정된 실제 아웃'으로 바꾸지 말 것.
4. KBO 시즌 합계만으로 아웃 종류가 구분되지 않으면, **없는 값을 꾸며 만들지 말 것.** 이 경우 `그 밖의 타석 결과(세부 기록 없음)`처럼 범위가 드러나는 최소 표기를 사용하되 1차 결과의 큰 카드에 불명확한 수치만 올리지 마라.
5. KBO 기록에서 구분 가능한 삼진·볼넷·사구·안타/장타, 그리고 확실한 잔여 집계만 보여라. 미기록 항목은 `0`이 아니라 `기록 없음`으로 취급한다.
6. `그 밖의 결과`가 40~50%인 그래프가 나왔다면 사용자가 무엇을 해석해야 하는지 분명하게 설명하거나, 세부 정보가 충분한 데이터에서는 이를 실제 사건별 차트로 교체하라.
7. 계산 모델 자체를 바꾸는 경우 MLB 2023/2024 홀드아웃 평가, KBO 원본 재현, 총합 100%, 사건 중복, 예전 결과를 함께 검증하라. **이름만 갈아 끼워서 해결한 척하지 마라.**

### D. 결과 용어와 계산 단위: P0 / 사용자가 오해하지 않게 수정

현재 화면의 `100번의 가상 대결`은 **100타석의 독립 추첨**이다. `1경기`도 아니고, `100경기`도 아니고, 9이닝 점수를 만든 것도 아니다. 이 구분을 숨기거나 과도하게 해명하지 말라.

- 통계 대결 모드명: **`타석 대결`** 등 정확하고 짧은 명칭.
- 결과 제목 예: **`김도영(2024) vs 안우진(2022) · 100타석`**.
- 결과 요약 예: **`100타석 결과: 17안타 · 26삼진 · 6볼넷`**.
- 예상과 실제 추첨을 구분해 `예상 안타 약 24개 / 이번 대결 17개` 형태로 간결하게 표시.
- `23.5%`는 **이 모델이 계산한 안타 확률**이지 해당 100타석에서 실제 발생한 안타율 17%와 동일하지 않다. 두 숫자에 각각 정확한 이름을 붙여라.
- `100타석 중 17안타`를 `타율 .170`으로 자동 변환하지 말 것. 볼넷·사구 등이 있으므로 PA와 AB가 다르다.
- **BaseballLab / EraMatch의 통계적 독립 타석**과 **Match의 AI 학습 시뮬레이션**을 같은 `대결`이라는 말만으로 섞어 쓰지 말라.
- 전체 9이닝 모드를 실제 구현·검증하기 전에는 타석 결과를 `최종 경기 점수`로 포장하지 말라. 반대로 9이닝 모드가 없다는 개발 보고를 화면 곳곳에 반복하지도 말라.
- 선수 이름·연도·모델·횟수·표기 지표는 항상 현재 선택과 실행 결과에서 파생한다.

### E. 데이터 원본의 어색한 필드: P1 / 사용자 문구에서 제거·정정

스크린샷의 선수 원본 영역에는 `사구 후보`, `실제 타수 미수록`, `타석/상대한 타자`처럼 개발 시 변환 과정에서 등장한 표현이 그대로 보인다.

- **실제 정의가 확인된 필드만** `타석`, `상대한 타자`, `타수`, `안타`, `삼진`, `볼넷`, `사구`, `2루타`, `3루타`, `홈런`으로 역할에 맞게 표기하라.
- 의미가 확실하지 않은 원천 필드(`HP`, `HBP`, `IB` 등)는 공식 데이터 사전·원본 과제 열 정의와 대조하고, 정체가 불분명하면 숫자를 확정된 `사구`로 표기하지 말라.
- `원본에 없음`과 `값이 0`을 구별한다.
- 원본 출처가 미확인인 KBO 기록은 내부·고급 상세에 상태를 두되, 첫 화면에 법적/기술적 장문으로 사용자를 압박하지 않는다.
- 이적 선수의 팀별 행·시즌 합산, 같은 이름 다른 선수, 분모 불일치, 리그·연도 혼합 오류를 별도 테스트한다.

## 3. UI/UX: 어색한 카피를 고치는 작업이 아니라 화면 자체를 다시 정리하라

### 하지 말아야 할 패턴

- 홈 카드 밑에 `선수만 고르세요`, `기록은 자동으로 준비합니다`, `이 컴퓨터에 보관합니다` 같은 **당연한 사용 절차 설명**을 반복해서 붙이기.
- 각 항목마다 `~가 아닙니다`, `~한계가 있습니다`, `~지원하지 않습니다`를 덧붙여 **한 화면을 사용설명서로 만들기**.
- `원본/개선 후보`, `표본 보정`, `연구 상태`, `외부 평가`, `재현 번호`처럼 **실무자용 단어를 첫 화면의 주인공으로 만들기**.
- `자세히 보기` 안에 또 `자세히 보기`를 중첩해, 실제 결과보다 메뉴 탐색이 많게 만들기.
- 사용자에게 선택하지 않은 기술 설정/자료 조달/검증 상태를 이해하도록 요구하기.
- '문구를 짧게 바꿨습니다' 한 줄로 UI 완료를 선언하기.

### 새로운 정보 우선순위

**첫 화면:** 세 프로젝트 이름 + 바로 실행할 동작. 부가적인 설명 문단 최소화.

**선수 선택:** 리그, 시즌, 타자, 투수, 타석 수, 대결 시작. 이미 갖춘 자료 준비 로직은 UI 뒤에서 동작. 실제 문제가 있을 때만 간결하게 오류와 재시도 제공.

**대결 결과:** 이름·연도·횟수 → 핵심 수치 → 사건별 시각화 → 타석별 장면 보기. 추가 설명과 통계 수식은 펼쳐지는 상세 영역에서 제공.

**전문 설명:** `이 확률은 어떻게 나왔나?`를 선택하면 현재 선수 기록과 Log5·보정 결과의 **실제 숫자**를 보여준다. 원론적인 문장만 늘어놓지 않는다.

**Match:** AI가 학습하면서 **어떤 선택을 언제 얼마나 바꿨고**, 성과가 실제로 달라졌는지를 시각적으로 보여준다. 제한 범위 경고가 첫 화면의 주 콘텐츠가 되어서는 안 된다.

### 문구·디자인의 구체적 품질 기준

- 버튼 하나에는 동작 하나만 담아 `대결 시작`, `다시 대결`, `이 결과 다시 보기`처럼 구별한다.
- 서술보다 **표·그래프·경기 장면·숫자**가 먼저 보인다.
- 한 문단은 특별한 사유가 없는 한 2문장을 넘기지 않는다. `한계/자료 조건`은 의미를 왜곡하지 않는 범위에서 한 번만 짧게 안내하고, 나머지는 고급 상세에 둔다.
- 차트에서 `예상`과 `이번 결과`를 색·범례·값으로 구분하고, 수치와 그래프가 같은 분모를 쓰는지 검증한다.
- 화면 390px에서도 줄바꿈·카드 높이·그래프 축·선택 입력이 깨지지 않아야 한다.
- 화면 읽기·키보드 접근성, 로딩·실패·빈 상태, 연타·취소·동시 클릭을 점검한다.
- 항목 제목을 바꾸면서 데이터 의미를 바꾸지 않는다. 불가능한 추정은 가능하다고 쓰지 않는다.

### 금지 문구 검사(사용자 화면 기준)

아래와 같은 문구는 기본 화면에서 **필요성과 맥락을 재검토해 제거 또는 대체**한다.

- `선수만 고르세요. 기록은 자동으로 준비합니다.`
- `지원하는 기록은 자동으로 준비하고 이 컴퓨터에 보관합니다.`
- `연구 범위를 먼저 확인하세요`
- `전체 9이닝·투구 추적은 미지원입니다`라는 반복 안내
- `그 밖의 결과`, `기타 타석`만 보이고 구성 설명이 없는 경우
- `25타석은 ...`처럼 실제 입력과 무관한 고정 숫자
- `100번의 가상 대결`처럼 실행 단위를 혼동시키는 표현
- `모델이 생성한`, `고정 기본정책`, `일반타석 / 정상 승부` 등 결과보다 구현 용어를 전면에 내세우는 표현

**주의:** 이 표현을 전역 문자열 바꾸기로 삭제해 기존 연구의 정확성까지 잃지 말라. 사용자 뷰와 연구 상세·기존 원본 기록을 분리하라.

## 4. Match: '개발 중'을 설명하는 페이지가 아니라 실제 AI 연구를 계속 만들어라

최신 HEAD에는 기존 R1(3아웃 전에 한 점)과 새로운 **3아웃까지 득점 누적** 학습 코드가 있다. 이것을 9이닝 전체 경기, 개별 공의 볼배합 학습 또는 인간 전략의 인과 비교를 이미 완성한 것처럼 포장하면 안 된다.

- 최신 `experiments/match/team_win/half_inning.py` 및 보고 화면의 **실제 실행·학습·상대 비교·리플레이가 동작하는지** 확인하라.
- Match 홈은 할 수 없는 일보다 **지금 실제로 할 수 있는 대결과 학습 실험**을 중심으로 구성하라.
- 학습 화면에는 `시작 → 학습 진행 → 전략 변화 → 과거 AI와 대결 → 결과 해석` 흐름이 실제로 연결돼야 한다.
- 기존 R1과 새로운 이닝 득점 실험의 규칙·목표·자료·결과는 분리해 표시한다.
- '언젠가 투구별 연구'라는 문구를 반복하는 대신, 실제 투구별 자료가 확보된 기능에 한해 다음 단계 구현을 진행하라. 없는 좌표/투수 능력을 지어내지 않는다.
- 사용자가 이미 요청한 핵심 목표인 **학습 단계별 우위 변화, 어떤 전략이 강화/약화됐는지, 인간 야구와의 비교**를 후속 작업 목록에서 잃지 말 것.
- 기능이 막히면 원인과 필요 작업을 개발 결과에 보고하고, 다른 메뉴의 장문 안내로 대신하지 말라.

### 반드시 추가할 자동화 검사

- `matchup.html` 및 Match 보고서의 텍스트에서 **선수명·연도·타석 수를 고정으로 작성한 부분**을 정적 검사하고, 실제 브라우저에서 25/100/250 변경에 대응하는 동적 테스트를 실행하라.
- 결과를 만들 때 `n == sum(counts.values()) == len(events)`가 유지되는지 검증하라.
- 모델 사건 분포 합계가 100%인지, 세부 분류로 확장한 사건별 확률·건수 합계도 일치하는지 검증하라.
- 테스트 데이터는 `MOCK_TEST_ONLY`를 사용하되, **실제 MLB/KBO 보관 자료를 이용한 통합 검증**과 섞어서 보고하지 마라.
- 웹 스크린샷을 자동 저장하고 **변경 전/후의 같은 화면**을 비교하라. 스크린샷만 찍고 읽어보지 않으면 안 된다.
- 브라우저 테스트는 고정 시드 결과 재현과 일반 모드의 신규 시드 발급을 모두 다룬다.
- 기존 테스트 숫자가 늘어도 사용자 불만이 해결되지 않으면 미완성으로 처리한다.

## 6. 실행 계획 — 확인 → 수정 → 제품 검증 → 회귀 → 보고

### 1단계: 1차 코드 감사(짧게)

- 시작 `git status` / HEAD / 관련 HTML·API·결과 렌더링 경로 확인.
- `seed=41`, `n=25`, `100번의 가상 대결`, `기타`, `그 밖`, `지원하지 않습니다` 등 전역 검색.
- 각 항목마다 **현재 화면에 실제로 왜 나타나는지, 어느 상태에서 바뀌지 않는지**를 한 줄로 기록.
- 이전 문서 수십 개를 다시 요약하지 마라. 최신 스키마·테스트·문제 파일만 읽는다.

### 2단계: 엔진/UX 실제 수정

우선순위 **P0: 신규 난수 → 동적 타석 수 → 명료한 분류·결과 의미 → 화면 재구성**. 이 네 가지를 먼저 완료하라.

### 3단계: Match 기능·UI 확인

기존 한 점 / 신규 3아웃 누적 득점 연구를 실제 클릭해 진입부터 결과까지 테스트하고, 학습 과정이 보이도록 사용자 화면을 고친다.

### 4단계: 전수 검사와 회귀

대결 화면뿐 아니라 홈, EraMatch, Match, 저장 보고서, 데이터 화면을 재방문한다. 기존 원본·데이터·체크포인트의 SHA256이 수정 전과 같은지 확인한다.

### 5단계: 결과 제출(짧지만 증거 있게)

아래만 보고하라.

1. **이전 문제 → 수정 내용 → 사용자가 체감하는 변화** (항목별 한 줄).
2. 실제 실행 화면 캡처: `25타석`, `100타석`, `같은 조건 새 대결 2회`, `같은 결과 재현`, `MLB 기타 분류`, `EraMatch`, `Match`.
3. `pytest` 결과와 실제 브라우저 시나리오의 성공/실패.
4. 실제 데이터를 사용해 확인한 것과 테스트 전용 모형만 검증한 것을 명확히 구분.
5. **아직 해결하지 못한 항목은 숨기지 말고 미완료로 표시**. 이유와 구체적 차단 요인을 적는다.

### 하위 에이전트와 토큰 사용

- 기본은 **메인 Codex 1개**가 작업한다.
- 독립적인 통계 검증이나 브라우저 QA에 꼭 필요할 때만 **하위 에이전트 최대 1개**를 호출한다.
- 작업마다 기획/데이터/UI/QA 에이전트를 일괄 실행하지 않는다.
- 하위 에이전트는 특정 파일 또는 특정 테스트만 맡고 **전체 저장소를 다시 읽지 않는다**.
- 보고서는 간결하되 실제 검증 증거를 생략하지 않는다.

## 7. 완료를 선언할 때 절대 해서는 안 될 말

다음과 같은 답변은 **기능 변경과 실제 사용자 검증 없이 단독으로 제출하면 불합격**이다.

- `사용자 친화적인 문구로 개선했습니다.`
- `연구 범위를 명확하게 안내하도록 수정했습니다.`
- `데이터가 없으면 안내를 표시합니다.`
- `테스트 000개가 통과했습니다.`
- `새로운 기능은 추후 진행하겠습니다.`

문구·안내·테스트는 개발의 일부일 뿐이다. **실제 대결이 매번 새롭게 실행되고, 선택한 타석 수에 맞는 결과가 보이고, 결과가 무슨 뜻인지 사용자가 이해할 수 있고, 이전 기능이 깨지지 않아야** 완료다.
