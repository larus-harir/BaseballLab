# Codex 최초 작업 프롬프트 — 부모 Baseball AI Lab + 자식 E01

첨부 `Baseball_AI_Lab_Master_Handoff.md` 전체를 읽고 그 문서를 프로젝트의 기준 명세서로 사용해 주세요. **기존 단독 `AI Baseball Evolution Lab` 기획에서 중요한 변경이 있습니다. 이 연구는 이제 하나의 실험 프로젝트가 아니라, 여러 야구 AI 연구를 추가할 수 있는 부모 플랫폼과 독립적인 자식 실험들로 구성됩니다.**

## 1. 연구 의도 (반드시 유지)

- 부모 `Baseball AI Lab`: 야구 규칙, 시뮬레이터, MLB/KBO 데이터, AI 정책, 학습, 평가, 실험 기록을 재사용하는 공통 연구 플랫폼.
- 첫 번째 자식 `E01 Batter vs Pitcher Evolution`: 타자 AI와 투수 AI가 야구 규칙·현실적 한계에서 **오직 승리**를 위해 학습·진화하고, 그 전략 변화와 실제 인간 야구의 역사/현재를 비교.
- 미래 자식 `E02 MLB vs KBO`: MLB와 KBO 데이터로 AI를 **각각 독립 학습한 뒤 공정한 공통 경기 환경에서 서로 대결**하고, 전략 차이와 환경/선수 능력 영향을 분리 분석.
- 미래에는 시대별 대결, 교타/장타/기교/구위 스타일 대회, 규칙 변화, 감독/주루/수비 정책 실험도 추가할 계획.
- 사용자에게 중요한 것은 AI가 기존 야구의 정답을 따라 하는 게 아니라 **경쟁 학습 끝에 어떤 새로운 전략으로 발전하는지 기록하고, 실제 인간의 야구와 비교하는 것**.

## 2. 가장 중요한 아키텍처 지침

1. 부모 공통 코드(`core`, `outcome`, `data`, `agents`, `training`, `evaluation`, `tracking`)와 자식 실험(`experiments/E01_...`, 후속 E02/...)을 분리한다.
2. 새로운 자식 실험은 공통 모듈을 재사용해야 하며 야구 규칙·경기 엔진을 복제하지 않는다.
3. MLB 리그명, 룰셋, 데이터 출처, 선수 분포를 엔진 로직에 하드코딩하지 않는다. `LeagueProfile`/`RuleSet`/`OutcomeModel`/`Policy`/`MatchSpec` 같은 **가벼운 계약과 설정 주입**으로 확장한다.
4. MLB AI vs KBO AI 교차 대결이 가능하도록 입력/행동 스키마 버전과 체크포인트 메타데이터(훈련 리그·룰셋·데이터 버전·seed)를 설계해 둔다. 비호환 정책 비교는 명확히 실패하게 한다.
5. KBO 고급 투구 단위 데이터가 MLB와 동일하게 공개된다고 가정하지 않는다. 수집 가능성과 사용 조건을 확인하기 전 KBO 학습을 구현하거나 실제 KBO 모델인 것처럼 표시하지 않는다.
6. 교차 리그 비교는 나중에 **동일 관측/행동 스키마·중립 평가 환경·동일 선수 능력·고정 상대·같은 평가 시드**와 리그별 평가 환경을 따로 활용한다. `정책 성능`과 `리그/선수 전력 차이`를 구분한다.
7. 단, 미래를 위해 추상화만 잔뜩 만들지 말고 M1에 필요한 만큼만 구현한다. `dataclass`, `Protocol`, 설정 파일과 단순 레지스트리 정도로 충분하다.

## 3. 절대 지켜야 할 연구 원칙

- 최종 목표는 **경기 승리**. 삼진·타율·OPS·초구 스트라이크·장타를 미리 정답이나 보상 목표로 강제하지 않는다.
- 실제 MLB/KBO 자료와 합성 확률, 현재 시뮬레이션 결과와 실제 야구의 근거를 분명히 분리한다.
- 타자가 미리 투수의 실제 구종/코스를 알고 행동하는 관측 누수를 방지한다.
- 불가능한 구속·제구/반칙·규칙 허점을 무한 보상으로 활용하지 않도록 현실 제약을 설계하되 향후 단계에서 차근차근 구현한다.
- 자기대결 승률 50%만으로 학습 정도를 판단하지 않고 베이스라인/과거 모델/다른 seed 상대를 통한 평가를 설계한다.
- 일반 노트북 CPU와 필요시 Colab을 전제로, 설치/실행이 간단하고 재현 가능하도록 한다.

## 4. 이번에 실제 구현할 범위: 부모 M0 + 자식 E01의 M1만

1. 기존 레포가 있다면 확인하고, 없으면 `baseball-ai-lab` 부모 구조 생성. `README.md`와 `docs/architecture.md`에 부모/자식 구분 및 확장 방법 설명.
2. 공통 `core`에 간이 볼/스트라이크·타석 상태 전이·합법 행동 처리를 구현하고, 실제 결과 확률은 별도 `outcome` 모델로 분리.
3. 최소한의 `LeagueProfile` 및 정책/룰셋/매치 명세 계약을 구축해 **E02가 추가되어도 엔진 재작성 없이** 새 데이터를 연결할 수 있게 한다. 필요하다면 현재는 `synthetic_demo` 프로파일로 실행.
4. 자식 `experiments/E01_batter_pitcher_evolution`을 만들고, 랜덤·적극·인내 타자 / 랜덤·스트라이크 우선·구종 혼합 투수의 기준선 조합을 실행.
5. `seed`, 대결 설정, 정책 종류, 결과, 스윙/기다리기/구종/초구 전략 선택 비율을 CSV 또는 JSON으로 기록.
6. `scripts/quickstart.py` 또는 동등한 명령 한 개로 동작, `pytest` 테스트(규칙·재현성·결과 확률·프로파일 교체).
7. E02의 README나 문서에 `MLB-trained vs KBO-trained` 실험 목적과 필요한 어댑터/평가 조건만 **설계 문서**로 남긴다. KBO 데이터 크롤링, 실제 리그 모델 훈련, RL 학습, 무거운 대시보드는 **이번 작업에서 제외**.
8. 실제 구동 확인 후 작동 명령·테스트 결과·샘플 출력·지금은 무엇이 합성 모델인지·다음 M2 개발 프롬프트를 보고.

## 5. 수락 기준

- 부모 구조가 있고 자식 E01이 독립적인 설정/실행/설명 문서로 존재한다.
- 공통 엔진을 E01이 호출하며 리그 교체를 위해 코드 복제가 필요하지 않다.
- E01은 seed 고정으로 재현 가능한 타석 시뮬레이션을 수행한다.
- 기술 부채가 적고 확장 포인트가 문서에 간단명료하게 정리돼 있다.
- `pytest` 통과 / 실행 결과 / 아직 학습하지 않았다는 명확한 표시.
- 새 자식 E02를 구현하기 위한 M2 계획과 데이터 입수상의 현실적 제약을 보고한다.
