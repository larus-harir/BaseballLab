## 0. 이 프로젝트를 한 문장으로

**야구의 실제 규칙과 현실 데이터를 바탕으로 실험 환경을 만들고, AI가 상대를 이기기 위해 자율적으로 경쟁하면서 어떤 야구 전략을 발전시키는지 사람이 경기처럼 관찰하고, 그 전략을 실제 인간 야구와 검증 가능하게 비교하는 연구 플랫폼.**

사용자가 궁금한 건 최종 승률 숫자 하나가 아니다.

> 인간이 오랫동안 발전시켜 온 야구를, 사람이 ‘좋은 전략’을 가르치지 않은 AI들이 **규칙 속에서 이기기 위해 경쟁하고 적응하며** 처음부터 다시 발전시킨다면 어떤 야구가 만들어질까? 인간 야구와 닮았을까, 다를까? 왜 그럴까?

**AI가 인간과 다른 기발한 전략을 찾아야만 성공하는 프로젝트는 아니다.** 인간과 비슷해져도, 전략이 순환해도, 성능 개선이 없어도 이유를 정직하게 기록·검증하면 연구 결과다.

## 1. 사용자에게 약속하는 경험 — 기술 기능 목록보다 우선

- **보이는 야구**: 아웃, 주자, 점수, 실제 지원되는 경기 선택을 2D 화면에서 이해하고 전후 장면을 볼 수 있다.
- **학습이 보이는 AI**: AI가 0회, 1,000회, 3,000회 뒤 같은 상황에서 어떻게 다르게 결정하는지 비교할 수 있다. 학습이 진행되는 '과정'이 주인공이다.
- **설명 가능한 결과**: 왜 어떤 결과가 나왔는지 *관찰한 사실, 모델의 선택, 검증된 근거, 불확실한 해석*을 구분할 수 있다.
- **한 번 실행하는 UX**: 가능한 데이터는 합법적·검증된 제공 경로로 자동 준비해 복잡한 CSV 처리·파이썬 명령을 일반 사용자에게 강요하지 않는다. 필요한 준비가 없다면 이유와 해결 방법을 보여준다.
- **신뢰할 수 있는 연구**: 임의 성공률·능력치·구속·물리 현상을 사실인 양 만들지 않으며, 자료 출처·품질·이용 조건·저장 위치·한계를 표시한다.
- **확장되는 실험실**: 타자/투수 전략, 팀 승리, MLB/KBO 학습 AI 교차 대결, 시대별 경기, 규칙 변경, 선수 능력 구성 등으로 확장한다.

### 사용자의 언어 기준

1차 화면은 **야구 팬이 읽는 문장**으로. 내부 개발 단어(`seed`, `policy`, `transition`, `donor`, `synthetic`, `checkpoint`, `baseline`, `R1`, `E01`)는 설명의 주인공이 아니다. 기능과 근거의 전문 정보는 펼쳐 보는 상세 화면/개발자 로그에 남긴다. 기술을 쉬운 말로 바꾸며 의미를 왜곡해서도 안 된다. `ordinary_turn`은 실제 선수의 개별 '스윙 선택'이 아니다.

## 2. 변하지 않는 연구 철학

### 2.1 AI에게 '야구를 전부 알려준다'의 정확한 뜻

**세 층을 혼동하지 않는다.**

| 구분 | 포함 | 포함하면 안 되는 것 |
|---|---|---|
| 게임 세계와 학습 환경 | 공식 규칙, 가능한 합법 행동, 현실 자료로 검증한 결과 모델, 선수의 현실적 제약, 상황 변화 | 출처 불명의 확률, 무한 능력, 사실과 다른 규칙 |
| 각 AI가 결정을 내릴 때 관측 | 그 역할의 선수·코치가 해당 시점에 합법적으로 알 수 있는 정보와 경기 이력 | 아직 던지지 않은 공의 실제 결과, 상대의 숨은 결정, 평가 데이터 정답 |
| 연구자가 나중에 확인 | 선택 확률, 경기 진행, 결과, 원천 자료, 불확실성, 행동 변화, 상대 적응 | 검증 없이 꾸며낸 원인 설명 |

AI는 **정해진 야구 규칙과 현실적으로 가능한 행동 안에서 자유롭게 탐색**한다. '무슨 수를 써서라도 이겨라'는 반칙·정보 누수·시뮬레이터 오류를 승리 수단으로 승인하라는 뜻이 아니다.

### 2.2 사람의 전략을 정답으로 주입하지 말 것

- `초구에는 스트라이크를 넣어라`, `볼넷이 좋다`, `번트가 좋다/나쁘다`를 정답으로 가르치지 않는다.
- 실제 인간의 전략·통계는 **현실적인 환경 보정/제약, 비교 기준선, 결과 해석**에 활용한다.
- 강화학습으로 행동 선택 확률이 변해도 성적 개선과 동일하지 않다. 선택 변화, 상대 변화, 성과 변화를 분리한다.
- 모델이 '기발한 전략'을 선택하면 먼저 환경의 결함/표본 편중/행동 정의 오류/보상 악용인지 검사한다.
- 결과가 설명 가능한 데이터와 통제 실험 없이 현실 최적 전략이라고 발표하지 않는다.

### 2.3 보상과 연구 질문을 섞지 않는다

- **Match-A의 초기 하위 실험**: 타석에서 출루하기/출루 저지하기처럼 제한된 목적을 연구할 수 있다. 단, '경기 승리'와 구별하고 장타·득점 맥락의 부재를 밝힌다.
- **Match-B의 현재 하위 실험**: 3아웃 전에 1점 이상 득점하기/저지하기. 출루 대리보상보다 승리 맥락에 가깝지만 **전체 경기 승패는 아니다**.
- **장기 목표**: 실제 경기와 연결된 점수·이닝·상대 팀을 갖춘 최종 경기 승패 보상. 타율·OPS·삼진·출루율은 성과 해석 지표이지 AI의 궁극적인 정답이 아니다.

## 3. 프로젝트의 명확한 구성

```text
BaseballLab — 부모: 야구 연구 공통 기반 + 웹 시뮬레이터
│
├─ 자료실: 실제 경기 기록, 출처/이용조건, 품질·보안·보관
├─ 야구 시뮬레이션: 실제 기록 관찰 / 실제 자료 기반 가상 상황
├─ 공통 엔진/상태/정책/평가/기록/2D 시각화
│
└─ BaseballLab-Match — 첫 자식: AI 전략 진화 연구
   ├─ Match-A: 타자 vs 투수 (타석·투구 판단을 위한 연구)
   │   └─ 과거 R0: 출루 기준 스윙/기다리기·구종 선택 경로
   │      → 실제 투구 자료 연결·모델 검증 후 연구 가능
   ├─ Match-B: 팀이 득점하고 승리하는 전략 연구
   │   ├─ 현재 R1: '3아웃 전에 1점 득점/저지' 제한된 실험
   │   └─ 미래: 실제 근거에 맞춰 이닝·득점차·주루·전체 경기 승패 확대
   └─ 공통 연구 관찰: 학습 시점·대결·인간 야구 비교

장래 자식 연구 후보:
- MLB 데이터 학습 AI vs KBO 데이터 학습 AI
- 시대별 야구 학습·재현/규칙 차이 실험
- 선수 유형/능력 구성의 유리함을 탐구하는 실험
- 규칙 변경에 따른 전략 변화 실험
```

**저장소를 지금 별개 GitHub 프로젝트로 나눌 필요는 없다.** 내부에 책임·사용자 메뉴·연구 기록을 분리하고 나중에 독립 가능하도록 공통 플랫폼 → Match 의존성만 허용한다. Match 고유 보상·해석을 부모 엔진에 강제하지 않는다.

### 부모 BaseballLab의 합격 기준
- 자식 AI 학습을 시작하지 않고도 야구 시뮬레이션/원본 장면 관찰을 실행한다.
- 시뮬레이터의 **지원 범위**와 **데이터/모델 출처**가 명확하다.
- 규칙·데이터·실행과 재현 기능이 공통 모듈로 제공되어 다음 연구가 재사용한다.
- 사용자가 데이터를 관리하고 원본·모델·연구결과의 보관/보안 상태를 이해한다.
- 9이닝·구종·타구 궤적 등 현재 없는 기능을 제공하는 것처럼 표시하지 않는다.

### 자식 Match의 합격 기준
- 실제로 **서로 상대를 바꾸며 학습하는** 둘 이상의 정책이 있다.
- AI가 어떤 상황에서 어떤 행동을 선택할 수 있는지 명확하다. 선택 결과의 실제 근거/가정이 구별된다.
- 훈련 체크포인트, 변한 정책, 고정 상대·과거 버전 평가, 여러 반복, 인과/선택편향 한계가 관찰된다.
- 사람이 경기처럼 리플레이하며 전략 변화를 이해할 수 있다.
- Match-A와 Match-B의 보상·행동·데이터·완료 상태를 혼동하지 않는다.

## 4. 지금까지의 흐름 — 왜 뒤죽박죽처럼 느껴졌는가

| 단계 | 사용자 의도·요구 | 진행·교훈 |
|---|---|---|
| 최초 호기심 | AI가 승리만을 위해 경쟁하면 야구 전략이 인간과 어떻게 달라질까? | 단순 시뮬레이터·통계가 아니라 *진화의 연구*가 본질 |
| 부모-자식 전환 | E01 외에도 KBO/MLB, 시대, 규칙 등 다른 실험을 추가하고 싶다 | BaseballLab 부모 + E01 자식 구조 도입 |
| 초기 구현 | 우선 작동 가능한 코드 | 고정/합성 확률 기반 관찰만으로는 실제 AI 학습 연구 아님을 발견 |
| 경쟁 학습 요구 | 배우고 서로 적응해야 한다 | 신경망 정책·체크포인트·상대 풀 추가 |
| 실제 데이터 우선 | 출처 없는 구속·능력·확률을 만들면 안 된다 | 합성 학습을 연구 결과에서 제외하고 실제 자료 진입·검증 추가 |
| 실용 UX | 수동 CSV/명령보다 웹에서 한 번 학습 시작 | 자동 준비 경로와 로컬 웹 실행실 추가. 처음에는 데이터 제공 연결이 부족했음 |
| 실제 연구 실행 | 처음부터 연구를 볼 수 있어야 한다 | Retrosheet 2024 실제 플레이 기록으로 R1(1점 득점) 실행. 2023 독립 시즌 평가 추가 |
| 부모·자식 분리 | 시뮬레이션과 Match 연구가 구분되어야 한다 | 최신 `4cb9895`에서 부모 관찰 화면·Match-A/B 메뉴 및 Match 보고서 분리 |
| **지금** | 용어가 난해하고 화면이 야구처럼 안 보인다. 데이터 보안이 걱정된다 | **일반 사용자 중심 UI·검증 가능한 해석·자료 보안/관리 체계**로 개선하는 단계 |

혼란의 원인은 **작동하는 코드 / 합당한 연구 / 실제 사용하기 좋은 제품**이라는 세 단계를 한꺼번에 '완성'이라고 불렀기 때문이다. 이제 매번 다른 기준으로 판단한다.

### 현재 실험 R1에서 실제로 하는 행동

- 공격 AI: **기록상 번트 시도가 포함된 플레이 묶음**과 번트가 관측되지 않은 일반 플레이 묶음 중 지원되는 선택.
- 수비 AI: **고의볼넷** 또는 **고의볼넷 없이 승부**.
- 관측: 해당 상황의 **아웃 수, 주자 위치**.
- 보상: **3아웃 전 1점 이상 득점 성공 또는 실패**. 출루 자체나 9이닝 승리를 보상하지 않음.
- 전이: 비슷한 실제 상황의 Retrosheet 관측 플레이 전이를 추출해 가상 게임 진행. 실제 선수의 그 순간 판단을 재현한 것은 아님.
- 학습: 두 신경망 정책이 반복 대결하며 가중치를 갱신. 모델의 미확인 인과 효과와 선택 편향은 남음.

이 수준에서 `AI 타자가 슬라이더를 노려 장타를 선택했다` 같은 서술은 불가능하다. R1은 **팀 측 선택의 작은 기초 연구**다.

### 현재 숫자에 대한 해석 안전장치

- 최신 문서는 R1 3,000상황씩 3회 학습으로 **가상 맞대결 중 공격 득점 704/1,500(46.9%)**, 보완 사건인 수비 저지 53.1%를 보고함. 이는 실제 야구 경기 승률이 아니다.
- 같은 변경 없는 상대에 대한 평가로 수비 저지 성적이 좋아졌다고 보고함. 공격 성적은 유의미한 개선이 확인되지 않았다고 보고함.
- **매우 중요한 해석 변경:** 이 게임은 서로 다른 역할과 임의의 동일 비중 24가지 시작상태가 있다. 50% 성공률은 자연적인 '공격/수비 힘의 균형' 기준이 아닐 수 있다. `46.9 대 53.1`이라는 숫자 차이만으로 수비 AI가 공격 AI보다 '잘한다'고 결론 내리는 기준을 재검토해야 한다. 사용자 첫 화면은 **관측 결과와 같은 상대 전후 개선** 중심으로 바꾼다.
- 2023년 평가는 2024 외부 조건 검증의 한 사례이지, 시대별 진화·MLB vs KBO를 완료했다는 뜻이 아니다.

## 6. 데이터 다양화: 왜 필요하고, 무엇을 제공하지 못하나

**2024년 한 시즌만으로 인간 야구 전체에 대해 결론을 내리지 않는다.** 하지만 첫 성공한 실험을 폐기하고 다년 전체를 먼저 수집할 필요도 없다.

| 범주 | 할 수 있는 일 | 확인·확장 필요 |
|---|---|---|
| Retrosheet 플레이별 기록 | 경기 흐름, 득점·아웃·주자·번트 관측 등 | 시즌별 데이터 정의, 선수·팀 편중, 행동 선택 편향 |
| 투구별 추적 기록(Statcast 등) | 확보·허용·검증 시 구종/구속/위치와 타자·투수 선택 분석 | 자동 사용 조건, 표본 정의, 사전/사후 관측 분리, 미선택 행동의 결과 |
| KBO 공식 기록 | 선수·시즌 등의 정보 참고 가능 | MLB와 같은 상세 데이터가 확보되는지·이용 조건 확인 필요 |
| 역사적 자료 | 시대별 규칙·전략 변화 비교 가능 | 시대별 지표 차이·측정 체계·사료의 빈틈 |

- **다양한 시즌을 섞으면 자동으로 편향이 사라지지 않는다.** 시즌별 독립 실험·외부 평가·선수/팀/구장 편중 검사와 결과 차이를 함께 보라.
- 실제 데이터는 AI에게 정답 전략을 가르치는 교과서가 아니라 **시뮬레이션의 현실적 조건과 결과를 보정하고 비교하는 근거**다.
- 정밀한 관측이 없는 행동은 '지원하지 않음'으로 두거나 명시한 가정·민감도 실험으로 취급한다.
- 공정한 MLB/KBO 교차 대결은 정책 차이와 전력 차이를 분리해야 하며 두 리그의 자료가 서로 다른 수준이면 곧바로 결론 낼 수 없다.

## 7. 보안과 신뢰성: 둘을 나눠 생각한다

### 실사용 자료 보호 (Security & Privacy)
- 현재는 단일 사용자 PC의 `127.0.0.1` 로컬 웹을 기본으로 둔다. 공개 온라인 배포가 되면 인증·권한·HTTPS·저장 정책을 새로 설계해야 한다.
- 원본·사용자 업로드·학습 모델·결과/로그를 범주별로 보관한다. 민감 데이터/계정 토큰/절대 경로가 Git이나 보고서에 노출되지 않도록 한다.
- 원본/가중치/캐시 데이터의 저장 위치, 접근 권한, 동기화·백업/보관·삭제 방법을 사용자에게 설명한다. 암호화 저장 여부는 검증하기 전까지 '지원'이라고 하지 않는다.
- 다운로드 URL·라이선스·해시·압축해제 및 업로드 파일 안전성을 검사한다.

### 실험 근거 보호 (Research Integrity)
- 실제 원본·모델 추정·시뮬레이션 결과·미검증 가정·테스트용 데이터 **절대 혼용 금지**.
- 자료/정규화/학습/평가 환경/코드/난수 번호를 기록해 반복 검증할 수 있게 한다.
- 데이터 수집의 합법성·라이선스·원본 수정 이력과, 동일 경기의 학습/최종 검증 누수 여부를 관리한다.
- 유의확률/구간·표본 수·선택 편향 등 연구 한계를 일반 사용자도 이해할 말로 전한다.

## 8. 앞으로의 개발 방향 — 핵심 목표를 계속 미루지 않기

### 지금 바로: 제품 이해 가능성/자료 보안 개선

- Codex 작업 기준은 **`BaseballLab_Codex_UX_Security_Execution_Plan.md`**. 홈, 부모 시뮬레이션 관람, Match의 전략 변화·기존 기록 활용, 자료 관리 화면을 실제 사용자가 알아볼 수 있게 바꾼다.
- 50% 우세 기준의 타당성부터 검토해 잘못된 결론 문구를 수정한다. 개발 용어만 바꾸는 표면 작업으로 종료하지 않는다.
- 저장 자료 보안·저작권·Git 노출 여부를 실제로 점검하며 자동 학습/기존 2024·2023 결과가 유지되는지 테스트한다.

### 다음: Match-A를 원래 질문에 더 가깝게

- 투구 단위 실제 자료의 합법적 확보 경로를 확인하고, 타자가 무엇을 볼 수 있었는지/투수가 무엇을 결정할 수 있었는지를 정의한다.
- 현실에서 가능한 투구/타격 행동과 결과의 관계를 검증하여 타자와 투수의 **개별 승부 전략이 변화하는 과정**을 보여 준다.
- 관측 인간 데이터의 선택 편향·사후 정보 누수 문제를 다루지 못하면 완성으로 부르지 않는다.

### 다음: Match-B를 실제 경기 승리로

- 현재 R1의 팀 측 제한된 선택에서 실제 경기 상태(이닝, 점수 차, 주자, 아웃, 제한된 주루/수비 등)를 검증된 근거로 확장한다.
- 최종적으로 **경기 승패 보상**에 도달하고 타순·교체·번트·수비·주루 등의 전략을 독립 평가한다.

### 장기 연구: 인간 야구와 비교하는 단계

- 동일 시대/동일 환경/동일 평가 조건에서 실제 인간의 관측 행동 분포와 AI가 배운 전략을 비교한다.
- 왜 다른지 조사할 때 선수 능력·측정 제한·규칙 차이·정책의 편향·결과 모델의 한계를 먼저 통제한다.
- MLB/KBO, 역사/시대, 규칙 변경과 선수 능력 구성은 **새로운 자식 연구**로 추가하고 부모를 재사용한다.

## 9. 개발 완료의 세 가지 서로 다른 정의

| 수준 | 의미 | 현재 상태 예시 |
|---|---|---|
| **코드가 돌아감** | 학습 실행/저장/웹 버튼/테스트 통과 | R1과 부모 관찰 일부 달성(개발 보고 기준) |
| **연구가 타당함** | 실제 자료와 검증 가능한 결과 모델, 반복 대결, 데이터 편향·선택 편향 검사 | R1 기초 검증만. 현실 최적화·인과효과 주장 불가 |
| **제품이 이해되고 쓸 만함** | 야구처럼 보이는 UI, 쉬운 용어, 상황별 AI 선택 변화, 자료/보안 설명 | 여전히 개선 필요 |

어떤 개발 완료 보고라도 이 세 가지를 구분해야 한다.

## 10. 다음 Codex 작업에서 지켜야 하는 규칙

1. **수정하기 전** 최신 커밋 확인, 기존 코드/화면/테스트·저장 결과 점검. 이미 작동하는 기능은 재사용한다.
2. **목표를 지키는 최소 변경부터**: 문서 작성만 하고 끝내지 말고 브라우저로 보이는 사용자 경험을 수정한다.
3. **세 가지 상태 표기**: 작동/검증 완료, 부분 구현, 미지원. 보안과 연구 결과도 같은 기준.
4. **데이터가 없는 일을 꾸며내지 말 것**: 3D 투구·선수 실력·구종·좌표·유의한 역사적 우월성 등.
5. **기존 실험 존중**: 과거 R1 데이터·체크포인트·Git 결과 JSON과 2023 다른 시즌 검증, 별도 Statcast R0 경로를 새 UI로 연결하되 무음 변경/덮어쓰기 금지.
6. **자동 경로 안전**: 공식 확인 제공자 외 임의 네트워크 접근·스크래핑/재배포로 자료 문제 해결하지 않는다.
7. **사용자 말부터**: 결론, 경기 장면, AI 선택 변화, 근거, 상세 로그 순서. `정책`/`전이`/`seed`가 첫 제목이 되면 다시 설계한다.
8. **보이는 결과 제출**: 실제 화면 캡처, 본인 환경에서 실행한 브라우저·테스트 결과, 사용자 문구 변경 전후, 남은 한계를 보고한다.
9. **소통 방식**: 사용자는 장황한 기술 수치보다 '무엇이 됐고, 무엇을 볼 수 있고, 어떤 한계가 남는지'를 먼저 듣고 싶다. 선택적 기술 정보는 아래에.
10. **기능 과잉 방지**: 플레이스타일 진화/9이닝/MLB-KBO 비교를 오늘 모두 끝내려 하지 않는다. 이번에 수정할 화면과 다음 연구 단계를 명확히 구분한다.

## 11. 앞으로 변경될 때 이 문서를 유지하는 방법

Codex는 단계 완료마다 아래 짧은 변경 기록을 `docs/PROJECT_STATUS.md` 또는 본 문서 하단에 갱신한다.

```text
날짜 / 최신 커밋:
이번에 실제 완료한 사용자 기능:
직접 실행한 테스트(명령·통과/실패)와 브라우저 화면:
실제 연구로 검증된 범위:
새로 발견한 편향·모델 한계·보안 위험:
이전 결과·데이터/모델/보고서 호환 여부:
아직 지원하지 않는 것:
다음 개발 작업 단 1~3개:
```

**프로젝트 방향 문서(Compass)**는 철학과 경계를 유지하고, **실행 문서(UX/Security Plan)**는 당장 고칠 화면과 구체적 인수 기준을 다룬다. 새 요청이 들어올 때마다 새 기획서를 중복 생성하지 말고 둘 중 어디를 바꿀지 판단한다.
